# 第七闸口轮换 · 计划书 v3

> **取代** `plan-gate-rotation-v2.md`。唯一变更：根因排序。v2 把「节点身份不稳定」排第一；诊断深化后，最根本的是「系统看不见自己的流量」，身份问题是它的一个后果而不是前提。v2 的数字一概不作为锚点，本文件全部数字来自本轮新上下文的实测。

## 0. 名词

| 词 | 意思 |
|---|---|
| 槽位（slot） | 一个独立的 sing-box 进程。全系统 7 个，slot-1..slot-7 |
| 第七闸口 / 池闸（slot-7） | 兜底槽位，端口 7897、Clash API 9097，选择器名 `proxy`，成员是机场池节点 |
| 选择器（selector） | sing-box 里的一个「虚拟出站」：内含节点列表 + 一个当前选中项，所有流量走选中项 |
| 入口名（tag） | 节点在选择器里的名字，形如 `cn.bing.com:443~7-any` |
| 出口（egress） | 真实落地的服务器地址。**请求额度消耗在它身上，不在名字上** |
| 凭据摘要 | 把账号/密码算成短哈希，用来区分「同一台机器上的不同用户」 |
| 归因（attribution） | 把一次请求的消耗，记到「当时正在服务它的那个出口」头上 |
| P2C | Power of Two Choices：随机抽两个候选，取分数高的那个。比全局最优便宜，比纯随机均匀 |
| Retry-After | 上游在 429 里给的「多少秒后再来」。实测回过 46999 秒（约 13 小时） |
| 出口级额度 | 换 IP 能绕过的额度 |
| 账号级额度 | 换 IP 也绕不过的额度 |
| 判死 | 把节点从候选里剔除一段时间 |
| 观测 / 盲切 | 调度器看得见 / 看不见 9router 的请求。决定走哪条选点策略 |
| 有列、无写入 | 表里有这一列，但没有任何代码路径给它写过非默认值 |

## 1. 资源模型：机场与 WARP 的约束方向相反

| | WARP | 机场 |
|---|---|---|
| 出口 IP | 会被封，可无限换新 | 固定一批，每台只有你在用 |
| 每个出口的额度 | 几乎不限 | **200–300 次请求** |
| 最优策略 | 发现被烧 → 立刻换新 IP | 谁用过、用了多少、下一个该用谁 |
| 换的动作本身 | 免费 | **要花一个新节点的额度，而且那一次请求可能失败** |

同一套调度器，在这两种约束下最优策略是**相反**的。现在这套代码是照 WARP 写的，然后拿来跑机场池——这是全部问题的总源头，比任何单点 bug 都根本。

你的前提把排序定死了：节点基本都可用，所以「怎么找到能用的」不是问题；**「用过」这件事才是**。

## 3. 因果链

按「最根本」排序，不按「最好修」。

### R1 · 系统看不见自己的流量（最根本）

请求由 9router 直接打到 sing-box 的 mixed 入站，**daemon 全程不代理流量**，只在换线那一刻 PUT 一下选择器。

所以「这个节点承接了多少请求」在 daemon 的视野里**结构上不存在**。不是它不肯记，是它看不到。

> 这一条是本轮诊断的主结论，也是 v3 与 v2 的全部差异所在。

### R2 · 于是只能用代理指标推断

| 代理信号 | 它真实代表什么 | 为什么偏 |
|---|---|---|
| 延迟 | 此刻连得上、快 | 越快越像「好用」，越被反复选 |
| 9router 错误率 | 已经出事的比例 | 只在烧穿之后才上升 |
| 最后使用时间（5 条） | 刚用过 | 只挡得住 5 个名字 |

三个都不等于额度。**用代理指标分配有限额度，必然退化成集中使用少数节点**：延迟低的被反复选，错误率只在烧穿后上升，最后使用时间只挡 5 个。

### R3 · 而「用过」这件事，账上是空的

三句定稿（写任何文档都用这三句）：

1. **节点侧**——有一列 `call_count`，**从未被写过非 0 值**（171/171 = 0）；另有一个按 tag 计「选中次数」的内存字典，20 分钟一清、不落盘、**数的是选中不是请求**。
2. **请求侧**——9router 有完整请求记录（47 万行），但**没有「走了哪个节点」这个字段**。
3. **两者之间**——缺一根线，不是缺数据。

关键在第 3 句：**两边各自都完整，中间断开。** 所以这件事的性质是**接线**，不是重建。

而就算线接上，内存那份计数也还有两个缺陷：4 个调用点里 2 个显式不计数（其中就包括 429 触发的那个），剩下在计数的那个三小时只发生 1 次。所以内存计数器不是「被 20 分钟清零清空」，是**根本没有东西可清**。

### R4 · 就算想均匀，也没有稳定的记账主体

系统里有**三套互相矛盾**的身份定义（见 2.1）。而真正被计数的键是 tag，tag 是订阅到达位次：删一个节点后面全体减一，加一个全体加一。

额度随 tag 走，tag 换指即额度换指。而 `node_info` 与 `.bad_nodes.json` **都没有指纹列**——换指之后，旧的判死、旧的 IP 会直接挂到新节点身上，系统自己无从察觉。

现网还有一对活例：同一台机器同时占着无后缀和 `~2` 两个 tag（同 SNI 同密码），因为 URI 源分支算出指纹后只记录、不跳过，JSON 源分支却会丢弃第二台——**同一个文件的两条源对「是不是同一台」给出相反答案**。

### R5 · 于是只剩「挑最快的」

`_strategy_mode` 默认 `normal` = 延迟优先；只有错误率超阈值才切 `pressure` = 均匀分散，盲切模式永远停在 normal。

正反馈闭环：

> 默认挑最快的 → 越快越被选（快本身就说明它可用）→ 被选最多的正是最快的 → 额度先烧穿 → 429 才把策略推成均匀分散 → 但此时已经烧穿，而 429 触发的轮换**又不计数**

**90.2% 的轮换由 429 触发**不是「被 429 推着走」，是它本来就没有别的信号可用。

### R6 · 去重把候选砍掉 70%，并且永久锁定

去重按台账里的 IP 分组，每组保留一条。意图正确（同一出口别重复用），但喂进去的 IP **不是节点出口**（R1/R4 的直接后果）：实测 202 候选 → **62 组** → 剔除 **140**（69.3%）。

更要命的是排序键：按 `call_count` 升序，而这一列恒 0 → 全部并列 → 稳定排序 → **永远保留候选列表第一条**。组内赢家永久固定，`pressure` 也换不动；输家只有「被选中」才刷新 IP，永不被选中 → 永不刷新 → **自锁**。

### R7 · 429 语义错位

429 被当 60 秒限速，冷却后再打。实测恢复中位 4.07 小时、复发 412/412 = 100%。每次 429 变成一串无效重试，而**每次重试都在真实烧额度**。

`Retry-After`（实测 46999 秒 ≈ 13 小时）是可靠的恢复时刻，系统只拿它覆盖一个默认值，没把它当成「这个出口在几点之前不能再用」的硬约束。

机场节点基本一一对应出口，所以换节点**有效**（这点与 WARP 不同）。也正因为有效，才更不该在同一出口上盲目重打。

### R8 · 判死是放大器，不是病因

79% 的判死来自单次探测失败，其中 61.9% 复测是通的。在「节点基本都可用」的前提下，这些大多是误判；但候选只剩 62 组，误杀一条的边际伤害被放大。

### R9 · 工程健壮性（最后）

池成员漂移无人重建（热重载不重建出站、自愈跳过池闸、16 小时零告警）；两个写者抢同一个选择器（一个锁外、一个锁内，4 次「回读不符」全部同秒配对到 keeper）。

## 3.5 设计约束：能复用的就复用，公共代码放到公共模块

这是本次的设计红线，优先级高于任何「顺手写一个」的便利。

**两条规则**
1. **能复用的就复用**——已有能力存在时，不重写一遍。
2. **要被复用的公共代码，放到公共模块**——不放在这次改动的文件里，更不复制一份。

**落到这个项目，已有能力清单**

| 已有能力 | 在哪 | 禁止 |
|---|---|---|
| Clash API 客户端（读写选择器、查成员、查连接） | `asip/clash_client.py` | 自己写 HTTP 请求 |
| 出口实测（trace URL、IP 探测、地域解析） | `asip/egress.py` | 自己调 ipify / ip-api |
| 原子写文件 | `asip/atomic_io.py` | 各写各的 `json.dump` |
| 脱敏 | `asip/redact.py` | 自己过滤敏感字段 |
| 成员比对（D-1 单一事实源） | `asip/config_projection.py` | 写第二份集合比较 |

**已知重复，本次要顺手消掉**

节点指纹（`server｜port｜type｜transport｜path｜host｜SNI`）目前在 `parse_subscription.py` 与 `dormant_probe.py` **各有一份相同实现**。S2 落地时抽到公共模块（`asip/identity.py`），两处都改成引用，**禁止留复制**。理由：S2 要往指纹里加凭据摘要，两份复制必然只改一份，那就是制造下一次身份分裂。

**模块归属规则**

- **跨槽位、跨用途**的算法（选点、去重、身份、计量、额度状态）→ `asip/` 下的公共模块。
- **只有第七闸口用**的编排（池闸的 /rotate 语义、keeper、恢复即回、池内换节点）→ `asip/gate/` 包。
- `asip/gate/` 是**包**，不是单个文件。

## 4. 方案

每个方案必须回答：**凭什么它能解决对应的那一环。**

### S1 · 给请求补归因（对 R1）

**做法**：把观测点从「daemon 自己猜」改成「从 sing-box 的 connections 接口读」——该接口逐条返回每个活跃连接经过的出站名，daemon 侧只需要按出站聚合，就能得到「某一时刻哪个出口正在服务」。

**为何能解决 R1**：这是唯一一条**不经由 daemon 代理流量却仍能看见流量**的路径。它不改 9router、不改 sing-box、不动订阅，只是把 daemon 的眼睛从「换线瞬间」扩展到「持续」。接上之后，「用过」第一次成为可测量的量。

**代价与边界**：connections 给的是连接级事实（活跃连接数、累计字节），不是请求数。在 keep-alive 下一条连接可能承载多个请求。所以第一步只求「哪个出口正在服务」这个事实成立，请求级精确计数留给 S3 校准。这个取舍已拍板。

### S2 · 定义记账主体（对 R4）

**做法**：身份 = `出口 IP + 凭据摘要`。凭据摘要参与指纹，使同一台机器上的不同账号被判为不同主体；出口 IP 参与指纹，使同一账号换入口不被误判为换人。

**为何能解决 R4**：它把三套互相矛盾的定义收敛成一套，并且**对准了额度的真正载体**（出口）。而 tag 位次漂移的危害是「账挂不住」——有了稳定主体，账挂在主体上，tag 变了不影响归属。

**代价**：每个节点至少要做一次真实出口实测，才能建立主体。这是一次性成本。

### S3 · 建立计量（对 R3）

**做法**：让每次请求的消耗落到 S2 定义的主体上。分两步：先把「某个出口当时在服务」这个事实记下来（接 S1 的线）；再把请求数按活跃连接/流量摊到出口上做校准。

**为何能解决 R3**：它把「两边各有数据、中间断开」变成一根线。而且**不再依赖 daemon 代理流量**——计量来自观测面，不来自转发面。

**为什么不做「让 daemon 代理流量然后自己记」**：那等于为了记账把转发路径重写一遍，风险远大于收益；而事实面本来就在 sing-box 手里。

### S4 · 用账分配（对 R5）

**做法**：把 `pressure`（均匀分散）变成默认，`normal`（延迟优先）变成例外（只在池子极小时启用）。

**为何能解决 R5**：它切断「挑最快 → 集中 → 烧穿」这条正反馈。分散的依据从「延迟」换成「用量」，而用量正是 S3 刚接上的那根线。

**为何排在 S3 之后**：没有账，均匀分散就是把一个瞎子改成另一个瞎子。

### S5 · 修去重数据源 + 组内可轮换（对 R6）

**做法**：分组键从「台账里的错 IP」换成「S2 的真实出口」；组内排序不再依赖那列恒 0 的 `call_count`，改用 S3 的真实用量。

**为何能解决 R6**：候选从 62 组回到接近 202；组内不再永久锁定同一个赢家；输家拿到被选中的机会，不再自锁。

**为何不排在最前**：它砍得最狠（剔除 70%），但**修好它只是给了系统更多可挑的**——只要分配依据还是延迟，系统照样挑最快的几个。它是量的问题，不是机制的问题。

### S6 · 重定义 429（对 R7）

**做法**：429 不再当 60 秒限速，而是「这个出口在 `Retry-After` 时刻之前不能再用」。同时动作从「等」改成「换节点」——因为换节点在机场模型下有效。

**为何能解决 R7**：复发 412/412 = 100% 说明「冷却后再打」等于白打。改成硬冷却 + 换节点，无效重试从一串变成一次。

**为何排在 S3 之后**：不知道那个出口还剩多少额度，就判断不了「该等」还是「该换」。

### S7 · 判死（对 R8）

**做法**：判死前置条件从「单次探测失败」改成「连续 N 次 + 与用量交叉验证」。

**为何能解决 R8**：它把「额度耗尽」和「链路坏了」分开。前者是换节点能解决的，后者才是判死该管的。

### S8 · 工程健壮性（对 R9）

池成员漂移纳入自愈路径与告警；选择器写入收敛到单一写者。

## 5. 因果对应

| 根因 | 对应方案 | 修好的判据 |
|---|---|---|
| R1 看不见流量 | S1 | 每个出口的实时服务状态可查询 |
| R3 账是空的 | S3 | 每个主体上有请求数，且随时间递增 |
| R4 身份不稳 | S2 | 同一台机器同一账号，无论名字怎么变，主体恒定 |
| R5 只挑最快的 | S4 | 不再出现「少数节点承担绝大多数请求」 |
| R6 候选坍缩 + 自锁 | S5 | 候选数回到接近池规模；组内赢家随用量变化 |
| R7 429 语义 | S6 | 429 后不再在同一出口上重复失败 |
| R8 判死误杀 | S7 | 复测为通的节点不再被判死 |
| R9 工程 | S8 | 成员漂移与并发写在告警中可见 |

## 6. 明确不做

1. **不让 daemon 代理流量来记账**——为了记账重写转发路径，风险大于收益。
2. **不改 9router**——观测走 sing-box connections，不侵入别人的服务。
3. **不改订阅解析的 `~N` 生成规则**——它是位次语义，改了会波及一切按 tag 存的状态；替代方案是 S2 让账不依赖 tag。
4. **不先修判死**——它不是病因，修好它池子还是 62 组。
5. **不引入新的第三方依赖**——`asip/gate/` 只用标准库与既有 Clash API 封装。

## 7. 验收判据

| 阶段 | 判据 |
|---|---|
| S1 | 连续 30 分钟内，每个出口的服务状态可查询，且与 9router 的错误时间戳能对上 |
| S2 | 抽查 20 个节点，`出口 IP + 凭据摘要` 恒定，名字变化不影响归属 |
| S3 | 每个主体上的计数随真实请求递增；进程重启不丢失 |
| S4 | 连续 24 小时，任一出口的请求占比不超过 `2 / 活跃出口数` |
| S5 | 候选数 ≥ 池规模的 80%；组内赢家在 24 小时内发生变化 |
| S6 | 429 后 13 小时内，同一出口不再被选中 |
| S7 | 复测为通的节点不再被判死（抽样 0 例） |

## 8. 风险与回滚

| 风险 | 触发 | 回滚 |
|---|---|---|
| connections 轮询开销 | 池规模增长 | 降采样；只保留活跃出口 |
| 请求级计数是估算 | keep-alive 下连接≠请求 | 只在 S3 校准；不进 S4 的硬指标 |
| 凭据摘要的哈希碰撞 | 同摘要不同账号 | 摘要加盐；碰撞概率按 128 位计 |
| S4 立刻改默认策略 | 分散后整体延迟上升 | 单键回退到 `normal` |
| S5 候选暴增 | 池节点并入 | 保留候选上限；分批放开 |

每个方案都有独立开关，可单独回退；所有开关默认「旧行为」，灰度逐个打开。
