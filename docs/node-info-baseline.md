## B. 整列判废

- **`node_info` 的 ip / country / city / isp 四列**：至少 141 / 171 行必然错误。四重证据：
  1. 16:28–16:33 有 31 条记录横跨 5 个以上机场域名，全部写成同一个地址；
  2. 单地址 67 行横跨 25 个不同域名族；
  3. 独立实例抽测 10 个（8 个可用）出口互不相同，0 个命中该地址；
  4. 离线扫描产物中 13 个节点有 9 个与台账不一致。
- **判死名单文件**：叠加了多批过期条目，不能当作某一时刻的死节点集合。可靠来源是主循环状态行自报的 `dead=N`。
- **日志里"切换成功"行打印的节点地址**：是上一跳的缓存值，不是当次实测。
- **已作废的指标**：429 按地址口径的 68.4% / HHI 0.4758 / "等效 2.1 个出口" / "66.2% 轮换同地址" / "5 连窗 96.3% 重复"。这些全部建立在被污染的那一列上。

## C. 待测

1. **修复后的真实并发宽度**：现有独立实测只有 13 个节点 → 10 个出口，且集中在三个同源域名，不能外推。
2. **单节点额度与重置窗口**：Retry-After 的证据全部来自 WARP 侧，池侧没有一份带时间戳、覆盖足够样本的标定。
3. **"429 在节点名上近似均匀（Top5 仅 10.5%）"的成因**：目前只有观测，没有机制解释。

## D. 待修（按收益排序）

1. **节点地址按节点自身测量**：先把该节点切到被测进程，再从**该进程的端口**查询出口（闸口现成就有 9097 + 7897），并把测量端口与测量时刻一起落库。
2. **去重不再以该列为键**：现在按错误标签连坐剔除 141 个健康候选，这是候选饥饿的直接原因。
3. **请求级归属**：请求明细与用量历史里没有任何节点字段，连接标识全为空 → "每个节点用了多少"这件事全系统不存在。
4. **台账改软删**，并补"上次使用""首次出现""所属槽位"三个维度；现在是覆盖式写入 + 按白名单硬删，节点一下线历史就没了。
5. **修正那条自证正确的代码注释**：它写着"这是该出口真在被服务的准确时刻"，而请求实际走的是主进程端口。错误前提以"已经实测过"的语气固化下来，是后续所有误判的源头。

## E. 口径限制（引用数字时必须带上）

1. 主结论用 02:43:35 之后的 2027 条；更早的 617 条属于重启前段，内存状态在 02:39 被清空，跨边界的窗口不满足"同一份内存状态"前提。
2. 台账行 = **被选中 ∧ 测量成功 ∧ 仍在选择器内**，是三重过滤后的结果，不是抽样。所以 171 行只能读作"被测量成功率"，不能读作覆盖率或健康度。
3. 429 有两个不可混用的基数：**尝试级 3252**（含早期段、口径不同、未独立复核）与**事件级 2385**（主表用这个）。
4. 那一列错误数据有**两个消费者，状态完全不同**：去重（无门控，**当前正在生效**，把 202 压成 61 组、剔除 141 个候选）与 6 小时脏出口避让（受观测模式短路，**当前惰性**，降级到盲切时会把整桶节点当脏出口集体回避）。不能只说"惰性"——第一条的扳机已经扣下了。
