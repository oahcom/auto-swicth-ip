# H2 为什么几乎不被选为主出口 —— 2026-11-05 调查

> 问题：`opencode-out` 选线时，31 条 H2 线在全天 303 次换线里只拿到 143 次，
> 且 12:00 之后断崖（13:00 那一小时 34 次换线、H2 **0** 次），而当时池子里
> 每天都有 8~14 条新鲜 H2 候选。
>
> 本文只记录**证据与机制**。结论分三档置信度，最后一段列出可改项与风险。

## 一、先排除三个不是原因的假设

| 假设 | 实测 | 判定 |
|---|---|---|
| H2 线在重启中，被 `warming` / `_WARP_REFRESHING` 挡掉 | 每次换线时「重启中」的 H2 线数为 **0**（全天） | 否 |
| H2 没有新鲜候选 | 13:00 那 34 次，平均 **8.1 条** H2 在 120s 内有模型层 OK | 否 |
| 地址被封（惩罚期） | 全天 303 次里「有 OK 但地址已封」只有 **1** 次 | 否 |

`_warp_line_fresh_candidates`（`daemon.py:4920`）的准入条件全部满足，
问题在准入之后的**排序**。

> **2026-11-05 已按本文结论改代码**：档 1 与档 2 对调（`probe_ok_ts` 优先于
> `last_ok_ts`），两档内都改成「越新越优先」。下面第二、三节记录的是**改动前**
> 的状态与证据。

## 二、主机制：H2 基本进不了档 1，而这与「H2 重启太快」无关

`_warp_ip_rank`（`daemon.py:6232`）改动前的档 1 判据是 `entry["last_ok_ts"]` 为真。
这个字段的语义是「该地址**撑过生产流量**」，唯一写入点是
`_record_active_ip_success`（`daemon.py:6132`），它只给 `_ACTIVE_WARP_IP` 记账
—— **备线服务得再好也拿不到这个章**。再加上 `_warp_line_restart` 拿到新地址后
`st["last_ok_ts"] = 0.0`（`daemon.py:5163`），同一个地址也继承不了上一次的成功。

**最初怀疑是「H2 重启太快，章刚盖上就被抹掉」。实测否掉了这个解释**：
每线重启间隔中位 H2 17s、WG 11s、CF 17s —— WG 重启得比 H2 还勤。

真正的机制是**正反馈**：当选的线是活动线，活动线只换不重连，于是它持续服务
生产流量、保住 `last_ok_ts`、继续当选；落选的线被探测器按脏地址反复重启，
每次重启都把 `last_ok_ts` 清零。全天 37 553 个出口地址里只有 **61 个**
（CF 22 / WG 13 / H2 26，占 0.1~0.5%）带这个章 —— 稀缺本身就是证据。

**结果：H2 几乎总在档 2，而少数几条 WG/CF 长期占着档 1，且档 1 没有时效上限。**

`ban_probes`（RLE 连续观测段，覆盖全天、不受台账「只留最后一次」影响）重建
13:00 的赢家：34 次换线由 **16 条不同的线**拿下，它们当时都处在
**1~6 小时不间断的 OK 段**里：

```
WARP-CF-F   ×5  连续 OK 段 18692s      WARP-WG-10  ×4  连续 OK 段 21618s
WARP-WG-11  ×5  连续 OK 段  4297s      WARP-WG-2   ×4  连续 OK 段  3870s
WARP-WG-18  ×2  连续 OK 段  5638s      WARP-WG-17  ×2  连续 OK 段  3088s
```

这 16 条线是「只要不重启就一直赢」的那批 —— 不是作弊，是档 1 的正反馈：
被选中 → 服务成功 → 拿 `last_ok_ts` → 永远优先 → 继续被选中。

## 三、次机制：同档内「验得越久越优先」把 H2 钉在末尾

`_warp_ip_rank` 改动前档 2 的排序值是 `-(now - probe_ok_ts)`（原 `daemon.py:6199`），
即**证据越旧越优先**。注释给的理由是「验得越久越接近 TTL，不用就白验了」。

H2 在风暴里被反复重启、反复重探，`probe_ok_ts` 永远最新 → 排序值恒为最差。
实测非 H2 胜出的 126 次里，**102 次（81%）赢家的 OK 证据比落选的 H2 候选更旧**
—— 纯粹赢在「验得早」，不是赢在「更可能可用」。

而且这个启发式**没有预测力**：按被选中线自身的 OK 年龄分桶，段内存活并不是
单调的（0–10s→10s，10–30s→8s，30–60s→4s，60–90s→8s，90–121s→7s）。

## 四、校正：H2 的「短命」是选它的时机造成的

先前的口径（全天 H2 中位 6s vs CF 30s / WG 36s）会被时段混淆：H2 只在没什么
新鲜线时才被推上去，那时任何线都活不过几秒。同一小时比较：

| 时 | H2 | WG | CF |
|---|---|---|---|
| 05 | n=26 中位 **11s** | – | n=10 中位 12s |
| 08 | n=17 中位 **5s** | n=12 中位 6s | n=1 中位 38s |
| 13 | 无 | n=23 中位 22s | n=11 中位 11s |
| 14 | n=3 中位 **9s** | n=9 中位 7s | n=7 中位 11s |
| 17 | n=13 中位 5s | – | n=13 中位 **3s** |
| 18 | n=23 中位 5s | – | n=8 中位 6s |

同一时段内**没有线型差异**。全天 6s 对 30s 的差距来自「H2 只在坏时段上场」。

校准测试：若选线对候选一视同仁，H2 的期望选中次数 = Σ(每次换线池中 H2 占比)。
全天实际 158 / 期望 227.9 → **A/E = 0.69**；13:00 → **0.00**；14:00 → 0.34；
06:00/07:00/18:00 → 1.00（那时段根本没有别的线，不是「更公平」）。

## 五、供给侧才是更大的问题（与选线独立）

### 5.1 92% 的地址获取量打在 2% 的坑里

H2 每次重启拿到一个 /128。按**获取那一刻**其 /64 的状态分档，看首个模型层结论：

| /64 状态（获取时） | 获取数 | 首个结论数 | OK | quota | OK 率 |
|---|---|---|---|---|---|
| 干净段 | 932 | 900 | 276 | 623 | **30.7%** |
| 已用未烧段 | 856 | 838 | 313 | 517 | **37.4%** |
| 已烧段 | 20 824 | 19 677 | 395 | 19 228 | **2.0%** |

WG / CF 同向（WG 8.8% / 1.9% / 0.6%；CF 22.4% / 38.8% / 0.9%）。

> **与既定事实的冲突（待复核）**：`CLAUDE.md` 与 `established-facts.md`
> 有「别把 /64 段状态当选线判据」一条，依据是「已烧段全新 /128 OK=0/2469（0%），
> 未烧段 3/152（2.0%）」。那个实验用**最终台账**分段（含未来信息），本表用
> **获取时刻**分段，结论相反。两套口径必须再跑一次时间序回放才能定稿；
> 在定稿前**不要**据此加段级准入。

### 5.2 五条线吃掉 26% 的重启量，产出 4.5%

| 组 | 重启 | 拿到地址 | 模型层 OK | 重启/OK |
|---|---|---|---|---|
| 低产组（TPE-5/6/18、ICN-10/22/23、NRT-0/1/13/14、SLC-11/12/24、HKG-8） | 29 192 | 28 365 | 88 | **331.7** |
| 其余 H2 | 81 560 | 77 111 | 1 856 | **43.9** |

低产组每条线的 `ban_probes` 都是 1000+ 次里 OK 为 0~75 次，且 `ban_hold_until`
都是空的（`_channel_ban_hold_hit` 要求「当天全部 quota」，这些线偶尔出一次 OK
就永远锁不上，`daemon.py:3237`）。它们是**永久低产但不满足锁定条件**的线。

## 六、置信度分档

| 结论 | 依据 | 置信度 |
|---|---|---|
| `last_ok_ts` 只发给当前出口，备线服务再好也拿不到 | 代码直接可读（`daemon.py:6132`） | **确定** |
| 重启会清空 `last_ok_ts`；但重启频率**不是** H2 劣势的原因（WG 更勤） | 代码 + 日志统计 | **确定** |
| 档 1 无时效上限，少数线可长期垄断 | 代码直接可读（`daemon.py:6232`） | **确定** |
| 13:00 赢家是 16 条处在 1~6h OK 段的线 | `ban_probes` 段回放 | **高** |
| 同档「验得久优先」使 102/126 次由更旧的证据胜出 | 日志 OK 事件重建 + `ban_probes` | **高** |
| 各小时 A/E 比值 | 日志重建候选池 | **中**（见下） |
| 干净段 OK 率 30% vs 已烧段 2% | 顺序敏感的分档回放 | **中**（与既定事实冲突） |

**已知的回放偏差**：`· TTL 内已有 OK`（`daemon.py:6447`）**不刷新** `last_ok_ts`，
只复用探测缓存；重建脚本把它当成了刷新，候选池因此偏「新鲜」。这会让 A/E
的绝对值偏高，但**不改变档位归属的方向**（H2 仍然不会进档 1）。
另：台账只保留最后一次 `last_ok_ts` / `probe_ok_ts`，凡晚于选择时刻的记录一律
无法回溯，因此档位归因里有一半是 UNKNOWN，本文只用可精确判定的部分下结论。

## 七、最终改动（2026-11-05 实施）

主人拍板的两条，已实现并跑绿全量测试（903 项）：

| # | 改动 | 位置 | 语义 |
|---|---|---|---|
| **1** | 档 1 与档 2 对调：**探针刚验过 OK（`probe_ok_ts`）排到「撑过生产流量」（`last_ok_ts`）之前** | `_warp_ip_rank` | 探针是每条线都在跑的**此刻**结论；`last_ok_ts` 只由当前出口挣得、重启即清零，奖励的是「一直没被换下」 |
| **2** | 两档的档内排序都改成**越新越优先**（排序值取正） | `_warp_ip_rank` | 刚刷出来的 OK 说明这个地址这一刻还没被烧；原先「越旧越优先」的理由（怕 OK 过期白验）在 30min TTL 下不成立 |

不变的部分：档 0（从没出现过）仍在最前；档 3（从无成功记录）仍在最后；
`/64` 静置仍是同档内的第二判据；`_warp_ip_needs_refresh` 仍只刷档 3；
探针 OK **仍然不写** `last_ok_ts`（两档的存在意义就是把这两个维度分开）。

**未采纳的三条**（记录理由，避免以后重复提）：

- **档内改成「最久没被选过」轮转** —— 与改动 2 重复，且「越新越优先」更贴合
  「刚刷出来的 OK 还没被烧」这个正向信号。
- **给档加时效上限** —— 对调 + 越新优先之后，旧证据天然排在后面，不需要额外阈值。
- **停掉低产线 / 加段级准入** —— 低产不等于无产；段级口径与
  `established-facts.md`「别把 /64 段状态当选线判据」冲突，以文档为准。

**不要做**的：把探针 OK 写进 `last_ok_ts`。`daemon.py:6532` 的注释已论证：
那会让「只在空跑里验过」的地址与「撑过流量」的地址同权（台账 2945 条里 738 条
属于这种）。

## 八、复现方法

日志：`daemon.log{,1..5}`（`daemon.log.5` 起于 02:17，`daemon.log` 截止 19:07）。
解析脚本放在 `/tmp/opencode/`（未入库）；关键几条：

- 候选池重建：按 `✓ WARP 换线成功:` 时刻，取 120s 内有 `模型层: OK` /
  `TTL 内已有 OK` 的线，排除被选者与当前线
- 段存活：相邻两次 `换线成功` 的时间差，上限截断 600s
- 档位回放：`ban_probes` 的连续段（`[起, 止, 条数, 结论]`）取选择时刻所处的段

⚠ 重建无法 100% 复现真实选择（实测复现率 2%），原因是台账只留最后一次结论 +
缓存命中不刷新 `last_ok_ts`。任何**定量**反事实（「改选 H2 会更好吗」）都只能
当方向性参考；本文引用的绝对数字仅用于横向比较，不作承诺。
