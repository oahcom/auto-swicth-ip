# opencode 429 限流机制 — 最终结论

> 日期：2026-11-12 | 实测消耗约 2939 发（机场 v4/v6 + WARP）| 32 条 IP 打空
> 结论基于行为实验（同秒对齐反推窗口、五组独立样本、并发梯度），不基于猜测。

## 一句话结论

opencode 对每个出口 IP 有**两道独立闸**：**L1 = 累计 40 个不同 session 即全封**，**L2 = 24h 滚动窗口总发数额度（各 IP 不同，0–358 发）**。命中先到的那道，两者返回**同一个错误体**。

---

## 一、结论总表

| # | 结论 | 关键证据 | 置信度 |
|---|---|---|---|
| 1 | **L1：同一出口累计 40 个不同 session → 整条出口全封（含老 session）** | 5 个独立 `stop=quota` 样本，跨 3 个 ASN，全部精确停在第 41 个 session | 高 |
| 2 | **L2：额度按 IP 计，24h 滚动窗口，各 IP 上限差异极大（0–358 发）** | 已测到顶：215/244/257/358/272/261/239/132/135 | 高 |
| 3 | **两道闸返回同一错误体，无法从响应区分** | 429 正文 208 字节，恒为 `FreeUsageLimitError` | 高 |
| 4 | **窗口是滚动 24h，不是统一 08:00 重置** | 同秒对齐发射 4 个已 429 IP，反推 T 跨度 2042s（34 分钟） | 高 |
| 5 | **并发不消耗额度、不产生干扰** | 16 路 272 发 > 1 路 261 发；32 路 239 发；全程 trans=0 | 高 |
| 6 | **额度由 IP 余额决定，与 session 数无关** | 1 session=358 发 > 15 session=85 发 > 20 session=90/74 发 | 高 |
| 7 | **v4/v6 无机制差异** | v6 单 session 110/244/257/358，与 v4 108–272 同量级；L1 阈值两者都 40 | 高 |
| 8 | **换 session 重试不仅无效而且有害** | L1 满后老 session 一并封；每换一次吃 1 个名额 | 高 |
| 9 | **"IP 分等级"假说未被支持** | 能打的差不到 1.7 倍（215–358），0 发的差无穷倍 → 更像同批池子被消耗到不同进度 | 中（需额度回满后复测） |

**未证实 / 暂不下结论：**
- L1 的 40 记在哪一层（单 IP / /64 / 全局）——缺"同段两出口各 20 session 合计 40"的对照。
- "分级" 与 "同批资源池被用空" 仍不可区分，需等各 IP 按 `Retry-After` 回满后复测。

## 二、两道闸的判定规则

| 层 | 计数单位 | 阈值 | 是否随 IP / 地址族变 | 触顶表现 |
|---|---|---|---|---|
| **L1 session 闸** | 同一出口用过的**不同 session 数** | **40** | 不变（v4 各段、v6 全为 40） | 第 41 个 session 起 429，**已用过的老 session 也一起 429** |
| **L2 发数额度** | 同一出口**总请求数**（滚动 24h） | 按 IP 分档，实测 0–358 | 变，且分布连续无阶梯 | 达到该 IP 余量后 429，`ra` 倒计时到窗口滑出 |
| **L3 窗口重置** | 时间 | 该 IP 窗口内最早请求 + 24h | 各 IP 不同（实测 08:13–08:58） | `ra` 按 elapsed 逐秒递减，重置时刻 T 恒定 ±1s |

**怎么判断命中哪道闸**：看"发数 vs session 数"哪个先到 40 量级。
- 单 session 连打：只占 1 个名额，必然先撞 L2。
- 每发换 session：发数 = session 数，先撞 L1。
- 旧文档里"40 发上限"与"40 session 上限"其实是同一个数字——一直是两道闸里先到的那道。

### 关键实测：滚动窗口（决定性实验）

22:00:10 同一秒对 4 个已 429 的固定 v4 出口各打一发，`t` 完全相同，差值即 T 差值：

| IP | Retry-After | 反推恢复时刻 T | 相对偏移 |
|---|---|---|---|
| 64.120.94.207 | 36801 | 08:13:31 | +0 |
| 154.83.87.187 | 37324 | 08:22:14 | +523s |
| 45.207.156.48 | 37820 | 08:30:30 | +1019s |
| 134.195.101.195 | 38843 | 08:47:33 | +2042s |

40 秒后复打，`ra` 精确递减（36801→36760，即 −41；37324→37285，即 −39），T 保持不变。**证明 `ra` 是从绝对时刻起算的倒计时，且各 IP 的 T 天然不同 → 滚动 24h 窗口。**

> 推论：**"等到次日 08:00 再用"是错假设**，08:00 对绝大多数 IP 无意义；`ra` 会在最早请求滑出窗口时跳变，非线性归零。生产必须按各自 `Retry-After` 排期。

## 三、关键实测数据

### 1. L1 = 40 session（5 个独立样本，跨 3 个 ASN）

| 出口 IP | 来源 | 结果 |
|---|---|---|
| `2405:84c0:8060:4500::` | 机场 v6 | 第 41 个 session 429，ra=40369 |
| `2405:84c0:8060:7f00::` | 机场 v6 | 第 41 个 session 429 |
| `52.196.41.126` | AWS 东京 v4 | 第 41 个 session 429，ra=34703 |
| `13.158.42.154` | AWS 东京 v4 | 第 41 个 session 429，ra=37344 |
| `103.175.99.31` | upoz v4 | 第 41 个 session 429，ra=35367 |

**L1 满后老 session 一并失效**（`13.158.42.154` 实测）：老 session A 首打 200 → 38 个新 session 全 200 → 第 39 个新 session 429 → **回头用 A 打也 429**，再开新 session 仍 429。
→ L1 不是"新 session 准入控制"，是**整条出口全封**。

### 2. L2 额度分布（已测到顶的 IP）

| IP | 地址族 | 额度 | 备注 |
|---|---|---|---|
| `2602:f988:84:4f7::e6b` | v6 | **358** | 单 session 顺序，最高 |
| `216.234.143.116` | v4 | **272** | 16 路并发 |
| `152.175.33.133` | v4 | 261 | 单路顺序 |
| `2a0c:9a40:9205:1:be24:11ff:fe8f:aa81` | v6 | 257 | 单 session |
| `2405:84c0:8001:bf00::` | v6 | 244 | 单 session |
| `104.28.205.194` | v4 | 239 | 32 路并发 |
| `64.120.94.207` | v4 | 215 | — |
| `154.83.87.187` | v4 | 156 | 37 session / 156 发 → **L2 先到** |
| `2a09:bac1:4c00::245:d3` | v6 | 86 | 16 路并发 |
| `82.152.160.7` | v4 | 90 | 20 固定 session |
| `160.248.69.190` | v4 | 74 | 20 固定 session |
| `2a09:bac5:1f07:1232` | v6 | 85 | 15 固定 session（72+13） |
| 其余 8 个 v4 | v4 | 0 | 首次探测即 429 |

分布**连续、无阶梯、无分档边界** → 不支持"按等级分档"，更像同一批资源池被消耗到不同进度。9 个"真·首次即 429"的样本（AWS 三台 + WARP 五个 /128 + 134.195.101.195）证明**池子里大量 IP 余额为零**。

### 3. 并发梯度（单 session）

| IP | 家族 | 并发 | 额度 | 用时 | 吞吐 |
|---|---|---|---|---|---|
| 216.234.143.116 | v4 | 16 | **272** | 38.8s | 7.0 发/s |
| 152.175.33.133 | v4 | 1 | 261 | 423.6s | 0.62 发/s |
| 104.28.205.194 | v4 | 32 | 239 | 40.7s | 5.9 发/s |
| 2405:84c0:8001:3200:: | v6 | 1 | 110 | 189.6s | 0.58 发/s |
| 2a09:bac1:4c00::245:d3 | v6 | 16 | 86 | 18.2s | 4.7 发/s |

- 16 并发 272 > 1 并发 261：**并发不碰额度**；全程 `trans=0`，无并发冲突。
- 吞吐 16 路是 1 路的 11.4 倍；32 路反降到 5.9 → **16 路是效率拐点**（再高只增内耗）。

### 4. session 数 vs 额度（方向性反证）

| 测法 | 样本 | 结果 |
|---|---|---|
| 单 session 固定 | 152.175.33.133 / 2602:f988 | 261 / **358** |
| 15 固定 session | 2a09:bac5:1f07:1232 | 85 |
| 20 固定 session | 82.152.160.7 / 160.248.69.190 | 90 / 74 |
| 每发换 session | 2405:84c0:8060:4500:: | **40**（= L1 阈值） |

**session 越少打得越多**，总量只由 IP 余额决定。唯一与 session 有关的硬闸是 L1 的 40。

### 5. v6 专项（用户要求的对照组）

- v6 单 session 连打 200 发，**3/3 出口全部 200 未触顶**（逐发校验出口 IP 未漂移）。
- 续测到顶：244 / 257 / 358 → **不存在打不完的出口**。
- v6 多 session：第 41 发 429（`8060:7f00` / `8060:4500`，复核全新 session 仍 429）。
- `8040:9e00` 段第 19 发即 429 → 该出口 L2 先到（余额仅 19）。
- 结论：**v6 与 v4 同机制同量级，无地址族特权，也无额外惩罚。**

### 6. 429 响应体（两条闸完全一样）

```
{"type":"error","error":{"type":"FreeUsageLimitError","message":"Free usage limit reached..."}}
```
208 字节，无 `Retry-After` 以外的可用信号，`ra` 落在响应头。**无法靠错误体区分 session 闸与额度闸**，只能靠"发数/ session 数哪个先到 40 量级"判别。

## 四、已撤回的结论（勿再引用）

| 错误结论 | 推翻原因 |
|---|---|
| 429 按内容指纹限流 | 同内容不同 IP 结果不同 |
| session 是唯一维度 | 单 session 也能打到 358 发 |
| 生产单 IP 最高 115 发 | `count_segment_requests` SQL 无 slot 过滤，统计口径错 |
| 额度按 /24 分段 | 同段 `45.95.212.122`=132 vs `.167`=40 |
| 换 session 重试可恢复 | 会加速撞 L1，且 L1 满后老 session 也封 |
| WARP "只值 10 发" | 18:22 那轮是池子被榨干，不是 WARP 特性 |
| "IP 每 1-2 分钟自漂移" | IP 变化与 `systemctl restart` 一一对应 |
| "次日 08:00 统一重置" | 同秒对齐实验证伪，各 IP T 跨 34 分钟 |
| "按段分级" | 原论据（210 发）是 WARP 漂移数据，作废 |

**方法论坑（下次别再踩）：**
- **WARP 会换整个 /32**：任何起止 IP 不一致的数据必须作废。
- **tag ≠ IP**：多个入口 tag 共享同一落地机（`67.159.48.148` 同时是 `pq.aws65` 和 `downloadcfpro~3-vl` 的出口）。必须先解析出口 IP 再比对全局台账。
- **不同时刻的请求 + 各自 `ra` 反推不了 T**：必须同一秒对齐发射。
- **统计前先查自己打没打过这个 IP**：否则"首发 429"里混着自污染样本。
