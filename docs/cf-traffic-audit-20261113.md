## 三、反例：IP 活着时能撑多少

今天表现最好的两条，证明「IP 没被打死时，生产流量能持续打进去」：

| 线 | 出口 IP | 请求 | 成功 | 429 | 存活 |
|---|---|---|---|---|---|
| WARP-CF-G | `2a09:bac5:1f03:1232::1d0:ba` | **76** | **76** | **0** | 975s |
| WARP-CF-C | `2a09:bac5:1f03:3046::4cf:5f` | 39 | 38 | 0 | 1,040s |

这两条都不是被额度打死的（0 个 429），而是流量被别的槽位/请求分走才停。**说明 IP 侧完全撑得住连续几十发，问题不在 IP 能力。**

`/64` 维度同样支持：`2a09:bac5:1f03:1232::/64` 全天 82 发、95% 成功；而 `2a09:bac5:1f01:3050::/64` 95 发只有 2 发成功。同样是 ~90 发的量级，一个 95%、一个 2% —— 差别在**出现时间**（前者在 11:00–12:00 新鲜期，后者在 14:00 之后）。

## 四、为什么不复用：换线次数比请求数还多

| 指标 | 数值 |
|---|---|
| 26 小时 rotate 总次数 | **30,350** |
| 其中真实换线 `reason=ok` | 10,914 |
| `already_retired`（重复请求已退休槽位） | 13,789 |
| `no_healthy_slot`（换不出去，原地重启） | 3,750 |
| 生产总请求 | 17,468 |
| **rotate / 请求** | **1.7 倍** |

平均每个请求触发 1.7 次 rotate，每次换线产生一个新的 (线,IP) 组合 → 4,541 个组合承接 17,468 个请求 → **平均每个 IP 只分到 3.8 发**。

一个 IP 要打到 300 发，前提是「300 个连续请求期间零换线」。而当前机制是**一遇 429 立即换线**，429 率 71%，所以任何 IP 在攒到 300 之前必然被切走。

## 五、池子被打穿的时间线

11:00 是额度重置后的新鲜池子，14:00 已基本打空：

```
11:00  ████░░░░░░░░░░░░░░░░   0%  新 IP 首死，91 发 99% 成功
12:00  ████████░░░░░░░░░░░░  42%
13:00  █████████████░░░░░░░  68%
14:00  ██████████████████░░  94%   ← 崩盘点
15:00  ████████████████░░░░  80%
...
01:00  ████████████████████ 100%
```

14:00 之后，**新换出来的 IP 有 80–100% 第一发就 429**。此时换线只是从一个死 IP 换到另一个死 IP，`no_healthy_slot` 3,750 次就是这么来的。

## 六、额度是谁烧掉的

daemon 探测日志（`✓ ... 模型层: OK` = 真吃掉 1 格额度）按小时对照生产：

| 小时 | CF 生产请求 | 探针判 OK 次数 | 探针触达的不同 IP |
|---|---|---|---|
| 14:00 | 425 | **1,343** | 1,338 |
| 15:00 | 477 | 998 | 990 |
| 16:00 | 414 | 1,134 | 1,119 |
| 17:00 | 361 | 862 | 850 |
| 18:00 | 197 | 545 | 540 |
| 19:00 | 38 | 229 | 224 |
| **全天** | **3,377** | **6,329** | — |

**探针每小时在 1,000+ 个不同 IP 上各消耗 1 格，生产每小时只用 400–500 格。探针消耗是生产的 2–6 倍。**

探测器不是在验「正在用的线」，而是在「每条线重启 → 打 1 发 → 判 quota → 再重启」的流水线上跑。它每验证一次就把那格额度用掉了，然后把这条线留给生产时已经少一格。

## 七、结论

**「生产用不到 300」不是容量不存在，是三个约束叠加，让任何一个 IP 都没有机会攒到 300 发：**

1. **需求密度不足（决定性）**：CF 全天 3,377 发，摊到 421 个 IP = 平均 8 发。哪怕把所有 CF 请求全压到单一 IP 上，上限也只有 3,377。要单 IP 打满 300，需要 300 个请求在同一个 IP 上连续通过，而生产每小时 CF 只有 100–470 发、分散在 9 条线 × 6 个槽位。
2. **一 429 就换线（结构性）**：429 率 71%，IP 存活中位 12 秒。每换一次就换新 IP，等于把本来可以累积的发数每次清零。26 小时 rotate 30,350 次 > 请求 17,468 次。
3. **池子在 14:00 被打穿（环境）**：之后 80–100% 的新 IP 第一发就死，换 IP 无效。此时即使需求足够，也攒不起发数。

**300+ 是「单 IP 无干扰、独占流量」条件下的上限；生产是「多槽并发 + 429 立即换线 + 探针同时消耗」，三个条件都不满足，所以永远不会出现 300 发/IP 的观测值。** 观测到的 2 发/IP 不是 IP 的能力，是架构的产物。

**要真的把单 IP 用量提上去，只有两条路：**
- 减换线：429 不再无条件换 IP，先在同 IP 上退避重试（把 71% 的 429 变成等待而不是换线）；
- 减探针：在槽线免探，探测只服务待命线（当前探针消耗是生产的 2–6 倍）。

## 八、补查：额度没用完为什么被切走

对 30,350 条 rotate 按「所属请求的报错来源」归类（rotate 打在 429 之前，必须按请求整体判定）：

| 触发源 | 全量 rotate | 占比 | CF 作为被换走方 | 占比 |
|---|---|---|---|---|
| 429 | 20,745 | 68.4% | 1,955 | **59.6%** |
| **transport（header-timeout）** | **9,154** | **30.2%** | **1,269** | **38.7%** |
| 无报错（被槽位调度挪走） | 451 | 1.5% | 56 | 1.7% |

**CF 有 38.7% 的换线发生在「这条线一次 429 都没有」的情况下**，触发源是请求头超时，不是额度。

### 硬证据：今天最强那条线

`2a09:bac5:1f03:1232::1d0:ba`（WARP-CF-G）：76 发、76 成功、**0 个 429**、存活 975s。
它被换走 6 次，逐条查触发源：

| req | reason | 触发源 |
|---|---|---|
| wd0emt828 | already_retired | transport |
| wd0ggeb35 | ok | **transport**（body 795KB，20s 超时） |
| wd0j1y34s | already_retired | 429 + transport |
| wd0j83w4u | already_retired | **transport**（body 800KB） |
| wd0zco97k | ok | **transport** |
| wd16kwkan | ok | 别的请求的 429 |

**6 次里 5 次是超大请求超时（795–800KB），跟这条线的额度没有任何关系。**

### 超时预算与实测

- `resolveHeaderTimeoutMs`：20s + 每 500KB 加 15s，封顶 55s。11-12 11:56 起生效（之前固定 20s）。
- 生效后仍撞天花板：`45000ms` 超时 **441 次**，`20000ms` 184 次（11:56 前的旧进程）。
- transport 超时请求体：中位 **591KB**、p90 **847KB**、max 1088KB。
- 换线重放取 `max(首次预算, 45s)`，所以一个 800KB 请求最坏要 45s + 45s = 90s 才判失败。

### 换线并没有救回请求

有 transport 且换过线的 **4,463 个请求**里，**71%（3,172 个）之后又 429**。因为换线时 `_slot_pick` 优先挑「当前没被占用」的线，而健康线（40/422 从没 429）本来就被各槽抢着用，超时触发的那次换线往往落到一条更差的线上。

### 机制根因

`classifyRotateReason` 的判据是「429 一律换线；403 只有 abusive traffic 才换」。transport 超时走同一套 `rotateEgress` 路径 —— 于是**「上游 prefill 慢」和「这个 IP 没额度了」被当成同一件事处理，都是换 IP**。而换 IP 不会让上游 prefill 变快。

## 九、深挖：别的请求的 429 为什么会打脏优质线

### 9.0 先更正口径（上一版这一节用了错字段，结论已撤回）

上一版把 `[ASIP] rotate ... ip=` 当成了「失败那一发打中的地址」，**这是错的**：
该字段由 daemon 的 `_slot_current()` **事后**读取，请求发出后线可能已被换走。
全局 30,350 条 rotate 里 `reason_out=already_retired`（迟到账、不换线）占 **45.4%**，这批的 `ip=`
基本都是换过之后的新地址 —— 拿它当失败地址，就会制造「新 IP 首发就 429」「跨很多 /64 全 429」这类假象。

**正确口径**：`[EGRESS] retry N/M 429 -> accounted on <port>` 明确写出「这一发 429 记在哪个端口」，
再用该端口**在那一刻**绑定的 IP。可定位 30,411 / 30,417 条（100%）。

### 9.1 transport 不都伴随 429（此条口径无关，成立）

| 类别 | 请求数 | 占比 |
|---|---|---|
| 有 `[TRANSPORT]` 的请求 | 4,688 | — |
| 其中同时有 ERROR 429 | 3,172 | 67.7% |
| 其中**没有 429** | 1,516 | **32.3%** |

那 1,516 条的结局：**760 条最终 503**（9router sidecar 超时后合成的 fail fast）、755 条无错误行。
体量中位 516KB。20s 首字节预算下，它们不是「等到 429 才超时」，而是上游一直没吐首字节。

### 9.2 单 IP 容量是真的：100–180 发

用正确口径统计 6,713 个出口 IP：**中位只承载 3 发、p90 9 发**，但长尾很硬：

| 出口 IP | 承载 | 429 |
|---|---|---|
| `2a09:bac5:1f02:1246::1d2:2e` | **180** | 18 |
| `2a09:bac5:a5fc:1cd2::2df:e4` | 143 | 2 |
| `2a09:bac5:1f00:1232::1d0:d4` | 121 | 18 |
| `2a09:bac5:1f04:3046::4cf:42` | 111 | 8 |
| `2a09:bac5:5a8:2e32::49a:26` | 107 | **0** |
| `2a09:bac5:9de6:188c::272:106` | 92 | **0** |

和一个能扛 180 发的中位 3 发，差距 60 倍。**这不是 IP 能力问题，是 IP 被换得太早。**

### 9.3 429 落在 IP 生命的哪一段

| 该 IP 已承载 | 429 次数 | 占比 |
|---|---|---|
| 本 IP 首发 | 3,613 | 27.9% |
| 2–3 发 | 4,759 | 36.8% |
| 4–10 发 | 4,144 | 32.0% |
| 11–50 发 | 355 | 2.7% |
| 51–150 发 | 72 | 0.6% |

段侧（该 /64 已承载）：≤3 发 12.5%、4–10 发 20.5%、**11–50 发 48.6%**、51–150 发 17.6%、>150 发 0.7%。

### 9.4 借用重试：别的请求的失败记在健康线头上（此条口径可靠）

`_rotate_slot_once` → `_slot_redirect_payload` → `_pick_healthy_slot()`：一台槽位报障后，
daemon 挑**另一台健康槽的端口**让 9router 重试；重试再失败时，`_slot_current()` 读到的是
**这条健康线的 IP** → 标脏 → 认领修整 → 换走。它自己一次错都没犯。

wd16kwkan（11-12 12:11，body 546KB）：

```
12:11:32 PROXY url=127.0.0.1:7890                      ← 首发，PHX-127
12:11:35 rotate 7890 → to=slot-2 WARP-CF-G ip=...1d0:ba
12:11:39 rotate 7892 line=WARP-CF-G verdict=OK → to=slot-3 LAX-131  ← CF-G 被打脏换走
12:11:48 rotate 7893 line=LAX-131 verdict=OK → to=slot-2 SIN-136    ← LAX-131 同样连坐
12:11:48 ERROR 429 · 16548ms
```

按请求的首发端口拆分 30,350 条 rotate：

| | 首发 | 被借 | 借用占比 |
|---|---|---|---|
| 全线路 | 15,921 | 14,429 | **47.5%** |
| CF 12 条 | 1,959 | 1,194 | **37.9%** |

### 9.5 明确不知道的

1. **同一个 IP 探针一发 200、生产下一发 429** —— 不知道原因。之前给过的「体量差 8–227 倍」「请求级 429」「账号级限流」都是推测，没有一条被验证。
2. **27.9% 的新 IP 首发就 429** —— 不知道。这批不可能是额度耗尽（段和 IP 都是新的），但也没有证据指向具体机制。
3. `reason_out=already_retired` 占 45.4%（13,789 次）—— 这代表大量 429 是迟到账，账算在已换过的地址上。它对「谁该负责」的影响还没算清。

### 9.6 已撤回的说法

| 说法 | 撤回理由 |
|---|---|
| 「换 IP 换不出额度」 | 错。9.2 有 180 发 / 143 发 / 107 发零 429 的实例 |
| 「99.9% 的请求跨 2–6 个不同 /64 全 429」 | 口径错，用的是 rotate 的**事后** `ip=` |
| 「22.8% 的失败发生在全新 /64 的第一发」 | 同上，同一错误口径 |
| 「429 跟请求走，不跟 IP 走」 | 无证据，撤回 |
