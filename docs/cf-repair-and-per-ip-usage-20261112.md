### 坏的三条到底坏在哪

单元定义里 `ExecStart=usque-launch.sh <port> -`，最后这个 `-` 表示**要求走 v4**；
其余六条写的是 `-6`。而本机到 Cloudflare WARP 的 **v4 MASQUE 端点不可用**，于是这三条从头到尾没连上过（16:28–16:41 启动，日志刷了 7 小时 `timeout: no recent network activity`）。

把参数改成 `-6` 后三条立即恢复。改动落在：

```
/etc/systemd/system/usque-warp-d.service   ExecStart=... 1083 -6
/etc/systemd/system/usque-warp-e.service   ExecStart=... 1084 -6
/etc/systemd/system/usque-warp-f.service   ExecStart=... 1085 -6
```

原文件已备份为 `*.service.bak-20261112-*`，已 `daemon-reload`。

### 关于「v4 应该是通的」

v4 本身确实通，我一开始的表述不准，这里给完整验证：

| 验证项 | 结果 |
|---|---|
| 本机 v4 常规上网 | 通，`curl -4 https://www.cloudflare.com` → 200，出口 61.146.77.66 |
| TCP 到 162.159.192.1:443 / 193.1:443 | 通 |
| TCP 到 162.159.198.2:443 | **超时** |
| MASQUE(v4) → 162.159.198.2 | **完全无响应**（timeout） |
| MASQUE(v4) → 198.3 / 198.4 / 198.5 / 198.6 | 有响应，但 TLS **0x128 handshake failure** |
| MASQUE(v4) → 198.2 换端口 500/1701/4500/2408 | **全部超时** |
| MASQUE(v6) → 2606:4700:103::2 | **正常连上** |

为了排除「同一设备并发两条隧道被拒」这个干扰，我**新注册了一个 WARP 设备**（`usque register`）单独测：
v4 依旧 timeout，v6 立刻 `Connected to MASQUE server`。

→ 结论：**通的是整机 v4 上网，不通的是 Cloudflare WARP 的 v4 MASQUE 端点这条路**（198.2 丢包、198.3–6 拒绝握手），跟 usque 配置、设备注册、端口都无关。

顺带说明为什么这不算降级：WARP 无论走 v4 还是 v6 传输，**分到的出口 IP 都是 v6**（`2a09:bac*`），所以改用 v6 传输不改变出口地址池，不损失容量。

## 二、生产里每个出口 IP 平均只用了 3 发

### 统计方法

两路日志按时间对齐，归属成功率 **98.5%**：

- `[PROXY] OPENCODE ... url=http://127.0.0.1:789x` —— 每个请求都记录了走的槽位
- `[ASIP] rotate ... to=slot-N to_line=... to_ip=...` —— 槽位的线路/IP 变更序列

请求按槽位落到当时的 (线路, 出口IP)，再按 IP 聚合。

### 结果

窗口 4 小时，2003 个请求，957 次 (线,IP) 激活：

| 口径 | 数值 |
|---|---|
| 全局 | 1973 请求 / 957 次激活 = **2.06 发/次** |
| **CF 专项** | 307 请求 / 94 次激活 = **3.27 发/IP** |
| 非 CF（H2 为主） | 1666 请求 / 863 次激活 = 1.93 发/IP |
| CF 单 IP 驻留 | 中位 **42 秒**，p90 175 秒，最长 1694 秒 |

单次激活的承载分布：

| 接到请求数 | 占比 |
|---|---|
| 1–4 发 | 844 / 957（88%） |
| 5–19 发 | 100 / 957 |
| 20–49 发 | 13 / 957 |
| **≥50 发** | **0** |

中位 1 发，p90 5 发，最高 49 发。

### 和你说的 150+ 对一下

| | 数值 |
|---|---|
| 实测单 IP 容量 | ≥150（保守；v6 单会话 200 发未触顶，L2 最高记录 358） |
| 生产实际用量 | 3.27 发（CF） |
| **利用率** | **约 2.2%** |
| 缺口 | 约 **46 倍** |

也就是说：**每一条 CF 出口 IP 被扔掉的时候，钱包里还剩 97.8% 的额度。**

### 是谁把它们扔掉的

看换线时旧线的判活结论（2500 次换线）：

| 线族 | verdict=OK 占比 | verdict=quota |
|---|---|---|
| CF | **82.4%**（361/438） | 0 |
| H2 | 77.0%（1546/2008） | 9 |

全部 2500 次换线里，`quota` 触发的只有 **9 次（0.36%）**。

→ **绝大多数换手不是因为 IP 被限流，是 daemon 主动换的。** 这才是 CF「看起来没在用」的真因：不是没分到流量，是分到 42 秒就走了。

> 注意字段语义：rotate 日志里的 `reason=ok` 指的是「这次换线请求被受理」，**不是**「这条线没问题」。判断该不该换要看同一行的 `verdict`。

## 三、按性价比的处理顺序

1. **先掐住 verdict=OK 的换线**：只有 `quota` / `403` / `transport` 才允许换，OK 的线留在原地。这一刀能把 3.27 发往上抬一个量级，其他都是次要的。
2. **探针固定 session**（已改：每天 15 个、随机取 1）—— 不再自己烧 L1 名额。
3. **429 按各自 Retry-After 排期**，别用统一 60s 冷却对滚动窗口。
4. 冷却要真正落到 sing-box selector，现在 `_mark_egress_cooling` 只写内存 dict，全文件没有一处操作 selector。
