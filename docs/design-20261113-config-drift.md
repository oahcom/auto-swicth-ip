## 0. 审查框架（沿用上一份的三方 × 六维，框架不变）

**三方** = 需求方（主人要的到底是什么）/ 运维（线上会不会被搞坏）/ 复核者（代码与注释、文档是否自洽）。
**六维** = 正确性 / 一致性 / 边界与异常 / 性能与成本 / 可测性 / **兼容与演进**。

> 第六维的定义沿用上一份（落盘格式演进、老数据迁移、新旧并存、回滚），不因话题换就换维度——审查框架要稳定才能跨议题对比。
> 本方案的核心主张是「可自愈」，它不单列维度，而是压在 D1 正确性（闭环是否成立）与 D2 一致性（告警口径是否精确）里审。
> 如果你更想把第六维换成「可观测与可自愈」，矩阵可以整体重映射，见 §8 未决问题 Q4。

**术语表**（本话题新增；其余见 `docs/design-20261113-ledger-lifecycle.md` §0.3）：

| 术语 | 含义 | 本项目具体所指 |
|---|---|---|
| **面（plane）** | 同一份配置事实的一份副本所在处 | 见 §2.1 的六面表 |
| **生效面** | 进程内真正加载的那份配置 | sing-box 进程里的 selector 成员集，经 Clash API `all` 读出 |
| **产物面** | 磁盘上渲染出来的配置文件 | `.warp/h2/singbox.json`、各 `lineN/singbox.json`、槽位配置 |
| **声明面** | 人类维护的意图清单 | `config.CFG["warp"]["members"]`（由 `.warp/h2/channels.json` 派生） |
| **热重载** | 不杀进程、只让进程重读配置 | `PUT /configs?force=true` |
| **投影** | 磁盘配置在进程内的呈现 | 「产物面 → 生效面」的关系，像投影一样可能丢失信息 |
| **闭环** | 写盘 → 重载 → **验证** → 未生效则升级，四步串成一件事 | 本方案的 L2 |
| **告警精度** | 只报需要人处理的不一致 | 项目既有哲学：「告警的精度决定它有没有人看」（`_config_consistency_check_impl` 注释） |
| **熔断计数** | 限制自动修复频率的计数器 | 必须落盘，否则重启即清零（INC-019 教训） |

## 1. 需求方视角：这次到底要解决什么

### 1.1 一句话

**配置事实有六个「面」，其中五个在磁盘上被对账，第六个面——进程内真正生效的配置——从未被对账。于是「写盘成功 + 自检通过」不等于「配置已生效」，漂移一再复发。**

### 1.2 两次复发的时间线（真实证据，非推断）

| 时间 | 事件 | 现象 | 处理 | 处理为什么不够 |
|---|---|---|---|---|
| **2026-11-09** INC-017 | sing-box 主进程跨多次 asip 重启存活（`KillMode=process`），订阅刷新的热重载回 204，但 Clash selector `all` 仍 170 | 本地渠锁虚高、dead 虚高，与 VPS 对不上 | 手工 kill 旧进程 + 清 48 条 SCAN 残留线 | 只修了这一次的现场，没修「204 ≠ 已生效」这个判据 |
| **2026-11-13 13:39** | 磁盘配置更新后槽位进程未重载，配置里的新线不在 selector `all` 里，PUT 得到 400 `Selector update error: not found` | **六槽连报 no_candidate**，台账里 10 条新鲜 OK 一条也塞不进 | 补闸跳过 + 5 分钟节流告警（commit `7529886`） | 跳过+告警只让漂移「不再撞死」，漂移本身还在，下一轮还会撞 |
| 同类问题文档面已复发两次 | FR-12 / R-9：`CLAUDE.md` 里的 `rate429_guard_sec`、`proactive_mode` 与运行值不一致 | 报告读数与真实行为不符 | 人工核对 | FR-12 自己写着「无测试，靠人工核对」——复发是设计使然 |

### 1.3 为什么治标必然复发（三层根因）

**技术根因：「生效」这一步没有验证回路。**
`reload_singbox_config` 只以 HTTP 状态码 200/204 判成功。而 INC-017 的实测结论是：**热重载回 204 不等于 selector 已更新**，旧进程存活时热重载是假成功，必须 kill + 重拉才能真对账。该函数的 docstring 还写着「50ms 粒度探测 7890 全程 0 次失败」——但那次探测测的是**端口可达**，不是**配置内容**。一个只看返回码、不看结果的重载，等于没有验证。

**机制根因：漂移只在业务路径上被撞见，没有独立巡检；发现后只跳过、不修复。**
今天的补闸是在 `_refill_slots_from_probe` 塞候选时才发现「这条线不在运行时成员里」。这意味着：漂移发生后，它会一直存在，直到有人尝试换线才暴露，然后被跳过、打一条 5 分钟节流的告警。告警不会让漂移消失，只会让下一轮再撞一次。

**结构根因：写盘与生效是两条路，靠「changed 列表」传参衔接，传漏即漂。**
渲染脚本（`deploy/render_h2_lines.py`）写 `singbox.json`，重载（`_reload_config_set`）只对 `changed` 列表里的配置文件生效；补丁脚本（`deploy/patch-wg-outbounds.py`）写主配置后自己决定要不要重载。任何一处漏传、漏调，配置就停在磁盘上。而**自检只对账磁盘上的五个面**（`_config_consistency_check_impl` 明确列出 5 个真相源），进程内生效面是盲区。

### 1.4 非目标（本次明确不动）

1. 不改成员清单的来源体系：H2 成员唯一事实源是 `.warp/h2/channels.json`、块成员唯一事实源是 `.warp/block-map.json`、WG 开关单一化（`config.py` 里「两处各存一份必然会漂移」的既有原则保持）。
2. 不改探测三道闸门、换线、惩罚期、选线档位的任何语义。
3. 不做配置体系的全量重构（例如 schema 驱动配置）。本方案只补「生效验证 + 对账 + 自愈」这一层。

### 1.5 成功判据（可度量）

| # | 判据 | 度量方式 | 目标 |
|---|---|---|---|
| S1 | 漂移不依赖业务路径才被发现 | 独立巡检周期内自动发现 | 漂移存活时间 ≤ 1 个巡检周期 |
| S2 | 发现后可自动收敛 | 热重载 → 验证 → 未生效则重启 → 再验证 | 无人工介入下收敛；失败有明确告警 |
| S3 | 「写盘 + 自检通过」不再等于「已生效」 | 生效必须带验证证据 | 三态返回（已验证 / 仅重载 / 未收敛） |
| S4 | 文档面配置值不再靠人工核对 | `asip audit --doc-drift` 进部署前关卡 | 文档漂移检出率 100% |
| S5 | 自动修复可一键关闭且不被重启绕过 | 开关 + 熔断计数落盘 | 回滚演练通过 |

## 3. 解决计划（分层，从治本到兜底）

### L1 单一事实源与派生（已有原则，补漏）

项目已经确立并多次执行的原则：**两处各存一份必然漂移**（`config.py` 关于块成员、`warp_wg.py` 关于节点清单、`warp_blocks.py` 关于 nodes[] 都有对应注释）。本次只补漏：

- **文档面**改为「生成或校验」，不再靠人工抄写与人工核对（见 L5）。
- 所有「写盘」路径必须走同一个原语，不允许各脚本自己 `write_text` 后各自决定要不要重载（见 L2）。

### L2 生效闭环（本方案的治本动作）

把「配置生效」从一次调用升级成**四步串成一件事**：

> 写盘 → 热重载 → **验证运行时投影** → 未生效则升级为整进程重启 → 再验证 → 仍未收敛才告警

关键点：

1. **验证是必选项，不是可选项**。判定「生效」的证据是**运行时成员集 == 产物面期望集**，不是 HTTP 204。
2. **升级路径沿用 INC-017 的教训**：热重载无效（旧进程存活）时 kill + 重拉，而不是相信 204。
3. **三态返回**：`verified`（已验证生效）/ `restarted`（重启后生效）/ `unresolved`（仍未收敛）。调用方据三态决定是否告警，不再用布尔值把「重载了」和「生效了」混为一谈。

### L3 六面对账巡检（扩展现有自检）

在 `_config_consistency_check_impl` 的 6 个分类之外新增**分类七：生效面与产物面不一致**（磁盘产物里有、进程 `all` 里没有的成员）。同时：

- 巡检独立于业务路径，按固定周期跑（不等换线才撞见）；
- 发现漂移可**自动触发 L2 闭环**（限频、可开关），而不是只打日志；
- 沿用项目的「告警精度」哲学：只报需要人处理的不一致，自动修复成功的不再报，**修复失败才升级告警**。

### L4 分级告警与可观测

| 情形 | 动作 | 频率 |
|---|---|---|
| 漂移被发现且自动修复成功 | 记 `_CONFIG_DRIFT_STATS`，不告警 | — |
| 漂移被发现、热重载无效、重启后生效 | 一条信息日志（含升级原因） | 每事件一条 |
| 漂移修复失败（重启后仍不一致） | 告警，指明需人工介入 | 5 分钟节流（沿用现有阈值） |
| 自动修复触发整进程重启 | 必须记熔断计数，且**计数落盘** | 每小时上限（见 R-1） |

### L5 文档同源（文档面复发两次的解法）

`tools/asip_audit.py` 新增 `--doc-drift`：从 `config.CFG` 抽取关键配置值（`rate429_guard_sec`、`proactive_mode`、`blocked_guard_sec`、`api.production_429_ban_sec` 等），与 `CLAUDE.md` 里的对应表格逐项比对；不一致退出 1。挂到部署前关卡（`deploy/acceptance_h2_reconcile.py` 已有部署前关卡的先例）。

**为什么能解决**：FR-12 当初就写着「无测试，靠人工核对」，R-9 结论是「文档漂移再次发生……接受」。人工核对的复发率是 100%，只有把核对变成可执行判据才不会复发。

### L6 状态面残留自动剪除（INC-017 的另一半根因）

INC-017 的第一个根因是 `.warp_line_state.json` 里 48 条 `WARP-H2-SCAN-*` 残留线虚增渠锁、挡探测。`_config_consistency_check_impl` 已经把它分类为 `retired`（台账外单元残骸）并认定「是渲染器只增不减的直接证据，是下一次缩容会原样重演的根因」。本次把 `deploy/reconcile_h2_units.py` 的「台账外单元剪除」挂到巡检，限频自动执行。

## 4. 代码修改方案（函数级；不贴代码，只讲改什么与为何能解决）

| # | 改动点 | 改什么 | 为何能解决问题 | 风险 |
|---|---|---|---|---|
| **A** | 新增 `_verify_runtime_projection(slot 或 path, expected_tags)` | 读运行时 selector 成员集（复用 `_slot_selector_members` 的取数方式），与产物面期望集（复用 `_singbox_outbound_tags` 的解析）比对，返回（是否一致、缺失集、多余集） | 这是**第六面的读能力**，也是 D-1 要求的单一事实源：闭环、巡检、审计三处共用同一个比对判据，不再各写一份 | 读不到 API 时必须返回「未知」而不是「一致」，否则假阴性 |
| **B** | `reload_singbox_config` → `_apply_config_change(...)` | 四步闭环：热重载 → 验证 → 未生效则 `restart_singbox` → 再验证；返回三态。**同步修正 docstring**：删掉「204 = 完成」的误导，改为引用 INC-017 的实测结论 | 直接堵住技术根因：「生效」从此有验证证据，204 不再被当成成功 | 重启会带来 ≈13s 出口空窗（见 R-4），故升级必须限频 |
| **C** | `_config_consistency_check_impl` 新增分类七 | 产物面 ⊄ 生效面的成员单独归类；可选自动触发 B | 漂移从「业务路径撞见」变成「巡检主动发现」；沿用 6 分类的精度哲学，不制造新噪声 | 自检是纯观测，加自动修复要显式开关（见 R-5） |
| **D** | `_refill_slots_from_probe` 升级 | 跳过缺失成员后，**限频触发 B** 并在本轮重试；告警语义从「发现了漂移」改为「修复失败」 | 补闸从「绕过问题」变成「顺手修问题」，漂移不会活到下一轮 | 限频必须落盘熔断（R-1） |
| **E** | `tools/asip_audit.py` 新增 `read_runtime_members()` 与 `--doc-drift` | 把第六面的读能力放进判据唯一来源；文档值比对进部署前关卡 | 与 `DESIGN-2026-11-11.md` 的「唯一判据来源」原则一致：巡检与审计共用判据，避免第二份解释 | 审计脚本只读，不改配置，保持纯度 |
| **F** | 状态残留剪除挂巡检 | `retired`（台账外单元残骸）限频调用 `reconcile_h2_units` 的剪除 | 堵住 INC-017 的第一个根因，防止缩容原样重演 | 剪除要限频 + 可回滚（状态表先备份） |
| **G** | 测试清单 | 见 §4.1 | 让每个改动点有回归 | — |

### 4.1 测试清单（每条都必须能在改动前后转红/转绿）

| # | 用例 | 断言要点 |
|---|---|---|
| T1 | 假 204 场景 | mock 热重载返回 204 但运行时成员不变 → 必须走整进程重启路径，且最终三态为 `restarted` |
| T2 | 验证闭环三态 | 重载即生效 → `verified`；重载无效重启后生效 → `restarted`；重启后仍不一致 → `unresolved` 且告警 |
| T3 | 巡检主动发现 | 不走换线路径，构造产物面有、生效面无的成员 → 巡检周期内报分类七 |
| T4 | 自动修复限频熔断 | 连续 N 次触发修复 → 第 N+1 次被熔断；**重启进程后熔断计数仍在**（INC-019 教训） |
| T5 | 读不到 API 不假阴性 | `_verify_runtime_projection` 在 API 不可达时返回「未知」，不判「一致」 |

## 6. 风险登记册

| # | 风险 | 触发条件 | 影响 | 缓解 | 观测 |
|---|---|---|---|---|---|
| R-1 | **重启风暴**：自动修复频繁升级成整进程重启 | 漂移持续存在或验证判据写错 | 出口反复 13s 空窗，比漂移本身更伤 | 熔断计数**落盘**（INC-019 教训）+ 每小时上限 + 必须记原因 | `_CONFIG_DRIFT_STATS`、restart 计数 |

| R-3 | **观测掀翻服务** | 巡检内部异常（已有先例） | 守护进程崩溃循环 | 复用 `_config_consistency_check` 的异常隔离壳 | `selfcheck_failed` 标记 |
| R-4 | **出口空窗**：kill + 重拉 ≈13s | 验证失败被升级 | 期间 9router 每个请求 ECONNREFUSED → 503 | 仅验证失败才升级；限频；优先热重载 | 升级次数、503 计数 |
| R-5 | **自动修复与人工操作打架** | 运维手工改配置时巡检在跑 | 反复覆盖 | 开关默认关（先报告后修复）；巡检读到人工操作日志时退避 | 开关状态、修复次数 |
| R-6 | **假阴性**：API 不可达被当成「一致」 | 网络抖动、端口未起 | 漂移静默存在 | 「未知 ≠ 一致」（T5），未知只记不判 | 未知计数 |
