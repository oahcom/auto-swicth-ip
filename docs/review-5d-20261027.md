## TL;DR

20 条 WARP 线全部停探 13.3 小时，探测器静默 56.6 分钟，74 次换线 0 成功，
网关侧三个活跃代理池算出同一个 egress id 导致备用出口恒为空。

**根因是两个同构缺陷**：一次"换个出口重试"的自愈机制，被它自己的健康判定排空了候选集 ——
出口侧是调度队列（`next_probe_ts` 在未来），网关侧是候选集（egress id 碰撞）。

审查结论：Bug 单可执行，但有 **2 条阻断性红线**（其一已修）和 **1 个必须先定案的架构耦合**
（B9 修完仍会"换线换到同一物理出口"）。出口侧修完可消除 91.2% 的 503 主体。

## 1. 问题与动机

### 1.1 现场事实（全部可复现，命令见 §9.4）

15:28:08 9router 启动 → 18:40 观测窗口内：

| 指标 | 实测值 |
|---|---|
| `ERROR 503` 总数 | 3858 |
| 其中 `"timeout":true`（族 A） | 3519（91.2%） |
| 其中 `ECONNREFUSED`（族 B） | 270（7.0%） |
| 换线触发 `↻ WARP 换线` | 74 |
| 换线成功 `✓ WARP 换线成功` | 0 |
| 换线放弃 `⚠ 无新鲜备线不切` | 73 |
| 20 条线中 `last_ok_ts = 0` | 20 |
| 20 条线中 `next_probe_ts` 在次日 08:00 | 18（另 2 条在当日 23:29 / 23:31） |
| 持续停探时长 | 56.6 分钟且仍在持续 |

**503 的两种形态，判别指纹相差两个数量级**：

- 族 A — sing-box 进程活着，内部 WARP 隧道静默死亡。连接建立但永无首字节，
  `UPSTREAM_TIMEOUT_MS=19000` 到点 abort，合成 503（最短 19287ms）。
- 族 B — sing-box 进程本身未监听 7890。内核立刻回 RST（实测 46–92ms）。
  17:48:23–17:48:53 的重启窗口内 39 次 ECONNREFUSED 直接产生 20 次 503。

### 1.2 动机不是"503 太多"

503 本身是出口不可用的**症状**，上游 WARP 隧道会死是既定事实，修不掉。
要修的是**系统失去自愈能力**这件事：出口死了应该换一条，而现在换不动，也探不了。

74 次换线全部落在同一条日志上：

```
· 暂无 120s 内 OK 的备线，等待探测器写入
⚠ 等待超时仍无新鲜备线，本次不切（不重启、不落池）
```

`_warp_line_fresh_candidates` 返回空 → 换线在"等备线"阶段就 `return False`，
**根本没进入重启分支**。于是「没有新鲜线 → 不切 → 不重启 → 没有新 IP → 还是没有新鲜线」
形成闭环。`restart_count` 的分布（CF-E 281 / CF-16 267 / CF-15 243）说明重启这条路
历史上是有效的，只是现在被 wait_fresh 挡在前面。

### 1.3 用户指令（设计前提）

> **探测逻辑不应该被任何东西限制，即使没有任何东西可以探测，即使探测的结果全都是不好的。**

这条对应一个可检验的设计原则：**探测是观测，不是决策。观测不应因观测结果而停止。**

当前实现违反了它 —— 探测结论（`quota`）被写回成探测排程（`next_probe_ts`），
于是"结果不好"直接变成了"不再观测"。

**M4 量的是「我们多久看一眼这条线」，不是「上游多久解禁这个 IP」。** 两者必须分清：

| 字段 | 回答什么 | 谁定的 | 本 PRD 是否改动 |
|---|---|---|---|
| `ban_until` | 这个 IP 什么时候能重新服务 | 上游（实测 417/417 条落在次日 08:00） | **不改，也改不了**。这是物理事实 |

现状的缺陷是**把对 IP 的惩罚记到了线头上**：IP 13.3h 不能用 ≠ 这条线 13.3h 不许观测。
60 秒后复检看到的是「这条线现在是不是换了地址」，不是「这个 IP 是不是解禁了」。

**60s 复检不会白烧配额**，因为 `_probe_one_line` 的顺序是先查地址、再决定要不要花配额：

```
3019  ip = warp_egress_ip(port)          ← 查这条线当前地址（不烧 opencode 配额）
3027  if _warp_ip_is_blocked(ip, now):   ← 地址仍在惩罚期
3032      _warp_line_restart(...)        ← 直接重启换会话地址，return
3042  ok = _warp_model_usable(...)       ← 只有地址干净才走到这里，才烧一格

实测（模拟惩罚期内的 IP 调 `_warp_model_usable`）：`probe_warp.probe` 被调用 **0 次**，
日志输出「台账已判脏，跳过实测」。**烧配额的只有全新地址，而那是唯一能知道它能不能用的方式。**
| M5 | 三个同 url 活跃池的 egress id 去重数 | 1 | **3**，且两两不互为备选 | 新用例 `same_url_different_pools_must_not_collide` |

6. 修 B2（改 record_observation）→ M1
7. 修 B4（改 note_ok）          → M1
8. 修 B5（缩短 TTL）            → M6
9. 修 B6（催探测 + 缩短等待）   → M2 / M3

```

**第 3、4 步必须同批落地**：FR-13 单独上线 = 60s 节奏叠加「blocked 即重启」
（`_probe_one_line:3027-3033` + 重启成功后 `next_restart_ts = 0`）→ 每线每小时最多
60 次重启。而 `restart_max_per_hour_per_line` 这个上限**只写在 `CLAUDE.md:664`，
daemon.py 中 0 处引用、config.py 里也没有这个键** —— 它从未被实现。
当前实测已经是 **76 次/h/线**（M9），装上节拍器后只会更确定地打满。

**先修 B12 的理由**：它是拆门禁的连带产物（§0.3）。当前 `_warp_line_needs_probe` 对
一条刚被判 quota 的线，600 秒内返回 **600 次 True**（实测），节奏完全由
`probe_max_per_min=600` 兜底 —— 而 20 条线 × `probe_concurrency=32` 摸不到那个上限。
修它只需一个函数加两处调用，却同时堵住「13.3h 停摆」与「无节奏开环」两个极端。

**B3 紧随其后**：纯配置值，`probe_persistent_retry_sec` 21600 → 60。它与 B12 是同一个
上限的两端 —— B12 管「读取侧看多频繁」，B3 管「写入侧写多远」，缺一条都留着 6h 停摆。

**B1 放最后**：它需要新增调度逻辑，改动面最大，且必须区分两种 unknown。
前面几条修好后停探不再是 13.3h，B1 的冻结窗口自然变短，改动风险随之降低。

**FR-14 是 FR-13 的必要配套，不是额外要求。** 事实：

```
$ grep -rn 'restart_max_per_hour_per_line' --include='*.py' .
（无输出 —— daemon.py 中 0 处引用）

$ grep -n 'restart_max_per_hour_per_line' CLAUDE.md
664:warp.restart_max_per_hour_per_line: 20         # 每线每小时重启上限
```

**这个上限只存在于文档里，从未实现。** `config.py` 里也没有这个键，
运行时 `[k for k in CFG['warp'] if 'restart' in k]` 只返回 4 个键，没有一个管速率。

**实测已经超标，不必等 FR-13 生效**（`journalctl -u auto-switch-ip --since '3 hours ago'`，
窗口 `19:59:31` → `21:39:44` = 1.67h，样本 1836 条）：

| tag | 重启次数 | 折算 /h | 文档宣称上限 20/h |
|---|---|---|---|
| WARP-CF-F | 127 | **76** | 超 3.8× |
| WARP-CF-11 | 112 | **67** | 超 3.4× |
| WARP-CF-16 | 112 | **67** | 超 3.4× |
| WARP-CF-H | 109 | **65** | 超 3.3× |

全池合计 **1099 次/小时**。76 已经大于 60，说明连「60s 一次」的节奏都没有 ——
当前唯一的时间闸是 `restart_cooldown_sec=5`，而重启**成功**时 `next_restart_ts = 0.0`
（`:2952`）把它清零。理论天花板是 720 次/h/线，实测 76 只是被探测往返耗时拖住。

为什么 FR-13 落地后它变成 P0：`_probe_one_line` 对仍在惩罚期的地址走
`_warp_line_restart`（`:3027-3033`），而重启**成功后** `next_restart_ts = 0.0`（`:2952`，
不设退避）。于是 60s 节奏 = 每条线每小时最多 60 次重启、20 条线合计 1200 次/小时。
`restart_backoff_sec` 只在**失败**时生效，成功路径没有节流。
`restart_count`（`:2950` 写、`:2532` 初始化）**没有任何读取点** —— 差一个
`if restart_count >= N` 就是完整实现。

**两条必须同批落地**：只做 FR-13 = 把现在的随机风暴改成 60s 节拍器（更规则、也更确定地打满）；
只做 FR-14 = 停摆仍在（因为没人探测就没有结论触发重启）。

**FR-14 与 C-3 不冲突**：上限压的是**重启**（一个决策 + 一个有副作用的动作），不是**探测**（观测）。
达到上限后探测器照常按 60s 节奏看这条线，只是不再因它触发重启 —— 观测仍然不受结论限制。

**FR-13 与 FR-1/FR-2 的区别**：FR-1 说「不读 `ban_until`」，FR-2 说「6h 地板不进计算路径」，
两条都是**移除**；FR-13 是**补上**——移除之后探测侧没有任何节奏，非 OK 的线每轮都被调度。
三条同时成立才算修好：拆掉结论驱动的闸，同时装回一个与结论无关的闸。

**FR-13 的最小实现**（`cadence` 取 60s 常量时，600s 内恰好 9 次，满足 M8 的 ≤10）：

```python
# 读取侧：只由「上次探测」推出下次时刻
due = float(st.get("last_probe_ts") or 0.0) + _line_probe_cadence(st)
if now < due:
    return False, due
return True, due
```

注意**不要**写成 `due = min(next_probe_ts, last_probe_ts + 60)`：`min` 会在
`next_probe_ts == 0`（刚被 `note_ok` / `invalidate` 置零）时坍缩成 0，等于又完全放行。
`next_probe_ts` 继续保留为写入侧的**记录**字段（`_warp_line_wait_fresh` 与
`_warp_prober_loop` 的 idle 唤醒仍读它），但不再参与 `needs_probe` 判定。

**FR-12 为什么没有测试**：它改的是文档，不是行为。给它写用例只能锁住"文档里是某个字符串"，
而真正的判据是文档值等于 `config.CFG` 的运行值 —— 那是一次性核对，不是回归。
风险已登记为 R-9。

### 5.4 B9 改法必须连带解决「换线换到同一物理出口」

这是审查发现的**新问题**，不解决则 B9 修了等于白修。

先钉一个关键事实（与 `503-root-cause-20261027.md` §4.2 的说法不同）：

```js
// egress.js:238
if (egress.kind === "proxy") return null;   // ← proxy 从不进冷却表
```

所以改 id **不会「破坏」冷却一致性** —— proxy 本来就没冷却。但带来另一个后果：

```
修前：三池同一 id → 候选恒空 → 不换线（当前故障）
修后：三池不同 id → 能换线，但三个池的 proxyUrl 都是 127.0.0.1:7890
     → 换到池 B 还是同一个 sing-box 出口
     → 立即再 429 → 切池 C → 仍是同一个出口
     → 三个池轮一遍，出口 IP 完全没变
```

`markEgressCooling` 又对 proxy 全部 no-op，连「这个出口刚 429 过」都不记。

三个候选方案见 ADR-2。推荐 **A**：它把「候选去重」和「出口冷却」两件事分开 ——
去重看物理出口（`proxyUrl`），冷却（若有）看逻辑池，且不碰 `markEgressCooling` 里那段有 WHY 的注释。

## 8. 决策记录（ADR）

### ADR-1：探测节奏与探测结论解耦（采用固定节奏 + cap 60s）

**背景**：`wait = max(21600, ban_until - now)` 把 IP 惩罚期写进了探测排程。

**选项**：
1. 按结论分类退避（quota→6h、blocked→6h、其它指数）
2. 固定节奏（cap 60s），结论不参与
3. 完全无节奏（每次循环都探）

**决定**：**2**。

**理由**：选项 1 正是当前实现，它把"结果不好"变成"不再观测"，违反 C-3。
选项 3 会把 `probe_max_per_min` 打满、`fail_streak` 失去意义。
选项 2 保留退避的防风暴作用（`_line_probe_cadence` 仍按 `fail_streak` 指数），只是把上限硬钳 60s。

**代价**：不再"聪明地省配额"。接受 —— 可预测的消耗优于不可预测的停摆。

### ADR-2：B9 采用方案 A（`selectAlternateProxy` 按 `proxyUrl` 去重）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（采用）** | `selectAlternateProxy` 去重按 `proxyUrl` 而非 `egress.id` | 最小；语义上"不同池同 url"仍算同一出口，与物理事实一致 |
| B | `identifyFixedEgress` 的 id 纳入 `proxyPoolId` | 改变所有既有 egress 缓存键（R-8）；且仍需额外防同 url 互选 |
| C | 不做 B9，让用户改配置 | 与 N5 一致但对现有部署无效；用户已表态「配多少个池是用户的态度」 |

**决定**：**A**。

**理由**：把「候选去重」和「出口冷却」分开 —— 去重看物理出口，冷却（若有）看逻辑池。
不需要碰 `markEgressCooling` 的注释（N1）。

**注意 FR-9 与 FR-10 同时成立才算修好**：前者要求 id 能区分（用于标识/记账），
后者要求同 url 不互为备选（用于选线）。只做 FR-9 会退化成"能换线但换了个寂寞"。

### ADR-3：B1 采用「unknown_streak + 端口」双判据，不改 unknown 语义

**背景**：R-2 锁死「单次 unknown 不重启」。

**选项**：
1. 直接让 unknown 触发重启（推翻既有用例）
2. 只按 `_port_open` 判
3. `unknown_streak >= 3 and (not _port_open or streak >= 10)`

**决定**：**3**。

**理由**：选项 1 推翻一条有正当 WHY 的用例（unknown 也可能是探测瞬时超时，重启一个健康的线是白烧会话）。
选项 2 在 usque 进程半死时永远不成立（进程在监听，端口开，上游已死）—— 这正是本次现场。
选项 3 的 `or streak >= 10` 是给选项 2 兜底。

### ADR-4：撤回「删除闸 3 台账判脏」

**原方案**（`prober-gate-design-20261027.md` 初版 P0）：删掉 `_warp_ip_is_blocked` 在
`_probe_one_line` 与 `_warp_model_usable` 入口的判脏跳过。

**撤回依据**：三条既有用例锁定了它，且**它们是对的**。判脏后的动作不是"限制探测"，而是：

```python
_warp_line_record_observation(tag, ip, "blocked", ...)   # 记结论
_warp_line_restart(member, "出口处于惩罚期")              # ← 重启换址
```

重启后拿到新 IP，下次探测照常。**链条本身是通的。** 真正断的是 B1：
重启要从 `_probe_one_line` 里发起，而停探让 `_probe_one_line` 根本不执行。

**这是我上一轮分析的主要错误：把"预期行为"当成了"待移除的闸门"。**

### ADR-5：B10 / B11 记录不改

**B10**：`lastResetAt` 是全局的，但 sidecar 也是全局的（A-3）。「按出口分键」无处可落。
现状是「放大器 + 已有正确兜底」（`_verify_transport_failure` 先探出口，探通就不换线），
改动收益低于风险。

**B11**：非 strict 池静默降级直连会产生假 429。但降级的两个池**正是因为 B9 才成为候选**，
修好 B9 后攻击面自然消失（R-7 是它的复核触发条件）。

### ADR-6：拆门禁之后必须补一个**与结论无关**的固定节奏（FR-13）

**背景**：2026-10-27 11:59 UTC 另一个并行 session 把 `_warp_line_needs_probe`
的三行时间门禁整段注释掉了。现场实测（`python3 -c`，见 §0.2）：

```
一条刚被判 quota、写侧 next_probe_ts 推到 +47880s 的线
  600s 内被判定可探次数 = 600        ← 每一次循环都放行
  probe_max_per_min     = 600        ← 唯一还在起作用的限流
  probe_concurrency     = 32
```

即：**停摆问题变成了开环消耗问题**。两个极端都违反 C-3（观测不因结论而变）。

**这条改动本身不算错，但不能停在这里。** 用户的要求是「探测逻辑不应该被任何东西限制，
即使没有任何东西可以探测，即使探测的结果全都是不好的」—— 限制的对象是**结论**
（`last_verdict` / `ban_until`），不是**节奏**。

**选项**：

| 方案 | 做法 | 结论 |
|---|---|---|
| A | 把三行门禁原样装回去 | **否** —— 装回去就等于把 `ban_until` 重新接进排程，B2 复活 |
| B | 完全无节奏，每轮都探，靠 `probe_max_per_min` 兜底 | **否** —— 那个 600/min 是为「全局」设的，20 条线摸不到；单线消耗不可预测 |
| **C（采用）** | `due = last_probe_ts + cadence`，`cadence` 是与结论无关的常量（默认 60s）；**入参没有 `verdict`、没有 `ban_until`、没有 `next_probe_ts`** | 采用 |

**决定**：**C**。

**为什么是常量而不是 `min(base * 2^(streak-1), cap)`**：实测 `probe_transient_retry_sec = 120`，
`base * 2^0 = 120` 已经大于 `cap = 60` —— 这个"指数退避"在任何 `streak` 上都直接封顶，
七个档位全是 60.0s（实测）。写成一个看起来会退避、实际不退避的公式，只会误导后来者。
常量更诚实：**观测频率不随失败次数变化**，这也正是 C-3 的字面意思。

**理由**：`due` 只由 `last_probe_ts` 推出，读取侧结构上就拿不到结论，想把 `ban_until`
接回排程必须重写这个函数 —— 比"改一行赋值"显眼得多。这正是 ADR-1 想要而当时没做到的：
ADR-1 说「固定节奏」，但它把节奏写进了 `_warp_line_record_observation` 的写入侧，
而读取侧的 `next_probe_ts` 仍是一个纯被写字段，谁都能把它推到 13.3h。

**`next_probe_ts` 保留，但降级为记录字段**：它仍被 15 处写入、仍被 `_warp_line_wait_fresh`
与 `_warp_prober_loop` 的 idle 唤醒（`daemon.py:3101-3105`）读取，所以不能删。但它不再
决定「探不探」，只决定「空闲线程睡多久」。这条是本 ADR 最容易被后来者弄反的地方。

**代价与接受理由**：
- 单线最坏 60s 一次、20 条线合计 ≈ 20 次/分钟模型层探测（模拟 600s 窗口：9 次/线）。
  每次烧一格配额。这个量级低于 `probe_max_per_min=600` 两个数量级，且是**可预测**的。
- 放弃了"失败越多探得越稀"这个直觉。接受的依据：本次事故里 20 条线全部失败，
  退避正是让它们一起停摆 13.3 小时的机制之一。失败是一个需要**更多**观测而不是更少的状态。

**验收如何防止回退**：`test_cadence_is_verdict_independent` 对五种结论
（`quota/blocked/flagged/err/unreachable`）各测一次首次重探时刻，断言五者**完全相同**。
任何人日后把 verdict 接回节奏，这条立刻转红。

**与 ADR-1 的关系**：ADR-1 未被推翻，它是本条的前提；ADR-6 补的是 ADR-1 遗漏的
读取侧。两份决策合并后的完整表述是：**节奏由读取侧强制，写入侧的值只作记录。**
