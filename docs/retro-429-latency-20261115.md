## 二、成因解析

### 2.1 429：双形态收敛为单形态

| 形态 | 机制 | 当前状态 |
|---|---|---|
| **leak**（原主形态） | replay 续试只看 freshUrl/freshEgress，不校验 rotate 的 `switched=true`；`already_retired` 空切换后仍继续重放 → 撞退役出口 → 429 无 budget mark → 漏给客户端 | **已封死**：b72078e6 ① 补 `egressStillCurrent` veto 后，哨兵 23:00 / 01:01 / 03:02 三窗 leak=0 |
| **budget**（现唯一形态） | 25s `ROTATE_ATTEMPT_BUDGET_MS` 在 stall→rotate→再stall 循环中耗尽 → give-up 打出 429（带 budget mark） | 近三窗 429 全部是它（5 / 2 / 3 个），journal `rotate budget spent` 44 次 |

### 2.2 budget 为什么会变成唯一形态（放大链）

```
换线环封顶 3→6（60ed7ad7，为了覆盖六个常规闸口）
        ↓ 但 25s 预算没有同步放宽
单次请求换线链更长 → 更频繁撞 25s 预算
        ↓
每次 stall 检测 20~44s + 重试 header 预算 ≥45s（按 body 缩放）
        ↓ 单条链本身就要几十秒
budgetOverrun 的"最后一发"机制在跑（30 次触发）→ 救不回
        ↓
本该接盘的第七闸口兜底 = 死代码（见 2.4）→ 无人兜底
        ↓
429 以 budget 形态打出
```

### 2.3 高延迟正反馈环

```
header 停滞检测 20~44s（无降级，只能换线）
  → 换线重试（≥45s header budget）
  → socket 失败 → invalidateEgressConnections → clearProxyDispatchers 整 URL 池清
  → 在途请求陪葬（连坐）→ 内部产生更多 stall
  → 54 次/30min rotate → 互相抢线（already_retired 569 条 = A 换掉的线 B 正在用）
  → TTFT 10~60s，最长 97s
```

三个环节互相喂养：停滞检测太长（等待窗口大）、重试预算太大（单链耗时长）、整池连坐清（放大器）。

### 2.4 第七闸口死代码（本次复查抓到的实现缺陷）

b72078e6 ③ 的兜底条件：

```js
if (upstreamStatus === 429 && attemptResult === null ...) {
    // 第七闸口 fallback
}
// 注释本意：attemptResult === null = 换线环一发都没打出去
```

**问题**：give-up 路径必然至少打过一发（最后一发拿到 429 才会 give-up）→ `attemptResult` 永不为 `null` → 条件永假 → **0 次触发**。

作者把"一发都没打出去"（首发被同址/同端口拒绝）与"打了但全失败后 give-up"混在了一个条件里。前者本就罕见，后者才是 budget 耗尽的常态——恰好漏掉。这与 budgetOverrun"触发了但救不回"不同：**这是从没上场的死路径**。

### 3.2 针对"大概率是之前改动搞出来的 bug"的直接回答

用户的怀疑成立，具体是两处：

1. **b72078e6 ③ 是我 11-14 21:56 亲手写的实现缺陷**——兜底条件永假，本该在 budget 耗尽时接盘的第七闸口从没上场。这是本次 429 仍在出现的直接原因之一（防漏出的兜底失效）。
2. **60ed7ad7 的 3→6 封顶是副作用源**——意图正确（覆盖六个闸口），但没有同步审查 25s 预算与链长的耦合，把 leak 类失败转化/推迟成了 budget 类失败。

另需澄清一处误判的历史责任：此前"budgetOverrun/7th-gate 零触发 = 修复没跑"的结论，源于**用代码里的 flag 名 `budgetOverrun` 去 grep 日志**，而日志实际文案是 `last resort on pending slot`——是验证方法错误，不是部署问题。教训见第四节第 1 条。

### 3.3 为什么这些缺陷没被早发现

| 缺陷 | 验证盲区 |
|---|---|
| ③ 死条件 | 单测只验证"触发后行为"，没验证"条件可达性"；哨兵只统计 leak/budget 分类，没有兜底触发率指标 → 0 触发无人报警 |
| ② 预算/链长耦合 | 提封顶时只对齐了"六闸口全覆盖"的语义，没有跑预算压力测试 |
| 验证方法错误 | 用变量名 grep 日志而非日志文案；"零触发"与"没部署"现象相同，未做区分 |

## 四、复盘教训

1. **修复验证必须对日志实际文案 grep**，不能用代码 flag/变量名去搜日志——本次"budgetOverrun 零触发"就是这么得出的假结论，把在跑的修复（30 次）误判成没跑。
2. **兜底代码必须验证条件可达性**。"永假条件"和"没部署"在观测上完全一样（都是 0 触发），但根因和修法天差地别——发现 0 触发时，先查条件是否可达，再查部署。
3. **链长上限与预算是耦合参数**。提高换线次数上限必须同步审查时间预算，否则只是把失败形态从 leak 换成 budget，总失败量不变。
4. **连接失效要精准到 socket/连接**。整 URL 池清在多请求并发场景是正反馈放大器，会让一次换线变成一片 stall。
5. **停滞检测与重试预算要对齐正常延迟分位**。已知基线 p50=13.9s / p90=41s（#43），20s 检测阈值卡在分位之间，45s 重试预算在尾部之上——两者都在惩罚尾部而不是拦截异常。
6. **修复分层验证指标要补全**：leak 类看哨兵 leak 计数（已有）；budget 类要看 give-up 率与兜底触发率（缺失）；延迟类要看 rotate 频率与 already_retired 占比（缺失告警）。
