### 0.2 六维度（前五维沿用，第六维新增）

| # | 维度 | 关注什么 |
|---|---|---|
| D1 | 正确性 | 结论对不对，会不会把不该用的地址放回去 |
| D2 | 一致性 | 代码、注释、文档、报表说的是不是同一件事 |

| D5 | 可测性 | 新路径有没有回归、能不能被断言 |

**为什么必须加第六维（不是凑数）**：本方案要改的是**落盘状态格式 + 守护进程重启后的恢复行为**。而「老条目没有新字段怎么办」「新旧代码同时在跑会怎样」「出事怎么退回」这三件事，恰好落在原五维的空白区——原五维里最接近的「边界与异常」关注的是**运行期输入异常**（空 ip、坏值、锁顺序），不覆盖**跨版本状态迁移**。

仓库里已有同类先例可作参照，只是没被提升为独立维度：`docs/review-5d-20261027.md` 的 NFR-5「新增状态字段可缺省，旧状态文件无需迁移」是一条兼容性约束；而本方案要做的事比它更重——不仅加字段，还要**换掉删除判据**，所以必须把兼容与演进单列一维来审。

## 1. 需求方视角：这次到底要解决什么

### 1.1 一句话

**台账条目同时兼职「选线状态」「惩罚判定」「垃圾回收」三件事，而回收这件事借用了前两件事的字段当依据，于是同一个字段被三处按三种规则解释。**

### 1.2 两个待修缺陷（本轮实测确认）

#### 缺陷 A：同一个字段，两套解释

`ban_until` 被两处解释：

- **判定侧**（`_warp_ban_until`）先校验类型标记必须等于 `rate429`、数值必须是有限正数，否则**整条精确封禁作废**，退回该类型的默认窗口；
- **清理侧**只判断数值是否大于当前时刻，**不问类型、不问条目是否仍处于标记态**，大于就跳过不删。

结果：同一条记录，判定侧说「已解禁、可以复用」，清理侧说「还没到点、必须留着」。两条结论来自同一个字段，却用了不同的解释规则。

- **本轮实测**：37,159 条带标记条目中，`ban_until` 未到期 3,108 条，**类型非法的 0 条** → 当前**没有实际损害**，属**潜在的一致性缺陷**，不是正在造成损失的故障。
- **危害不是「删不掉」本身**，而是**口径分裂**：判定、清理、报表三处各读一次同一字段，将来改规则必然漏改一处。判定侧专门写了注释说明「坏值只丢精确封禁、按默认窗口保守处理」，清理侧完全不知道这条约定——这类不对称正是后续改判定规则时最容易漏的地方。

#### 缺陷 B：生命周期锚点被「碰过」污染

清理的删除条件是「`ts` 早于 24 小时前」，而 `ts` 在 `_warp_ip_used_locked` 第一行被**无条件**写成当前时刻——不管这次是标脏、是换线登记、还是普通触碰。于是记录只要被碰过，就永远不满足删除条件。

- **本轮实测**：台账从 11-11 的 42,556 条 / 13 MB 降到 13:45 的 37,199 条 / 11.93 MB（**没有单调增长**）；按现行规则做只读模拟，「当前应删」= **0 条**。所以缺陷 B **不是「删不动的积压问题」，而是「判据选错 + 语义失真」**。
- **自续命的直接证据**：255 条记录 `first_seen` 距今 > 24h（最老 156.6h）却 `ts` < 1h——24 小时窗口对它们完全失效。
- **语义失真**：台账自称「24 小时窗口」，实际语义是「最后一次被碰过之后 24 小时」。活跃记录可活到 6.5 天。而 `first_seen` / `served_sec` 是代码注释里明确定义为「事后评估这个地址活了多久」的字段，跨多个周期串算会把寿命统计拉长，进而误导策略判断。

### 1.3 非目标（本次明确不改，一个数值都不动）

1. 不改惩罚期时长语义：403 六小时、429 六十秒 + 精确封禁、legacy 二十四小时，全部保持。
2. 不改选线四档判据，不改 `/64` 段静置（`prefix_rest_sec`）语义。
3. 不改探测三道闸门、不改探测节奏（`line_probe_cadence_sec=0`）、不改探针结论缓存 TTL。
4. 不做「台账瘦身」专项：本方案只**顺带**让表长回归窗口语义，不承诺把 37k 条压到某个更小的目标。
5. 不动 `blocked` 字段「只置真、不复位」的既有事实（改动面会扩大，留待下一轮）。

### 1.4 成功判据（可度量）

| # | 判据 | 度量方式 | 目标 |
|---|---|---|---|
| S1 | 访问不再续命 | 同一条目在只有「探测记账 / 换线登记 / 被选中」事件下，生命周期到期时刻保持不变 | 单元测试断言 + 线上表长 |
| S2 | 表长有上界 | 条目数 ≤ 24h 内真实活跃 IP 数（+ 容差） | 不再出现「活 6.5 天」的记录 |
| S3 | 三处口径一致 | 判定侧、清理侧、报表侧对同一批条目给出同一结论 | 抽样脚本比对，0 差异 |
| S4 | 零事故迁移 | 冷启动后 24h 内无「封禁中的 IP 被当作从未出现过」 | 上线观察指标 |
| S5 | 可回滚 | 任一阶段出问题，5 分钟内回到改动前行为 | 回滚演练通过 |

## 3. 设计方案

### 3.1 核心主张

**把「生命周期」从业务字段里抽出来，成为独立、语义单一、只由状态变更事件驱动的字段 `expires_at`。**

判定侧继续独占「还剩多久不能选」的解释权；清理侧只负责「什么时候可以删」，且**只读 `expires_at`**；报表侧读同一套口径。三者不再对同一个原始字段各做一次解释。

### 3.2 字段职责表（改造后的语义分工）

| 字段 | 唯一职责 | 谁写 | 谁读 | 现状问题 |
|---|---|---|---|---|
| `ts` | 选线：最近一次被碰过的时刻（段静置 `_warp_prefix_rest`） | 所有事件 | `_warp_prefix_rest`、`_warp_rest_time` | 同时被清理当删除依据 → 缺陷 B |
| `first_seen` | 事后评估：首次入账时刻 | 创建时 | 报表、寿命统计 | 因 `ts` 被刷新而失去「活多久」语义 |
| `blocked` | 判定：是否被标记过 | 标脏时（单向置真） | 判定侧 | 从不复位，条目永远走「被标脏」分支 |
| `blocked_ts_by_kind` | 判定：各类型惩罚期起点 | 标脏时 | `_warp_block_stamps` | — |
| `ban_until` / `ban_kind` | 判定：确切解禁时刻与类型 | 标脏时（仅 429） | `_warp_ban_until` | **同时被清理侧无校验地读** → 缺陷 A |
| `last_ok_ts` / `probe_ok_ts` | 选线档位 1/2 | 成功打点、探测 | `_warp_ip_rank` | — |
| `served_sec` | 事后评估：上一轮服役时长 | 新一轮惩罚开启时 | 报表 | 跨周期串算 |
| **`expires_at`（新增）** | **生命周期：最早可以丢弃的时刻** | **仅状态变更事件** | **清理侧（唯一）** | — |

### 3.3 `expires_at` 的定义与事件契约

**定义**：`expires_at` = 这条记录最早可以丢弃的时刻（epoch 秒）。

**计算规则**（对任意「续命事件」）：

> `expires_at` ← max( `expires_at` 现值 , max( 锚点 , 该轮最晚解禁时刻 ) + 复用窗口 )

- **复用窗口** = `ip_reuse_guard_sec`（24h）。新增独立配置项 `ledger_retention_sec`，默认同值，便于单独调；
- **锚点** = 最近一次**真实承载成功流量**的时刻（即 `last_ok_ts`）；
- **该轮最晚解禁时刻** = 判定侧算「还剩多久不能选」时用的那套规则算出的释放时刻（各类型起点 + 惩罚期，或合法的 `ban_until`）；未标记时为 0。

**机制性保障：`expires_at` 单调不减**——只能往后推，不能往前拉。这是防止「提前删除仍在封禁的地址」的底层机制，而不是靠各处自觉判断。

**事件分类（改造后）**：

| 事件 | 是否续命 | 到期时刻怎么变 | 理由 |
|---|---|---|---|
| 真实成功流量打点（`last_ok_ts` 更新） | ✅ 续命 | now + 24h | 复用冷却本来就是「距上次成功 24h」，这类刷新是对的 |
| 新一轮惩罚开启（403/429 新轮） | ✅ 续命 | 该轮最晚解禁 + 24h | 惩罚期结束后还要留一个复用窗口，避免立刻被当成新地址 |
| 精确封禁延长（`ban_until` 更新） | ✅ 续命 | 同上 | 保护必须跟着封禁走 |
| 同一轮内重复标脏 | ❌ | 不变 | 本轮起点未变，重复标脏不代表新状态 |
| 探测判 quota/flagged 但属同一轮 | ❌ | 不变 | 同上；**这正是实测里 97% 的写入来源，也就是污染源** |
| 探测结论记账（OK / unreachable / err） | ❌ | 不变 | 探测不是服务成功 |
| 被选为出口 / 换下线登记 / 换线后新地址入库 | ❌ | 不变 | 只是「碰过」，不代表承载过流量 |
| 报表读取 | ❌ | 不变 | 只读 |

**与现状的差别，浓缩成一句**：现在「碰过」就续命；改造后只有「承载过成功流量」或「状态真的变了」才续命。

> 注意 `ts` **保持原样、继续每次刷新**——它服务的是「段静置」（刚烧过的 /64 段短时间内换 /128 几乎等于没换），刷新是对的。本次只把「能不能删」从它身上摘下来。

### 3.4 三处职责分离（缺陷 A 的解法）

| 角色 | 改造前读什么 | 改造后读什么 |
|---|---|---|
| 判定侧（能不能选） | `blocked` + `blocked_ts_by_kind` + `ban_until`（校验类型） | **不变**，独占解释权 |
| 清理侧（何时删） | `ts` + `blocked` + `ban_until`（**不校验类型**） | **只读 `expires_at`** |
| 报表侧 | 各自读原始字段 | 读判定侧口径（上一轮已加的 `tools/channel_report.py --blocked-ips` 即此口径） |

**为什么能解决缺陷 A**：清理侧彻底不再解释 `ban_until`——精确封禁的保护在**写入时**一次性折算进 `expires_at`，坏值（类型标记不对、数值非法）在载入时归一化并作废。三处不再读同一个字段做不同判断，第二次口径分裂不会发生。

### 3.5 安全不变量（改动中唯一可能造成线上事故的地方）

| 编号 | 不变量 | 为什么成立 |
|---|---|---|
| INV-1 | `expires_at` ≥ 该轮最晚解禁时刻（含合法 `ban_until`） | 精确封禁写入时被钳制在 1s~24h 内（≤ 标脏时刻 + 24h）；403 最长 6h、legacy 最长 24h（≤ 标脏时刻 + 24h）；再叠加「解禁 + 24h」的保留窗口 → 有 24h 余量 |
| INV-2 | `expires_at` ≥ 最近一次成功流量时刻 + 复用窗口 | 复用冷却期内地址不会被删成「从未出现过」，档位不会从 2 掉回 0 |
| INV-3 | `expires_at` 单调不减 | 任何后续事件都不能把它拉早；删除判据因此永远安全 |
| INV-4 | 删除判据唯一：`expires_at` < 当前时刻 | 只有一条判据，不再有「两条水位线 + 一条豁免」三选一 |

**论证 INV-1 为什么是唯一的事故点**：一旦提前删除了仍在封禁中的地址，判定侧会因为「条目不存在」把它当成「从未出现过」的档 0 最优地址直接选中，选上去立刻 403/429——直接引发限流爆发。除 INV-1 外的所有机制都不针对这个风险。

### 3.6 迁移与兼容（缺陷 B 的解法 + 第六维主体）

**载入时归一化（一次性，37k 条毫秒级）**：

1. 老条目无 `expires_at` → 按保守口径补齐：`expires_at = max(ts, 该轮最晚解禁时刻) + 复用窗口`。
   - **为什么不按 `first_seen`**：按 `first_seen` 会一次删掉 5,219 条（14%），冷启动风险显著更高；
   - **保守口径的代价**：这批老条目会多活约一个窗口（24h），之后全部由新逻辑接管，可接受。
2. 老条目的 `ban_until` 一并归一化：类型标记不是 `rate429`、或数值非法 → 置空，并按默认窗口重算解禁时刻。
3. `blocked` 字段**不复位**（既有事实，本次不动），判定侧继续沿用。

**倒序兼容矩阵**：

| 场景 | 结果 |
|---|---|
| 新代码读老文件 | ✅ 能。缺 `expires_at` 走载入归一化 |
| 老代码读新文件 | ⚠️ 能读（JSON 多字段无害，老代码会忽略 `expires_at`），但**老代码仍按旧规则清理** → 新旧并存期间两套删除口径不一致 |
| 新旧实例并行 | ❌ **禁止**。必须串行：先停旧实例，再起新实例 |

**因此灰度必须串行**，这一点写进部署说明与 runbook。

### 3.7 灰度四阶段与回滚

| 阶段 | 做什么 | 进入判据 | 退出判据 | 回滚方式 |
|---|---|---|---|---|
| **P0 影子计算** | 新代码只计算 `expires_at`，不写盘、不改清理；把影子值与判定侧释放时刻做比对 | 单测全绿 | 影子值与判定释放时刻一致率 ≥ 99.9% | 关开关，删影子逻辑 |
| **P1 双写** | 写 `expires_at` 到台账，清理仍走旧规则 | P0 通过 | 线上满 24h，INV-1/2 无违规 | 停止写字段，旧代码可继续 |
| **P2 切判据** | 清理改用 `expires_at`；旧规则保留但不再使用 | P1 满 24h，且表长开始下降 | 表长降到窗口语义附近，且 403/429 命中率无异常抬升 | 配置开关切回 legacy + 重启 |
| **P3 收尾** | 删除旧清理分支与旧字段依赖 | P2 满 48h | 报表口径与判定一致（S3 达成） | — |

**回滚可行性**：清理判据由配置项 `ledger_cleanup_mode`（`legacy` / `expires_at`）控制，P1↔P2 之间出问题，**改配置 + 重启即可回退，不需要回滚代码**。这是本方案回滚能力的来源。

### 3.8 上线观察指标

| 指标 | 期望 | 异常信号 |
|---|---|---|
| 台账条目数 | 显著低于 37,199，收敛到「24h 内活跃 IP 数」量级 | 继续上涨 → 续命事件分类有漏 |
| `expires_at` 与判定侧释放时刻的偏差分布 | 恒 ≥ 0 | 出现负值 → INV-1 被破坏，立即回滚 |

### 6.3 影子比对脚本（P0 阶段）

对全量条目逐条计算两个值并比对：① 判定侧释放时刻（现在还能不能选）；② 影子 `expires_at` 的锚点部分（不含保留窗口）。要求：`expires_at` 的锚点 ≥ 释放时刻，偏差 ≥ 0，一致率 ≥ 99.9%，且不存在「释放时刻在 `expires_at` 之后」的条目。
