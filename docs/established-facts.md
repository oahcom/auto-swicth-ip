## 零、最根本的一条：这个 IP 池是**共享的**，不是我们独占的

**看起来像**：换 IP 没用了 —— 刚换的新地址没过多久照样 429，说明"换出口"这套
方法已经失效，是不是该换个思路了？

**实际是**：**WARP 的出口 IP 池是所有 WARP 用户在共享的**。我们不用这些 IP，
它们照样会被别人用掉、照样会进 ban 位。这不是我们的地址在被消耗，是一个**公共
资源在以自己的节奏变脏**。

**时段规律（实测）**：

| 时段 | 池子状态 |
|---|---|
| 早上 08:00 → 下午 16:00 | 相对好，新地址存活率正常 |
| 傍晚之后 | 开始恶化 |
| 深夜 → 凌晨 | **只有少数 IP 存活**，其余全部进 ban |

**为什么会被误判**：观察到"换 IP 后很快又 429"，最自然的结论是"换 IP 无效"。
但这是把**池子的集体消耗**误读成了**我们的换址动作失效**。要看的是：
这一刻池子里还有多少干净地址，而不是"我上次换的地址活了几分钟"。

**推论（这些都已经在代码里体现）**：
- 换 IP 依然是唯一的解，只是**可用地址的供给随时段变化** —— 白天随手换就有，
  深夜要换很多次才撞到一个活的。
- 深夜重启刷不出新地址（10-31 夜间实测 17036 次重启、**0 次刷新成功**），
  不是因为重启坏了，是池子干了。所以有夜间锁（`warp_night.py`）。
- 渠道锁锁到次日 08:00（见下面第 1 条）也是同一个理由：额度重置 + 池子回血
  都发生在早八点。
- 判断"换址是否有效"必须**分时段看**。拿深夜的数据去论证"换 IP 没用"，
  等于用枯水期的水位论证这条河没有水。

**不要动**：不要因为"换了还是 429"就下结论说换 IP 无效并删除这套机制。先看
当时是几点、池子里还有没有活地址。

## 一、配额与封禁

### 1. 早八点（08:00）才解封 —— 这是 opencode 官方的重置时间

**看起来像**：为什么半夜被封的线路要等到早上八点？这不是过度限制吗？

**实际是**：`channel_ban_reset_hour = 8`。opencode 免费层的配额按**自然日**重置，
重置时刻是早上八点（本地时间）。一条渠道被判定"烧穿"后，重启换地址也拿不到
可用额度 —— 因为**整天**的额度都已经打完了。等到八点是**配额真实恢复的时刻**，
不是我们随便定的闹钟。

**为什么这么定**：2026-11-02 实测，中午之后 94% 的换址记录都是 ban、89.6% 的
地址首用即 quota，WG-1..6 在 NRT 的 12 个段上 100% 烧穿，每线刷了 1200~1600 次。
在额度耗尽的当天继续刷，只是把剩下的地址也一起烧掉。

**不要动**：`channel_ban_reset_hour`、`channel_ban_hold_enabled`。
真要改，先确认 opencode 的重置时间变了。

**相关的锁松开条件**：夜间锁 / 渠道锁 / 额度隔离 / 小时配额这四道锁，
在**刚换过节点**时必须让路（`_warp_line_restart(..., rebound=True)`）——
它们防的是"在同一个烂地址池里反复抽签"，换了节点池子就变了。

---

### 2. 渠道锁：当天最近 1000 条全 quota，或连续 5h 无出口地址

**看起来像**：1000 条才锁，是不是永远锁不上？

**实际是**（2026-11-04 主人定，替换 11-02 的三层口径）两条独立判据：
- **A**：当天最近 `channel_ban_min_samples = 1000` 条模型层实测**全部** `quota`
  —— 出现任何一条 `OK`/`flagged` 就否决；
- **B**：连续 `channel_noaddr_hold_sec = 5h` 探测不到出口地址（中途拿到一次就重新计时）。

样本只收地址级结论（OK / quota / flagged），探测自身失败（err / unreachable）
不入账 —— 那说的是探测器不通，不是渠道烧穿。

**锁定后**：`stop_probe = True`，`_warp_line_needs_probe` 与 `_probe_one_line`
两个入口都拦下，**不再探测、不再重启**；锁到次日 `channel_ban_reset_hour`。
到期由 `_rehome_held_lines` 统一释放：清 `stop_probe` + 当天样本 + 无地址计时，
并把 `ban_hold_until` 归零（不归零会每分钟再清一次，样本永远攒不满）。

**为什么废掉旧口径**：1h 窗口 + 31 条 100% 封禁的判据只在**旧样本滑出窗口前**
成立，而锁定期内还在继续探测、继续记账，到期时那一窗口的旧样本又把它续到
次日。实测 WARP-WG-21 在 11-03 08:00 被锁后，10:52~13:37 期间换两个全新 IP
出了 **7 次 OK**，锁依然留到次日 08:00；次日 08:00:19 又因旧样本重锁。旧口径
的「铺满半窗」只看最旧一条、不看中间空洞（实测 WG-4 有 20 分钟无样本仍算
"持续一小时"）。

**不要动**：`channel_ban_reset_hour`（见下面第 1 条）。要改阈值先想清楚
「能出 OK 的渠道不许锁」这条是主人的原话，任何让它可能被锁的改动都要先确认。

**锁定不是终点，补位才是**（2026-11-04 主人定）：一个渠道被封，**必定**要有
另外一个渠道补位 —— 拿已注册但没启用的空闲设备线，落到 ban 率最低的 colo 上，
08:00 再撤。它不是重定位：重定位救的是这条线自己，补位保证的是「锁定期内总还有
一条渠道在服务」。所以 `channel_rehome_enabled=False` 时重定位可以停，**补位照开**。
详见 [task-20261104-channel-backfill.md](task-20261104-channel-backfill.md)。

### 3. 429 是出口 IP 的配额，不是账号的

**看起来像**：既然换 IP 能解 429，为什么还有那么多 429？

**实际是**：opencode 免费层的 `FreeUsageLimitError`（429）**按出口 IP 判定**。
换出口即拿到新配额。实测 16:24 手动切 WARP 成员后成功率 3.5% → 9.3%（90s 窗口）。
这是整个 WARP 体系的立论基础 —— 如果配额跟账号走，换 IP 毫无意义，这套系统就不该存在。

**推论**：所有"换出口"的动作（主动轮换、错误换线、脏线刷新）都是在**买新配额**。
单 IP 配额不是固定值：主动轮换段的中位成功数是 **113.5** 条，429 残段中位只有 10 条
（后者是"还剩多少"，不是容量）。

**但换 IP 能买到多少，取决于当时池子里还有多少干净地址** —— 见上面第 0 条。
白天换一次就有效，深夜可能要换十几次才撞到一个活的。这不是方法失效，
是供给随时段波动。

## 二、地址池的物理约束

### 4. v6 每次重连必换地址，v4 只在 colo 的地址池内翻牌

**看起来像**：为什么 v4 线要特殊处理（跨 colo 换节点、首次重启就 rebind）？

**实际是**：
- **v6**：每次重连都拿到全新的地址，连 /64 都会变。所以同 colo 换个节点就够了。
- **v4**：地址由**落地 colo 决定**（每个 colo 一个小池子）。同一个 colo 换节点，
  拿回来的还是那批地址 —— 等于没换。**必须换 colo 才等于换了地址池**。

实测：同一节点连续重启，v4 地址在 `.211` / `.243` 之间跳，与节点无关；
四条 v4 线的出口只有 `104.28.243` / `237` / `205` 三个 /24。

**不要动**：`warp_blocks.V4_COLO = "ALL"`（v4 合并成一个虚拟块）、
`_same_block_standby` 里 v4 走 `others + same`（跨块优先）、
`_refresh_idle_warp` / `_restart_warp_inplace` 里 v4 的 `rebind=(family=="v4")`。

---

### 5. 直连 WARP 的 v4 不属于块模型

**看起来像**：v4 块里怎么少了那么多节点？明明有几十条 v4 线。

**实际是**：有两条完全不同的链路：
- **代理承载的 v4**（WG 线，UDP 经机场节点中转）→ 属于块模型，合并成一个 ALL 块
- **直连 WARP 的 v4**（`WARP-CF-D` / `WARP-CF-E`，usque 隧道，不经机场）→ **不属于块模型**

后者是本机 MASQUE 会话直接拿到的地址，很多节点，实际出口是 v6。混进块模型会让
v4 块里一半的渠道根本不该由 WG 线承担。

---

### 6. 主机名标签 ≠ 落地机房

**看起来像**：桶叫 CFB，怎么实测落地是 SJC？

**实际是**：机场的订阅桶标签（CFB / OLD / PHX…）是**机场自己的编号习惯**，不是机房。
实测 CFB 桶落地是 SJC、PHX 桶有 4/11 是 LAX、OLD 桶是 LAX。
所以 colo 一律取**实测 trace 值**，不取标签。

---

### 7. 块按 colo 切，绝不按落地 /64 切

**看起来像**：同一个 /64 的节点是不是该算一组？

**实际是**：段是**会话建立时的抽签结果**。同一节点连测 5 轮落到 5 个不同 /64，
7/16 组连 /48 都会变。按段切块，今天分的块明天重连就散架。
块只能按 colo（机房）这个稳定维度切。

## 三、探测与判定

### 8. STUN(3478) 探不通 ≠ WARP(2408) 跑不了

**看起来像**：这个节点 STUN 都不通，肯定跑不了 WARP 吧？

**实际是**：WARP 走的是 **2408**，节点完全可以只放行 2408 不放行 3478。
决定性证据：`pq.aws48` STUN=False，但它承载的 WARP-WG-5 正在正常出 v6 流量
（colo=NRT）。

**曾经的错误**：`udp_capable()` 曾用 STUN 判定并按 6 小时缓存，228 条缓存里 192 条
被误判为 False。`apply()` 据此把 22 条渠道砍到 8 条，v4 合并块直接清空。
现在这个函数**只做原样透传**。

**不要动**：不要给 `udp_capable` 加回任何过滤逻辑。节点能否承载 WARP，
只能靠**实际握手**（`warp_diag.py`）验证。

---

### 9. 系统 DNS 解析不了机场域名

**看起来像**：`socket.create_connection(节点域名)` 全部超时，是不是节点全死了？

**实际是**：机场节点域名**只由订阅里的 DoH 解析得了**
（`dns-airport` = `https://custom.juhazf.cn/inst`），系统 DNS 一律超时。
实测直接用系统 DNS 时 19 条线全部 TimeoutError/gaierror，而其中 **8 条当时正在
正常出流量** —— 拿系统 DNS 的失败当节点死亡，会把整批健康线判死并无谓重启。

**结论**：任何节点探测都必须经 sing-box，并复用生产 DNS 配置。

---

### 10. "节点 TCP 通"不等于"这条线能用"

**看起来像**：节点能连上，这条线为什么还是拿不到出口？

**实际是**：机场节点存在"收得了 TCP、不转发 UDP 2408"这一类。敲门有反应，
但隧道起不来。**唯一可靠的判据是「这条线有没有拿到过出口地址」**。

**曾经的错误**：用 `last_ok_ts`（这条线有没有成功服务过）判，但它在
`verdict=blocked/quota` 时会被主动清零 —— 而 blocked 说的是"这个出口 IP 被
opencode 限流"，不是"隧道不通"。结果 22 条线全被判死，包括正在出流量的 PHX。

---

### 11. 一次探测失败不算死，要连续 3 轮

**看起来像**：都两分钟没通了，为什么还不换？

**实际是**：机场线路抖得很厉害，可用性以分钟计。立刻换的话整个池子每两轮
就翻一次面，比不管还糟。守护按 60 秒一轮，连续 3 轮（约 3 分钟）才动手。

**另一半**：刚重启 / 刚换过节点的线，**2 分钟内不判**。隧道握手 + 拿出口地址要
几十秒，这期间它看起来就是"没出口"，但那是还没起来。

---

### 12. 探测通道失明时，自动退回历史判据

**看起来像**：整批 17 条线在同一秒全部 `unreachable`，节点全挂了？

**实际是**：那是探测通道自己的问题。`_warp_probe_blind` 在一整批**全部**
`unreachable` 时宣布失明 120 秒，期间不再发探测、历史判据重新生效。

实测 16:50:18 一批 17 条同一秒全灭，重启换 IP 后 16:50:50~52 全部 OK ——
那 17 次重启和配额全是白烧的。

**判据必须是「整批」**：单条 `unreachable` 是该出口的真实瞬态，只有同一批
同时全灭才可能是探测通道自己瞎了。用观测者的故障给被观测对象定罪，是最贵的错误。

---

## 四、链路与架构

### 13. H2（MASQUE over HTTP/2）必须满足三个硬条件

**看起来像**：配置都对，怎么还是 EOF / TLS 握手失败？

**实际是**，三个条件缺一不可：
1. **空 SNI**（`-s ''`）—— 带 SNI 会被拒
2. **RFC 7540 普通 CONNECT**，不是 extended CONNECT
3. **原始 TCP 中继**到 CF 的 IP 字面量，不经过 SOCKS 中转

另外 `usque -P` **只改端口不改 host**，必须在派生的设备配置里把
`endpoint_h2_v4` 改写成 `127.0.0.1`。

**还有一个致命细节**：sing-box 的 `direct` 入站如果配了转发规则，
**规则必须显式写 `"action": "route"`**。在 sing-box 1.13 里，没有 action 的规则
会被当作 **reject**，表现为 TLS `unexpected eof`、usque 报 `failed to send request: EOF`
—— 看起来和"机场节点死了"一模一样。

---

### 13b. 承载 WARP 有两条路：UDP（WireGuard）和 TCP（MASQUE/H2）

**看起来像**：`warp_diag.py` 报 `handshake` 全灭，所以这批节点不能承载 WARP。

**实际是**：那只是 **UDP 那一条路**不通。承载 WARP 有两条独立的路径，
判据、探针、落点全都不同，**必须分开测**：

| 路径 | 形态 | 探针 | 产物 | 池 |
|---|---|---|---|---|
| UDP | WireGuard，经代理节点转发 2408 | `warp_diag.py` | `WARP-BLK-*` 渠道 | WG 线位（`warp-wg-N`） |
| TCP | MASQUE over HTTP/2，裸 TCP 经节点 | `tools/probe_h2_nodes.py` | `WARP-H2-*` 渠道 | usque 设备（`usque-h2-N`） |

2026-11-04 实测同一批节点：UDP 判据 **0/2**，MASQUE 判据 **18/23**。
只跑 `warp_diag` 就下"不能承载"的结论，等于把一大半可用节点扔掉。

**改动的判据**：新增订阅源后两条都要测。`channels()` 里 H2 渠道是单独展开
的一份（v6 池显式剔除 `carrier == h2`，因为它不占 WG 线位），tag 前缀也不同
（`WARP-H2-` vs `WARP-BLK-`）—— 同名会让夜间白名单/台账/日志把两条线当成一条。

---

### 13c. H2 线的编号（=端口偏移）是既有部署契约，不能重算

**看起来像**：渲染器按「有多少台设备就取前几条」渲染，顺手重编号更整齐。

**实际是**：`WARP-H2-<COLO>-<N>` 的 **N 就是 SOCKS 端口偏移**（`1180 + N`），
这套映射同时写进了三处，任何一处对不上就是「线在跑但没人用它」：

| 位置 | 内容 |
|---|---|
| `.warp/warp-outbound.json` | 主 sing-box 的 H2 出站成员（tag + server_port） |
| 主配置 `opencode-out` 的成员表 | selector 可选成员 |
| `.warp/backfill.json` 的 `backfill_for` | 哪条 WG 线补哪条 H2 线的位 |

2026-11-04 实测教训：渲染器改成按「取前 n 条」重排后，19 条里只有 **2 条**
能对上主配置成员表。现象极难查 —— 19 条 usque 全 active、SOCKS 口全在监听、
`curl` 单条直连也能出 `warp=on`，但 selector 指到的名字对应的是别的端口。

**正确做法**：编号取既有成员表的顺序（`.warp/warp-outbound.json` 里
`WARP-H2-*` 的出现顺序），渲染器**只重选节点**，不改顺序、不改名字。
设备不够时宁可少渲染几条，也不许改名。

**同块多条线不能重名**：`ch["index"]` 是**块内**序号，同 colo 三条线会全叫
`NRT-0/1/2`；而成员编号必须是全局唯一的。两者不是一回事。

**新块/新渠道的续号**（2026-11-05 加）：`fixed_order` 原先只读
`warp-outbound.json`，于是块模型里**没有既有成员**的 colo（实测 BOM/FRA/GIG/LHR）
永远渲染不出来 —— 块测出来了、线一条没有。现在渲染器在既有成员之后按
「既有最大编号 + 1」续号补成员（`_member_order`），既有成员的编号/顺序仍
一位不动。新增 12 条（19 → 31）实测全部一次装成。

**自动同步链**：`_run_h2_probe` 只更新 block-map，不渲染。daemon 的
`_run_h2_sync`（30min 自限）跑 `render_h2_lines.py --check` 看差集，
有差集才渲染 → `h2-install.sh --no-render` → `members.py` →
`patch-wg-outbounds.py` → 重启主 sing-box。渲染必须在提权**之前**以本用户
完成：root 跑会把 `.warp/h2/*` 属主改成 root，daemon 之后读不回来。

**手动跑 `h2-install.sh` 只做一半，不要以为装完就到位了（2026-11-05 实测）**：
它只装 H2 子 sing-box + usque 单元，**不写** `warp-outbound.json`、**不跑**
`patch-wg-outbounds.py`。于是 5 条新线（SJC-35/BOM-36/DUB-37/IAD-38/JNB-39）
单元全 active、`h2-sel-N` 全在 9091 上、单条 SOCKS 直连也能出 `warp=on`，
但主 `opencode-out` 的成员表里**一条都没有** —— 69 项里查不到，daemon 永远
切不过去。而 `patch-wg-outbounds.py --check` 这时还报 `UNCHANGED`：它读的
`warp-outbound.json` 本身就没这 5 条（该文件由 `members.py` 从 `config.py`
的 `warp.members` 生成，而 H2 成员是 `config.py` 在 import 期从
`channels.json` 追加的 —— 必须重新跑一次 `members.py --write-warp-outbound`
才会看到）。

手动排障时的完整顺序（缺一步就是上面那个症状）：

```bash
python3 deploy/render_h2_lines.py          # 写 .warp/h2/
python3 deploy/members.py --write-warp-outbound   # ← h2-install.sh 不会做
./deploy/h2-install.sh
python3 deploy/patch-wg-outbounds.py       # ← h2-install.sh 不会做
# 主 sing-box 必须重载：它由 daemon Popen 拉起、无独立单元。
# 杀掉主进程，watchdog（30s 一轮）会按新配置重新拉起。
kill $(pgrep -f "sing-box run -c $PWD/singbox-config.json")
```

验证要看**运行中**的 selector，不是配置文件的：

```bash

  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(len(d["all"]), d["now"])'
```

### 13d. H2 线与 WG 线的「换节点」机制不同（不能互相套用）

**看起来像**：WG 有 `warp_wg.rebind()` 能在运行时换节点，H2 照抄一个就行。

**实际是**，两者切换点在**完全不同的地方**：

| | WG（`warp-wg-N`） | H2（`usque-h2-N`） |
|---|---|---|
| 节点写在哪 | 该线**自己的** `singbox.json` 内嵌出站副本 | 31 条线**共享**的 `asip-h2-singbox.service` |
| 运行时能换吗 | ✅ `rebind()` 改自己那份 + 重启自己那条 | ✅ `PUT /proxies/h2-sel-<i>`，**不重启任何进程** |
| 正规换法 | 运行时 rebind | selector 切换；只有**改候选池**才要重渲染 |

**2026-11-05 起 H2 换节点不需要重启了**（原先「只能重渲染 + 重启共享 sing-box，
19 条一起断」）。做法：渲染器把每个 colo 的**整个候选池**预写成出站（按节点
全局去重，`h2-<node>`）+ 每条线一个 `selector`（`h2-sel-<i>`）+ 独立的
Clash API（`127.0.0.1:9091`）；规则指向 selector 而不是某个节点出站。
daemon 换节点 = `PUT /proxies/h2-sel-<i>` `{"name": "h2-<node>"}`，即时生效。

**但「能换节点」不等于「换得到能用的节点」**。实测 2026-11-05：整个池子的
节点都不转发时，`_h2_repair` 会每 60s 在死节点之间轮转一圈 —— 每次 PUT 都清
`ip`、触发一整轮探测，日志看起来像在自愈，实际产出的出口地址是 0。为此加了
`_H2_TRIED`（本轮已试过的节点集合，拿到出口地址即清空）：整池试遍就停手，
等重渲染或网络恢复，而不是空转。**看到 H2 线在「换节点」不代表链路是通的，
要看它有没有拿到出口地址。**

**锁的前提对 H2 不成立**。`通道锁`（`ban_hold_until`）的两条入口都是「重启
白烧」—— 惩罚期换的是同一节点的地址、5h 无出口说明重启救不了。而 H2 换节点
不重启、不断流、零成本，所以 `_rehome_held_lines` 对**带 `ban_noaddr_since`
的 H2 线**先换节点、换成了就直接解锁放回探测（quota 锁不动：地址被烧时节点
本身是好的）。实测 2026-11-05：NRT-13/14、TPE-5/6/18、SLC-11/12 被锁到次日
08:00、整晚零探测，其中 NRT 两条当时就有 4 个 TCP 可达的候选；解锁后 31 条线
里有出口的从 12 条涨到 20 条。

两个仍然成立的前置条件：

1. **节点必须已在候选池里** —— sing-box 没有运行时追加出站的接口，PUT 一个
   未声明的名字回 400。加节点仍要重渲染 + `h2-install.sh`（这一次会重启共享
   sing-box）。所以 `_h2_select` 把 400 映射成 `"gone"`（别再重试）。
2. **补位是 WG 的活** —— H2 渠道没节点可用时，`_backfill_open` 拉起的是空闲
   **WG** 设备线（`kind="wg"`），落到 ban 率最低的 colo

`h2-install.sh` 判「要不要重启共享 sing-box」用的是 `/run/asip-h2-singbox.md5`
stamp（进程当前跑的那份配置的哈希），**不是**脚本前后两次哈希 —— `--no-render`
时后者恒等，新 selector 会一直不加载，PUT 回 404，换线静默失效（2026-11-05
实测踩到）。

### 13d2. 「设备用完」是两种设备用完了；补位只补 WG 那一种

**看起来像**：补位日志报「没有能起设备的空闲线」，那就再注册几台设备不就完了。

**实际是**，这里的「设备」有两套，互不通用：

| | WG 设备 | H2 设备 |
|---|---|---|
| 注册方式 | `wgcf register`（`warp_wg.register_line`） | `usque register`（`deploy/h2-add-devices.sh`） |
| 落点 | `.warp/wglines/lineN/profile.conf` | `.warp/usque*/config.json` |
| 占用方 | `warp-wg-N.service` | `usque-warp*.service` + `usque-h2-*.service` |
| 生成方式 | 注册 + **单元另一步**（`wg-lines-install.sh`） | 注册 + **重渲染**（`render_h2_lines.py`） |
| 能否补位 | ✅ 直接起一条新线 | ❌ 要重渲染 19 条线，全部断几秒 |

**所以 H2 渠道被封时，自愈动作是造 WG 设备线，不是造 usque 设备**。
2026-11-04 之前 `_ensure_h2_devices` 走反了方向：它注册 usque 设备，但补位
判据（`_backfill_spare_indices`）只认 `wglines/lineN`，注册多少台都补不上，
反而每台烧一格 CF 注册额度、把窗口拉长。

正确路径是 `_ensure_backfill_line()`（2026-11-04 加）：

1. 先找「已注册但**单元没装**」的线 → 跑 `deploy/wg-lines-install.sh --line N`
   （不烧 CF 注册额度）
2. 一台都没有 → `warp_wg.register_line(max+1)` + 同一条命令装单元
3. 每 `_WG_CREATE_GAP`(600s) 最多**注册**一条；CF 对 wgcf 约 9 台/窗口。
   **装单元不受这条限速**（不烧额度），且限速依据是磁盘上最新
   `profile.conf` 的 mtime，不是进程内变量 —— 后者 daemon 一重启就归零，
   实测 19:35 重启后 8 秒内连造两条线
4. 线号硬上限 `_WG_MAX_LINES`=64：补位判据哪天回归出 bug（新线装完单元却
   不被认），这条路径会每 10 分钟烧一台 CF 设备。宁可停下报错，不无声膨胀

**mask 的线（软链 `/dev/null`）永不自动恢复**：那是主人手工停用的，
不是「没部署」。

**为什么单元是独立一步**：`register_line` 只写 profile，单元由
`deploy/wg-lines-install.sh` 生成。只注册不装单元 = 那条线不存在 ——
实测 line31 注册了一整晚，补位日志每轮仍报「没有能起设备的空闲线」，
因为 `_backfill_spare_indices` 要求单元文件真实存在。

**装单元必须走 `systemd-run`，不能直接 `sudo`**：`auto-switch-ip.service`
带 `ProtectSystem=strict`，`/etc` 在**它的 mount namespace** 里是只读的，
而 `sudo` 不换 namespace —— 直接跑脚本会报
`/etc/systemd/system/warp-wg-32.service: Read-only file system`
（实测 2026-11-04 连挂两次）。`systemd-run` 新起一个独立 transient 单元，
在宿主 namespace 里跑，不受这份沙箱约束。

顺带：以 root 跑脚本时 `id -u`=0、`getent passwd 0` 得 `/root`，单元会被
写成 `User=root` + `HOME=/root`；凭据属 administrator，那条线起来读不到自己
的配置。调用方必须显式传 `ASIP_RUN_USER` / `ASIP_RUN_GROUP` / `ASIP_HOME_DIR`
（`_install_wg_unit` 从 `pwd.getpwuid(os.getuid())` 取）。

### 13e. 承载口径：三种 WARP 路径各有名字，`proxy` 只指「纯代理」

**看起来像**：`asip blk` 里 `承载=proxy`，所以这些节点「只是在用代理」。

**实际是**，`proxy` 这个词过去被当成三种东西的统称，必须拆开：

| 叫法 | 含义 | 判据 | 故障表现 |
|---|---|---|---|
| `warp-proxy` | WG over UDP，经机场节点中转 | UDP 2408 握手 | UDP 被封就死，TCP 通没用 |
| `h2-warp` | MASQUE over HTTP/2，裸 TCP 经节点 | CF trace 里 `warp=on` | 只要 TCP 通就能活 |
| `warp-direct` | 直连 WARP（usque 隧道，不经节点） | MASQUE 直连 CF | 与机场完全无关 |
| **`proxy`** | **纯代理，不承载 WARP** | 只是订阅池的轮换成员 | 与 WARP 无关 |

前三种都是「拿 WARP 出口」，差别在**用什么协议穿过去**；第四种根本没有
WARP 出口，它只是把流量转给机场。把它们都显示成 `proxy`，会让人以为
「这些节点只是在当代理用」，而实际上前三种都在产出 WARP 出口地址。

配置里的 `carrier` 字段（`proxy` / `both` / `h2`）是**块侧的口径**
（这个 colo 允许走哪几条路），对外展示必须翻译成上表的名字 ——
`tools/block_view.py` 的 `CARRIER_LABEL` 就是这张映射表。

### 13f. 块 = 该 colo 下**全部**适配节点；`channels_per_block` 只决定几条线位

**看起来像**：`asip blk --channels` 里 HKG 块只显示 3 行，所以这个块只有
3 个节点，其余 18 个「没进块」。

**实际是**：块的定义就是「同 colo 的节点放一块」，**块内所有适配节点都算
成员**。`channels_per_block`（默认 3）决定的是从这个池子里拉几条**线位**
（WG 线 / usque 设备），拉不完的留在池子里当候补。

实测 HKG 块：池 21 个节点、排成线位 3 个、候补 18 个。候补不是被丢弃 ——
前 3 个死了后面的顶上，这正是池子深度的意义。

**看块要看 `asip blk --blocks`**（块池视角：列出全部节点并标出谁有线位），
`--channels` 是「线位视角」，两者回答的不是同一个问题。

### 13g. 自动化探测的两条路必须用**各自的**台账

**看起来像**：`block-map` 里有 colo 就算测过了，自动探测据此跳过。

**实际是**：`colo` 是 **WG** 探测写的，`carrier=h2` 是 **H2** 探测写的，
两者互不代表。共用判据的后果是 H2 探测永远认为「已测过」——
实测 296 个生产节点里只有 61 个有 h2 结论，其余 235 个从没测过 H2，
`carrier=h2` 再也不会增加，H2 池子死在老节点上。

`_pending_probe_nodes(limit, state_path=...)` 因此分两种口径：
- WG：`block-map` 里没有 colo
- H2：**H2 自己的** `h2_probe_state.json` 里没有「测过且失败」

两边都遵守同一条：**测过且成功的不跳过**——成功不等于已入块，没跑 merge
的节点 colo 只留在 JSONL 里。

### 13h. 部分 H2 线绑在死节点上是**预期状态**，不是故障

**看起来像**：19 条 H2 里有 8 条 `curl` 不通、绑的是 `bilibili-image-cdn.juhazf.cn`，
显然是没修完。

**实际是**，这是池子容量的真实约束，改了反而更糟：

- okz 那批节点（`bilibili-image-cdn.juhazf.cn`）最近系统性超时 —— 这是机场侧
  现状，不是探测或配置问题
- 能承载 H2 的**活**节点集中在 **etcloud**（18 个），只覆盖 **6 个 colo**：
  NRT / LAX / SIN / HKG / ICN / BOM
- **TPE / ORD / SLC 三个 colo 里一个可达节点都没有**，绑在那些 colo 的线
  （TPE-5/6、ORD-9、SLC-11/12、TPE-18，以及 NRT-13/14）必然显示不通

2026-11-04 实测终态：**13/19 条 `warp=on`**。剩下 6 条不是 bug。

**为什么不能「优化」掉**：
- 把它们换成别的 colo 的活节点 = 块模型失去了「一条线一个 colo」的意义，
  colo 分布退化成少数几个落点
- 删掉它们 = 那 6 台 usque 设备被释放，但飞机场侧一旦恢复（okz 的节点只是
  超时、DNS 还在），这批线需要重新注册设备才能回来

**该等的**：okz 恢复、或多测出 TPE/ORD/SLC 的 H2 承载节点（`probe_h2_nodes.py`
只测过 etcloud 的 18 个；yyd2tett 的 49 个与 dasho 的 46 个从未测过 H2）。

**补位不救它**，也别误会：这些线不通时 `_backfill_open` 会给它们开 WG 补位线，
那是「被封渠道另有渠道顶上」，与「这条 H2 线自己恢复」是两回事（见 13d2）。

**2026-11-05 06:00 起的扩容推翻了「只有 6 个 colo」这条**：把
`.warp/h2_probe_state.json` 里 `ok` 但块表没 colo 的 31 个节点并进去后，块模型
多出 **FRA / GIG / IST / LHR / SYD** 五个 colo，H2 渠道 22 → 32 条。这些 colo
在 `.warp_ip_used.json` 里**一条记录都没有** —— 之前的 colo 归因分布里根本
没有它们，所以早先「NRT/PHX/SIN 100% 已封」的结论不覆盖它们。

但要看清收益的性质：**新 colo 换的是「换得出来的新鲜地址」，不是「能反复用的
地址」**。实测扩容后 12 分钟内取到 663 个不同出口、655 个是台账里首次出现的
全新地址，而单条地址仍然一格配额就 429（LHR-33 与 SYD-34 各自的新地址都在
2 分钟内被标 `rate429`）。所以扩容抬高的是**单位时间的可用地址产出**，不是
单地址寿命 —— 它救急，不改变「必须持续换」这件事。

**2026-11-05 下午第二波 + 补源：BOM / JNB / DUB / IAD 到手。** 远端此前
一条 greatgame 节点都没有，根因不在探测而在**订阅源缺失**：远端的
`.extra_subscriptions` 只有 yyd2tett 与 jiashule，本地多一条 etcloud
（`3e136476…`，29 个 greatgame）。补上后远端 H2 实测 **22/28 可承载**，
块数 15 → **19**，新增 SJC/BOM/DUB/IAD/JNB 五个块、5 条线（35–39）。
端到端实测全部 `warp=on`：BOM `2a09:bac5:3afa:11c3::1c5:12e` / DUB
`2a09:bac5:3a67:2400::396:68` / IAD `2a09:bac1:76a0:11c0::400:5d` /
JNB `2a09:bac5:d4b4:1b9b::2c0:2e` / SJC `2a09:bac5:661b:28::4:361`。

**这条源的成功率远高于早先那 1/6**：同一批 greatgame 节点在本地当时只用 6 个
样本、仅 1 个通过（`normal:2155` → HKG），而远端 28 个里 22 个通过。差异来自
**当时 okz 节点整体超时**，不是 greatgame 不行 —— 那次结论（13h 开头
「etcloud 只覆盖 6 个 colo」）是特定时段的测量，不是节点属性。

**补源时必然踩到的一个坑**：一次性订阅链接在本地拉过之后已失效，远端刷新会
走 `_fetch_or_cache` 回退上一轮快照（日志 `本轮用快照（0.2h）`）。所以补源的
正确顺序是**先传 `.sub_cache/<key>.json` 再改 `.extra_subscriptions`** ——
否则远端第一轮刷新拿不到任何节点，还会被后续刷新反复覆盖成空。

**新线「一直没出过口」先看 `last_probe_ts`，别急着怪节点**（2026-11-05，已修）。
`_warp_line_needs_probe` 的两条到期分支原本都返回 `now`，而 `_warp_prober_loop`
是 `due.sort(key=p[0])` 取前 `probe_concurrency`(32) 条 —— 排序键全相同，
排序退化成成员表顺序，前 32 条固定占满槽位。后果是**排在末尾的新线永远排不上**：
新增 5 条后 6 分钟 `daemon.log` 里一次没出现它们的 tag，状态表 `last_probe_ts`
恒为 0，而同时 69 条无 ip 的线在抢那 32 个槽位。线本身完全正常（SOCKS 口全监听、
直连 trace 出 `warp=on`）。改成返回 `last_probe_ts`（没探过=0 最优先）后，
5 条线 8~14 秒内全部探到、4 条立刻出 IP。

这个坑对你判断「节点行不行」有直接影响：**`last_probe_ts=0` 是「没探过」，
不是「探了不行」**。两种情况在报表上都表现为「这条线没有出口地址」，但结论相反。

另一个必须同时做的：**设备目录缺 `usque` 软链时渲染器会把它当空闲发出去**，
单元起上去是 `status=127` 无限重启，daemon 侧只表现为「一直取不到出口」。
远端 9 台 `usque-h2new*` 正是如此，扩容时才从 journal 里发现。`free_devices()`
现在会幂等补链接。

### 14. WG 线必须经代理节点中转，直连不通

**看起来像**：为什么要绕这一层，直连不是更快吗？

**实际是**：本机到 `162.159.192.1:2408` 的 UDP 被运营商 ACL 拦了
（实测在 27.50.59.99 收到 ICMP type 3 code 13），直连握手全部超时。
但同一条 UDP 经代理节点中转（sing-box endpoint 的 `detour`）后可以正常握手
并拿到 WARP 出口。

**这不是可选的优化，是物理约束。**

---

### 15. deploy 单元由代码推导，不手写

**看起来像**：直接改 `.service` 文件不是更快？

**实际是**：`deploy/install.sh` 从 `config.py` 的 `warp.members` 生成单元。
单元名必须与 `members[].service` 一致，否则 daemon 的 `systemctl restart` 打空。
改 `members` 后跑 `./deploy/install.sh --units-only` 重生成。

同理 `deploy/render_h2_lines.py` 从 `.warp/h2/channels.json` 渲染 H2 线路。

---

### 16. 系统级单元，禁止 `systemctl --user`

**看起来像**：用 `--user` 不是更安全？

**实际是**：单元在 `/etc/systemd/system/`。对系统级单元跑 `systemctl --user`
**会返回 0 而什么也不做** —— `asip warp stop` 报成功、隧道照跑，比报错更难查。
所有状态/重启命令一律用 `sudo systemctl`。

---

### 17. `warp-svc` 必须保持 masked + inactive

**看起来像**：装了 Cloudflare 的 WARP 客户端，为什么不启动它？

**实际是**：本项目用自己注册的 usque 设备（`.warp/usque*/config.json`）走
MASQUE / WireGuard，与 `warp-svc` 是两套独立身份。启动 `warp-svc` 会抢占
WARP 会话身份，导致所有隧道互相踢下线。

**禁止**：`start` / `enable` / `unmask` / 修改其设置。

## 五、换线与守护的边界

### 18. 轮回守护只管节点，不管出口 IP 好不好

**看起来像**：这条线的出口 IP 一直在被限流，守护怎么不管？

**实际是**：职责严格分开：

| 守护 | 管什么 | 判据 |
|---|---|---|
| **同块轮回**（`_node_rotation_pass`） | 节点还能不能跑起 WARP | 这条线拿不拿得到出口地址 |
| **探测器**（`prober`） | 出口 IP 好不好 | 模型层实测 verdict |
| **换线**（`reconnect_warp`） | 哪条线当当前出口 | 新鲜 OK + IP 分级 |

出口 IP 被限流是**换线 / 重启换地址**该解决的，换节点救不了 —— 换个节点
照样可能落在同一个被烧的地址池。

---

### 19. 只有当前出口（active）那条线不动

**看起来像**：这条线也坏了，为什么不换？

**实际是**：换节点要重启，会**掐断正在传的流量**（客户端收到
`upstream connection lost`）。当前出口只走"换线"路径 —— 切到另一条已经健康的线，
秒级且不中断在途请求，被换下的那条再在后台慢慢修。

---

### 20. 多条线不能挤在同一个节点上

**看起来像**：这台节点表现不错，多用几条线吧？

**实际是**：那是把分散风险变成集中风险。那台节点的 UDP 一挂，几条线一起死。
`_same_block_standby` 会跳过已被其他线绑着的节点
（实测踩过：一轮误换后 WG-1/WG-2 同时绑 `cn.bing.com~13`、WG-8/WG-9 同时绑
`pq.aws48`）。

---

### 20b. 轮换候选必须按「实测能不能承载 WARP」排序，块序不是判据

**看起来像**：`rotation` 列表已经按「同块优先」排好了，照着取第一个可达的就行。

**实际是**：`rotation` 是 `warp_wg.apply()` 那一刻按**延迟**（`order_nodes`）
生成的，之后不再重建 —— 它反映的是「当时哪台网络快」，不是「哪台能跑 WARP」。
实测 2026-11-04：22 条 WG 线的 176 个 rotation 槽位里 **135 个（77%）从没有过
WG 实测记录**；块内实测可用的节点被 rotation 覆盖的比例：NRT 14 台里只覆盖 1 台
（7%）、SIN 11 台里 0 台（0%）、LAX 8 台里 1 台（12%）。

后果是轮换在赌：WG-1 在两个 `wg=0/4` 的节点之间来回换了 12 次，每次都是
「节点 TCP 通但拿不到出口地址」；39 次同块轮换里 5 分钟内拿到出口的只有
15 次（38%）。

**处置**：`_warp_alive_rank()` 给候选分三档 —— 0 实测能承载 / 1 从没测过 /
2 实测不能。**只排序、不淘汰**（节点会恢复；剔除会让新加的、还没跑过 diag 的
节点永远上不了线）。同块/跨块顺序先定，再在同档内保持原序（稳定排序）。
`_channel_rehome_target()` 与 `_same_block_standby()` 两处共用同一个键。

`family=None`（换线目标先于线号确定）时两族都要看：已测的族**全部**失败
才算 rank 2。实测两族都测过的 5 台节点里 0 台出现「v6 死但 v4 活」或反向，
跨族兜底不会把能用的判死。

**残留问题（未修）**：`rotation` 本身仍只在 `apply()` 时生成，不会自己变新鲜。
修好排序只能保证「在已有的 8 个候选里挑对」，不能把块里另外 13 台可用节点
拉进候选池。

---

### 20c. 渠道锁的目标节点落在死节点上时，重启永不收敛

**看起来像**：`ban_hold_ready=0` 就再重启一次，这是「重启没成功就重试」的正常逻辑。

**实际是**：它只在**节点能出出口**时才收敛。实测 WG-1 被锁到
`cn.bing.com:443~13-any`（`wg=0/4`，节点收 TCP 不转发 UDP:2408）后，
每次重启都拿不到出口 → `ban_hold_ready` 永远写不进去 → 每分钟重定位一次。
近 30 分钟 119 次「渠道重定位」重启里它占 71 次（WG-22 占 47 次，同因）。

**处置**：`ban_hold_node` 的承载能力是 rank 2（实测不能）时，不再原地重启，
改投另一个通过承载能力排序的节点（`_channel_rehome_target`）。
**只有 rank 2 才改投** —— rank 1 是「没测过」，那正是待验证状态，不该因为
没数据就搬走。

实测改投后 WG-1 立刻拿到出口（`pq.aws63`，`2a09:bac5:55fa:25cd::3c4:53`），
重启次数从 71 次/30min 降到 1 次/h，`ban_hold_ready` 正常置位。

### 20d. `ban_probes` 落盘是游程，不是逐条样本

**看起来像**：状态表里 `ban_probes` 应该是 `[(ts, verdict), ...]`，报表直接遍历。

**实际是**：daemon 存的是**段** `[起, 止, 条数, 结论]`。判据只问「当天是否
全部 quota」，条数不丢，丢的是重复时间戳 —— 实测 19k 条样本里只有 484 段
连续同结论，压缩 39 倍（526 KB → 14 KB）。

WHY 必须压：探测是秒级写入，状态表按 5s 节流落盘。不压之前整个文件 565 KB，
**9.4 GB/天** 的磁盘写；压完 62 KB / 1.0 GB/天。不能改成按条数截断 ——
主人 2026-11-04 明确要求「ban_probes 得留多点」，截断会把排查用的时序丢掉。

两个格式都认（旧的两元组读进来会在 `_channel_ban_trim` 里就地压成段）；
结论在 **e[3]**，不是 e[1]（e[1] 是段尾时间戳）。读侧用
`_channel_ban_expand()`（daemon）或 `_expand_ban_probes()`（`tools/channel_report.py`）。

### 20e. 补位渠道永不被渠道锁

**看起来像**：所有线一视同仁，连续 5h 拿不到出口地址就锁。

**实际是**：补位渠道必须排除。它的意义就是「顶替一条被封的线」，锁住它等于
让被顶的那条线整夜没人补位。实测 2026-11-04：补位线 WG-23/24/25 被锁到
`ban_hold_until` 剩余约 **57 年**，当天三条 H2 线（SLC-11/12、NRT-13）整夜
没有补位。`_channel_ban_note` 的 quota 分支早就有这道跳过，`_channel_noaddr_note`
（连续无地址）漏了 —— 两条判据都要挡。

补位线坏了由 `_backfill_open` 重开，不需要用锁把它冻住。

## 六、状态字段的语义（最容易误用）

### 21. `last_ok_ts` ≠ "隧道通"

它在 `verdict=blocked/quota` 时被清零。含义是"这条线的出口 IP 最近没有
成功服务过"，**不是**"隧道建不起来"。

### 21b. `last_ok_ts` 只发给**当前出口**，且每次重启清零 —— 它奖励的是「一直在服务的那条」

两个事实叠加：

1. `last_ok_ts` 的唯一写入者是 `_record_active_ip_success`，它只给
   `_ACTIVE_WARP_IP` 记账 —— **备线服务得再好也拿不到**。
2. `_warp_line_restart` 拿到新地址后写 `st["last_ok_ts"] = 0.0`
   （`daemon.py:5097`，同类清零另有 6 处），旧地址的成功不能继承给新地址。

于是「有生产成功记录」在台账里极其稀有：全天 37 553 个出口地址中只有 **61 个**
（CF 22 / WG 13 / H2 26），占比 0.1~0.5%。而档 1 又**没有时效上限**，这 61 个
地址里仍在线的那些可以长期垄断选线权。

**注意这不是「H2 重启太频繁所以拿不到」**：实测每线重启间隔中位 H2 17s、
WG 11s、CF 17s —— WG 反而重启得最勤。真正的差别是「谁一直在当出口」：当选的
线不被重启（活动线只换不重连），于是持续服务、保住 `last_ok_ts`、继续当选；
落选的线被探测器按脏地址反复重启，每次都丢掉 `last_ok_ts`。

实测 2026-11-05：13:00 那一小时的 34 次换线全部由 16 条「当时正处在 1~6 小时
不间断 OK 段」的线拿下，而池里平均有 8.1 条新鲜 H2 候选、H2 被选中 0 次。
全天校准（实际选中次数 ÷ 按候选占比算的期望）H2 为 **0.69**，13:00 为 **0**。

**这不是 bug，是排序键的已知偏置**；是否修正见
[analysis-20261105-h2-selection-bias.md](analysis-20261105-h2-selection-bias.md)。
修的时候**不要**改成让探针 OK 写 `last_ok_ts` —— 那是另一种反例（见第 23b 条
与 `daemon.py:6463` 的论证）。

### 22. `ip` = "隧道真建起来了"

只在真正拿到 WARP 出口地址时才写入。这才是判断"节点能不能承载 WARP"的依据。

**但注意**：`_invalidate_warp_line_ip` 会在**每次隧道重启**时清空它，
所以重启后的线必然 `ip=None` —— 这期间不能判死（见第 11 条）。
另外 daemon 启动加载状态表时，`last_ok_ts` 过期的条目连 `ip` 一起清，
否则陈旧的 `ip` 会让守护以为死线还有出口。

### 23. `verdict` 说的是地址，不是线路

`OK` / `quota` / `flagged` / `unreachable` / `err` 描述的是**这个出口地址**
在模型层的表现。线路本身通不通，要看 `ip` 有没有值。

### 23b. 状态字段只能由「产生这个结论的那条路径」写

**看起来像**：2026-11-05 15:40 用户报「节点全部不可用」，`asip chan` 上
33/78 条线同时显示 `unknown`，看起来探测器根本没在跑。

**实际是**：探测一直在跑。同一时刻实测 —— 20 秒内 42 条线的
`last_probe_ts` 全在推进，30 分钟产生 1459 条模型层结论，平均每条线
30~50 次。拿 daemon 自己的 `warp_egress_ip()` 手动打 4 条「unknown」线，
1.4~4.5 秒全部拿到出口 IP。

坏的是 `last_verdict` 这个字段：`_warp_line_restart` 的成功分支在拿到地址后
写了 `st["last_verdict"] = "unknown"`（a377b4b 引入，2cd6845 重写这段 if/else
时原样留下）。`unknown` 的语义是「探测跑完但没拿到出口 IP」，而这条路径刚
拿到地址、只是还没做模型层探测 —— **用失败的词覆盖了一个未被证伪的结论**。
重启是 5~15s 一次的高频动作，于是这个字段约有一半时间显示假失败态。

**判据**：一个状态字段被 A 路径高频写、被 B 路径低频写、只被报表读 ——
A 写的值必须与 A 掌握的事实同级。A 只知道「我有地址了」，就不能写任何
关于模型层的词。没结论就不写，让上一条结论留着（它的时效由
`ip_ts` / `last_probe_ts` 的先后关系表达）。

**同类的第二个入口**：报表。`print_table` 早就有「窗口内零样本 → 印
`无样本`」的保护，`render_html` 漏了同一层判断，同一份数据两个视图给出
不同结论。两处现在同口径，`test_stale_verdict_is_not_printed_as_current`
锁住。

**排查这类问题的顺序**（别再从头查一遍）：
1. 先证明探测在跑：取两次 `last_probe_ts`，看是否推进（20 秒足够）。
2. 再证明链路通：`daemon.warp_egress_ip(port)` 手工打一条，看花多久、返回什么。
3. 最后才看字段值 —— 且要问「这个词是谁写的、它当时知道什么」。

### 23c. 校验脚本「永远报未找到」= 校验不存在

**看起来像**：`python3 probe_warp.py --check-fingerprint` 一直打印
`✗ 未找到 9router 源码: ~/.9router/open-sse/utils/opencodeFingerprint.js`。

**实际是**：`db_path` 在 `<数据目录>/db/data.sqlite`，`dirname` 拿到的是
**数据目录**；而源码树在 `~/9router/`，`~/.9router/` 里只有 auth/db/logs。
旧代码拼出 `~/.9router/open-sse/...`，永远命中不了，然后 `return 1` ——
而这个命令**没有任何调用方**，返回值没人看。整条指纹漂移检测等于不存在。

这类「唯一的用途就是报警、但报警被吞掉」的脚本，验收标准不是「它能跑」，
而是「把源码改一个字节，它必须变红」。已按候选列表修（env → `~/9router`
→ `~/.9router`），并实测两边逐字一致。

**顺带**：`ENV_WORKING_DIR` 原来写死 `/home/administrator/.9router`，
`test_portability.py` 因此长期红着。源码里写明路径**不是门控项**（上游只认
`<env>` 标记存在），所以按 `~` 推导即可，不必绑死某个用户名。

### 23d. 撞到长 Retry-After 不再冷却该线（1800s 隔离已删除）

**看起来像**：「这个地址的额度到 UTC 零点才恢复，先把这条线停 30 分钟再去
抽别的地址，不然白烧。」

**实际是**：2026-11-05 主人要求删掉。原因是这条推理的前提不成立 —— 它假设
「重启只会拿回同一个已烧的地址」，而实测重启换的是新 /64、新 /128，配额
跟着新地址走（见第 3 条）。1800s 冷却的唯一效果是在池子最脏的时候把线撤出
战场，而这恰恰是该多换几次的时候。

**删的是代码，不是开关**：`_warp_line_quarantined` / `_quarantine_line` /
比例闸 / 四个调用点 / `config.py` 里四个 `line_quota_quarantine_*` 全部移除，
`test_ha_quarantine.py` 整份删除。状态表里的 `quota_until` / `quota_ip`
由 `_drop_legacy_quarantine_locked` 在加载时清零，免得旧字段被报表当成还在
生效。

**仍然存在的是地址级的惩罚期**（`.warp_ip_used.json` 的 `blocked_ts_by_kind`
与 `ban_until`）：那不是冷却线路，是「这个地址已经烧了」的记账，作用于
**地址**而非线 —— 换到新地址立刻不受影响。两者的区别就是第 23 条说的
「结论说的是地址还是线路」。全局 `quota_hold_enabled` 是另一把闸（账号级
配额窗口），本来就关着，未改动。

### 23e. 出口探测的三种失败必须在台账里分开：`rc` 混装了两次

**看起来像**：`asip chan` 上一批线显示 `unknown`，手工 `curl --proxy` 打过去
`warp=on` 一切正常，于是怀疑探测逻辑算错了结论。

**实际是**：`probe_egress` 把三种性质完全不同的失败压成了同一个 `rc`。

| curl 退出码 | 真实含义 | 该做什么 |
|---|---|---|
| 28 | **超时**（`--max-time` 到点自己退出） | 隧道半死，重启能救 |
| 7 | 连接被拒（端口没监听） | 进程没了，systemd 的活 |
| 22 / 6 | HTTP 错误 / DNS 失败 | 该换节点 |

关键陷阱：`probe_egress` 给 curl 传 `--max-time N`，curl 会在第 N 秒以
**退出码 28** 自己结束，于是 `proc.timed_out`（进程级，N+5s）**永远轮不到**，
所有超时都落进 `if proc.code != 0: note("rc")`。实测 2026-11-05 远端 20 条线
6009ms 超时全记成 `rc`，与「端口没监听的 6ms `rc`」在台账里毫无区别。

判据：**一个错误分类如果同时覆盖「网络挂了」和「服务端拒绝」，它就没有
诊断价值**。28 现在单独记 `timeout`（`asip/egress.py`）。

### 23f. `unreachable` 触发的是**节点轮换**，不是无效重启

**看起来像**：链路抖动导致模型探测超时 → `unreachable` → 判低质 → 重启，
应该拦掉，否则把抖动当成了故障。

**实际是**：`unreachable` 的消费路径不是「重启同一条隧道」：

```
probe → unreachable
  → _probe_cache_put（结论进缓存）
  → _warp_ip_needs_refresh → True
  → _prewarm_standby_warp / _ip_disqualified
  → 重生隧道 → _node_rotation_pass 换**同块的另一个节点**
```

而「节点转发不了流量」正是 `unreachable` 的典型成因 —— 换节点是对症的，
不是空转。`test_stale_unreachable_still_restarts_when_channel_healthy`
（8fbc7e0，2026-10-26）锁的就是这个语义，别当 bug 改掉。

**但要注意一个真实的边界**：把 `refresh_model_timeout_sec` 从 15s 提到 30s
（2026-11-05，依据是 15s 下同端口连续 6 次全超时、手工探测却 `warp=on` 正常）
会让超时线多占并发槽位。`model_probe_concurrency` 是 32，一轮最坏 30s，
仍在 `node_rotation_interval_sec`(60s) 之内，不阻塞轮换 —— 提这个值之前先
核这两个数。

### 23g. 「探测不出 OK」先看端口有没有在监听，别先怀疑探测逻辑

**看起来像**：`unknown` 大面积出现，怀疑探测器坏了。

**实际是**：先花 1ms 查 `_port_open`，能省掉 20 秒白等。

实测 2026-11-05 本机 41 条在册线里 5 条（CF-C/G/H/I、WG-23）的 systemd 单元
早就没了（`is-enabled` 返回 `not-found`），但 `config.py` 的 members 里仍声明
着，于是每轮探测都对一个没人监听的端口等满 20 秒超时 —— 一轮并发预算被吃掉
四分之一。现在 `_probe_one_line` 在探测**之前**判端口，端口关着直接记
`port_closed` 并返回：**结论记 `port_closed` 而不是 `unknown`**，且不进
`fail_streak`（进程没了不是线的健康问题）。

配套的报表口径：窗口内零样本的线，`last_verdict` 是**旧值**，不能当当前状态
打印（CLI 表与 HTML 同一口径，`test_stale_verdict_is_not_printed_as_current`
锁住）。

### 24. 两台机器的 429 率不同，先怀疑池子，不要先怀疑部署

**看起来像**：云端 429 率 32%、本地 13%，同一套代码、同一批节点、同一个
`config.py` —— 一定是云端哪里没配好。

**实际是**：429 是**上游按出口 IP** 判的，两台机器各自从共享池里抽地址，
抽到的样本不同，429 率就不同。实测同一时刻：

| 探针 | 本地 | 云端 |
|---|---|---|
| 经 `7890`（各自当前出口）连打 12 条 | 12/12 429 | 12/12 429 |
| 经 PIT 落地（1189）连打 6 条 | 6/6 429 | 6/6 429 |

**完全相同**。差异只出现在「这一分钟里谁撞到了干净地址」这种抽样噪声上。

**判断顺序**（2026-11-03 凌晨实测走过一遍）：
1. 先在同一时刻、同一端口上做**对照实验**（见上表）。两边一致 → 不是部署问题。
2. 再看「新鲜备线数」。`_warp_line_fresh_candidates` 要求
   `last_ok_ts` 在 `line_fresh_sec`（120s）内 —— 深夜模型层几乎全是 quota，
   这个数经常是 **0**，于是换线只能反复空转（实测云端 68 次尝试成功 6 次）。
   这不是换线逻辑坏了，是**没有合格候选**。
3. 最后才查配置差异。实测云端与本地 `config.py` 的
   `line_fresh_sec` / `switch_wait_sec` / 探测并发全部逐项相同。

**为什么这条重要**：把池子的抽样噪声当成部署缺陷，会去改本来正确的参数，
把本地也一起改坏。第 0 条说的就是这个池子的宏观规律，本条说的是**单次观测**
上的同类陷阱。

### 25. `fail_streak` 只数「拿不到出口地址」，不数「地址被封」

**看起来像**：`WARP-WG-17 连续 2457 次取不到出口地址` —— 这条隧道彻底坏了。

**实际是**：它每次都拿到了出口地址（`2a09:bac5:6369:...`），每次被判
`quota`。`fail_streak` 曾经在 `verdict != "OK"` 时**无条件累加**，于是
quota / blocked / unknown 一视同仁地往上加。

它的唯一消费点是重启判据「连续 N 次取不到出口地址 且 端口还开着 → 隧道
半死」。**quota 说明隧道完全正常**，把健康线路当半死线路重启，还有一层后果：
真正「取不到地址」的故障被这堆噪声埋掉。

2026-11-03 已改为只在 `unknown` 时累加。看到这条日志先查该线最近一次
`模型层:` 结论——是 `quota` 就说明地址被封，不是隧道坏。

### 25b. 重启循环会把唯一能救它的机制顶在门外

**看起来像**：WG-4 每 ~60s 重启一次、`fail_streak` 一路涨，说明重启策略在
正常工作，再等等就好。

**实际是**：重启**没有**救它，而且它让轮回来不了。同块轮回的冷静期判据是
`now - max(rebind_ts, restart_ts) < 2×60s` —— 每次都刷新 `restart_ts` 的
重启循环，等于永远把轮回挡在门外。实测 2026-11-05 WG-4 `fail_streak` 41、
`ever_ip` 始终 False、每 ~60s 重启一次，而轮回日志里从没出现过它。

**判据：`ever_ip` 为假的线，重启没有意义。** `ever_ip` 与 `ip` 不同 ——
`_invalidate_warp_line_ip` 每次隧道重启都会清 `ip`，拿它判会把刚重启的正常
线也判死；`ever_ip` 只置位、不清，回答的是「这条线在本进程里成功出过口吗」。
没出过口就说明问题在节点或链路，换个 /128 救不了，得换节点。

两处重启入口（惩罚期、连续无出口）现在都先问 `_line_node_cannot_carry`。
**新增重启入口时必须挂同一道闸**，否则同一条线会从新入口漏过去。

顺带：`probe_node_tcp` 的 recv 超时现在返回 `False` 而不是抛异常 —— 超时
正是「接了本地端口却不转发」，是结论不是故障。之前它会冒到
`_node_rotation_pass` 外面，整轮轮回作废，一条坏节点拖住所有线（3h 18 次）。

**H2 线查的是另一个集合（`_H2_POOL_DEAD`）**：H2 的落地节点在共享 sing-box
的 selector 里，`warp_wg` 台账根本没有它们，查台账永远 `node=None` —— 整段
判据对 H2 从来没生效过。实测 2026-11-05 SLC-11/12/24 的 4 个候选 TCP 全死、
`ever_ip` 始终 False，仍每 ~2 分钟重启一次 `usque-h2-N`，`fail_streak` 涨到
1612。判据复用 `_h2_repair` 自己的结论（整池试遍换不出去 → 记进集合），
热路径上只读集合不打 Clash API；换到节点或拿到出口地址即清空。

**第一版只降频，不归零 —— 别把「加上闸」当成「循环没了」。** 这是本轮最容易
骗过自己的一处：05:57 加闸后 17 分钟内日志里再没有 SLC 的重启行，看起来收敛
了，实际是 `daemon.log` 被轮转清空。跨 `daemon.log.1` 重算 06:00 后：

| 线 | 重启次数 | 按小时 | 换节点后 180s 内 | 平均间隔 |
|---|---|---|---|---|
| SLC-12 | 44 | 09:13 10:11 11:13 12:7 | **44/44 (100%)** | 28s |
| SLC-11 | 53 | 09:16 10:8 11:15 12:13 | **53/53 (100%)** | 30s |
| SLC-24 | 42 | 09:8 10:15 11:11 12:8 | **42/42 (100%)** | 26s |

**全部重启都紧跟在换节点之后**，机制是：

```
16:58 ⇄ 换节点成功   → _H2_POOL_DEAD.pop(tag)  判死被清掉
16:59 ↻ 重启         → _NODE_NEXT_CHECK 把 _h2_repair 挡 60s，
                        闸看到 tag not in _H2_POOL_DEAD ⇒ 放行重启
17:38 ✗ 重启后出口=探测失败
17:58 ↻ 重启         （60s 节流到点前，_h2_repair 仍返回 False）
18:58 ⇄ 换节点        （节流到点，池子又走一个，回到第一行）
```

**换节点成功那一刻把「暂停重启」的许可也一起作废了**，而新节点要 ~40s 才
拿得到出口 —— 新节点从没被探测过就被掐掉。

**已修（判据分两段，先看出没出过口）**：

```python
st = _warp_line_state(tag)
if not bool(st.get("ever_ip")) and st.get("last_probe_ts"):
    return True          # 从没出过口：问题在节点/链路，重启换的是同一节点的新会话
return tag in _H2_POOL_DEAD   # 出过口：更可能是本机会话僵死，只有整池试遍才判死
```

`last_probe_ts` 那半个条件是必须的：刚 apply 完还没人探过的线，`ever_ip` 也是
假，但那是「还没看过」不是「看了不行」。

**不要改成 `bool(_H2_TRIED[tag])` 判死** —— 那样「池子重渲染后换得出去」的
自愈路径会被一起判死，`test_h2_exhausted_pool_stops_the_restart_loop` 里
「多出一个新节点 → 换得出去、判死解除」那段就是为它写的。

**同一天的实测口径（2026-11-05 05:23~05:40，17 分钟）**，用来分清「循环是
代码问题还是池子问题」：

| 指标 | 数值 |
|---|---|
| 重启 | 1491 次 |
| 轮回换到（节点） | 7 次 |
| 其中「出口处于惩罚期」 | 1092 次 |
| 其中「模型层 quota」 | 372 次 |
| 其中「连续 N 次取不到出口」 | 15 次（全是上面那三条 SLC 与 WG-2） |

**轮回已经在工作，但它救不了**：同一窗口内 WG-4 拿到出口 341 次、216 个不同
地址，**全新地址 0 个**；按落点 colo 归因，NRT 1254 个样本 / PHX 363 / SIN 46
**100% 都已在该台账里被 403/429 标脏**。台账全量：151 个 /48 里 112 个
（≥20 样本的）仍封禁率 ≥95%。所以「换节点」这一手在 08:00 前也换不到干净
池子 —— 是池子枯了，不是换得不够勤。

**已知未解**：同一晚 04:34:24 一条日志显示 WG-4 同块换到 `pq.aws50`，而
04:41:06 的探测行里节点已是 `downloadcfpro…~10-vl`，且 `home` 仍是 `pq.aws50`
（`apply()` 没跑过，状态文件 `updated` 停在 01:29）。`rebind()` 与
`_same_block_standby()` 都只能返回 `line["rotation"]` 里的值，而
`downloadcfpro` 不在 WG-4 的 rotation 里；`_rehome_held_lines` 的三条还原
日志在全天日志里 0 次命中。**仓库内没有任何写入者能产生这次回退**，怀疑是
带外写入（手工 `warp_wg.py apply/rebind` 或另一世代的 state 文件），未证实。

### 26. members 是**声明**，不等于单元在跑

**看起来像**：`config.py` 的 `warp.members` 里有 `WARP-CF-C`，那就该探它。

**实际是**：`usque-warp-c/g/h/i` 四条是 **inactive + disabled**（2026-10-28
缩容时把设备让给了 H2 线），但 members 里仍留着它们。prober 照样每秒探一次，
每次探不到出口，`fail_streak` 累积到 **22 万**：

| 线路 | fail_streak（修复前） |
|---|---|
| WARP-CF-C | 223495 |
| WARP-CF-G | 221635 |
| WARP-CF-H | 219682 |
| WARP-CF-I | 217025 |

本地同样有 14 万级别的计数，只是重启次数少还没刷满屏。

2026-11-03 起 prober 主循环用 `systemctl is-active` 过滤（带 60s 缓存——
单元启停是人工操作，不需要秒级感知；`is-active` 每次 5~15ms，每秒全量调用
会拖慢主循环）。查不到状态时按「在跑」处理，不能因为查询失败就停探。

**推论**：想让一条线彻底退出调度，光把它 disable 不够——还要从 members 里
删掉，或者靠这层过滤兜住。

### 26b. 一条线跑 v4 还是 v6，**只认配置声明**，状态表里的 `family` 可能是旧世代残留

**看起来像**：`.warp/warp_wg_state.json` 记着每条线的 `family`，那是
`warp_wg.apply()` 写进去的实际值，应该比 `config.py` 的声明更可信。

**实际是反过来的**：状态表的 `family` 只在 `apply()` 那一刻写一次，之后
**既不重建也不随配置更新**。改过拓扑的机器上它是上一代的残留值。

实测本机（2026-11-04）：`.env` 是 `WARP_WG_FAMILIES=v6`（22 节点 × 1 渠道，全 v6），
而 `.warp/warp_wg_state.json` 里 WG-1/2/3 还记着上一代 `v4,v6,v6,v6` 的 **v4**。
照状态表重写配置会把三条线全写成 `prefer_ipv4` —— 而 v4 出口**只由落地 colo
决定**，三条线实测立刻挤成同一个 `104.28.205.117`（第 27 条：v4 渠道数不应超过
colo 数）。正确的取值是 `member["family"]`，也就是 `WARP_WG_FAMILIES` 的声明；
`write_line(family=None)` 自身也按 `line_family(i)` 算，与 `apply()` 同源。

**误判过程（写下来防止再犯）**：看到状态表记 v4、配置文件记 `prefer_ipv6`，
先入为主地认为「配置被 bug 写坏了、状态表才是真相」，于是按状态表改配置 ——
把本来正确的 v6 改成了 v4，制造了那个「三条线撞同一出口」的现象。
**判据应该是 `WARP_WG_FAMILIES` 本身**，不是任何派生物。

**推论**：状态表的 `family` 只能当「上一次 apply 时的快照」看。任何按族做判断的
地方（`_warp_alive_rank` 选证据列、同块轮回的跨块优先）都取声明值。

### 26c. 部署的「覆盖」语义是错的：块表/探测台账是**累积知识**，不是配置

**看起来像**：`deploy/remote-deploy.sh` 的设计前提写着「拓扑以本机为准，远端只
复刻」，于是把本机的 `.warp/*.json` 整表覆盖过去是顺理成章的。

**实际是**：`.warp/block-map.json` 与 `.warp/h2_probe_state.json` **不是配置**，
是两台机器各自跑了多久探测就攒了多少的**实验结论**。daemon 每 15 分钟自动跑
`_run_h2_probe`，两台机器的时间线不同，覆盖面必然不同：

| | 本机 | 远端 |
|---|---|---|
| block-map 节点 | 174 | 181（独有 7） |
| H2 探测台账 | 38 条 / 12 ok | 156 条 / 78 ok |

覆盖 + 过滤的实测代价（2026-11-05 审计）：旧脚本先按**远端上一次部署的**
`singbox-config.json` 做白名单，而全新远端根本没这个文件 → `live` 为空 →
只剩入库的 65 条 dormant 快照 → 本机 174 条**删掉 130 条，其中 28 个 H2 落地
节点**。被删的远端此后不会自动加回：`warp_blocks.merge_diag()` 只给探测成功的
节点建档，而 `h2_probe_state.json` 又没传。更糟的是删掉了 `carrier: h2` 标记，
`warp_wg.apply()` 会把这些节点当 WG 落地 —— 拓扑直接分叉。

**正确语义**（现行实现）：
- block-map：**合并**，远端自己的观测优先（`merged = dict(mine); merged.update(cur)`）
- probe_state / pool_history：**合并**，远端优先、本机补缺
- `.sub_cache/`：只补不删（一次性链接失效后的唯一退路）
- `.extra_subscriptions`：**并集合并**，不是覆盖 —— 远端有 `jiashule` 是本机
  没有的，整文件覆盖会反向删源。它是拓扑输入，不是「每台机器自己的凭据」
- `h2/channels.json`：远端已有就**不覆盖** —— 它是本机产物台账，本机 31 条、
  远端 37 条，覆盖等于把远端砍到 31 条

**过滤器本身也不该存在**：它的原始理由是「远端没有 greatgame/dankenet 这两个
域名」，补源后已不成立；即便成立，`render_h2_lines.node_outbound()` 本来就会跳过
「不在主配置/沉睡池」的节点并打 warning —— 带着它们走渲染不出坏线，删掉却不可逆。

### 26d. 部署脚本漏了 `patch-wg-outbounds.py`，且渲染顺序反了

**看起来像**：步骤 5 写了 `parse_subscription → members.py → h2-install`，
看起来该有的都有。

**实际是**，两处让它变成半成品：

1. **缺 `patch-wg-outbounds.py`**。`members.py` 把新成员写进
   `warp-outbound.json`，但**没有任何人**把它们并进 `singbox-config.json` 的
   `opencode-out`。只能指望重启后那次隐式订阅刷新补上；刷新一失败就停在
   「单元全 active、`h2-sel-N` 全在、单条 SOCKS 能出 `warp=on`，但主 selector
   里一条新线都没有」（§20b/T-307 记的就是这个症状）。

2. **顺序反了**。`members.py` 跑在 `h2-install` **之前**，而 h2-install 会重新
   渲染并改写 `channels.json` —— `warp-outbound.json` 反映的是**上一轮**的台账。
   正确顺序与 daemon 的 `_run_h2_sync`（唯一被生产验证过的编排）一致：

   ```
   render_h2_lines.py（本用户）→ h2-install.sh --no-render
   → members.py --write-warp-outbound → patch-wg-outbounds.py → 重载主 sing-box
   ```

3. **`h2-install.sh` 不带 `--no-render` 时会以 root 重新渲染**，把 `.warp/h2/*`
   的属主改成 root；而且 `get_singbox_secret()` 按**当前 uid 的家目录**找
   `.singbox_secret`，实测 root 下读 `/root/.singbox_secret` 直接失败、返回空串
   → 渲染出的 Clash secret 为空 → daemon 每次 `PUT` 都 401。

4. **失败被管道吞掉**：`./h2-install.sh 2>&1 | tail -4` 返回的是 `tail` 的退出码，
   H2 渲染拒绝执行时脚本照样往下走，只在验收里显示 0 条。

5. **验收只报数字不比对**：旧版只印「成员 N 条」，`opencode-out` 少一半也看不出。
   现在比对盘上配置与**运行中** selector 的 tag 集合，并对每条 H2 台账端口做
   `warp=on` 端到端抽样。

**判读提示**：`remote-deploy.sh` 跑完后必须看 `✓ 运行中 selector 与盘上配置一致`
这一行。只有它绿，才说明「改了文件真的重载了」。

### 27. v4 线的出口数量上限 = 落地 colo 数

**看起来像**：开了 3 条 v4 线，应该有 3 个 v4 出口。

**实际是**：v4 地址由**落地 colo** 决定，同 colo 的多条线抽的是同一个小池子。
实测本地三条 v4 线（1110/1111/1112）全部落在 PHX，拿到**同一个**
`104.28.205.115`；云端同样是三条全 PHX，其中两条撞成 `104.28.205.117`。

所以 v4 渠道数**不应超过可用 colo 数**，否则多开的那几条只是在同一个池子里
重复抽签，白占设备槽位。

> 这条与 [architecture/ip-pools.md](architecture/ip-pools.md) §2 是同一事实的
> 两个侧面：那里讲地址池的收敛，这里讲它对**线路规划**的约束。

### 28. 「配置里没有 WARP 出口」是一份**合法**配置，探活发现不了

**看起来像**：`singbox=🟢`、Clash API 通、7890 能连、日志每小时「✓ 订阅刷新完毕」——
一切正常。

**实际是**：2026-11-03 远端丢了 3 小时 24 分的 WARP 出口，就是从这些绿灯里溜过去的。
链条：`warp-outbound.json` 属主被 sudo 部署写成 root → daemon 读不到 →
`parse_subscription.py` 打一行 stderr 后返回 `[]` → 生成一份**没有 `opencode-out`
selector、没有 opencode 路由规则**的配置 → `sing-box check` 通过（它确实合法）→
promote 上线 → opencode 流量静默落到 `final: proxy` 的机场池。

daemon 之后每次换线都是 `status=404`（实测 30362 条），而日志里没有任何一条
说明原因：那行 stderr 以 `WARP` 开头，被「只转发 ⚠ 开头的行」的过滤规则吃掉。

**现在有四道闸**（2026-11-03 起）：
1. `parse_subscription.py` 遇到**存在但读不了**直接 raise（缺文件仍放行）。
2. daemon 全量转发刷新 stderr（正常一轮只有 4 行以内，实测）。
3. watchdog 判 `opencode-out` 缺失/空/成员骤降 → 自动重建（失败按
   `(60, 120, 240, 480, 600)` 秒退避，成功即复位）。
4. `remote-deploy.sh` 显式传 `ASIP_RUN_USER` + 末尾统一 chown 兜底。

**判据的边界**：`_warp_selector_missing()` 只看**运行中**的 sing-box。文件读不了
但进程还在跑旧配置时它不会触发 —— 那是对的，真正的危险时刻是「坏配置被加载」。
2026-11-03 实测：剥掉全部 WARP 出口后让 sing-box 加载，watchdog 6 秒内发现并
重建完成（13:36:42 检测 → 13:36:44 让路 → 13:37:04 sing-box 重启成功）。

**重建必须走骤降护栏，不能直接跑 `parse_subscription.py`**：护栏是「新产出
< 上次基线的一半就拒绝覆盖」。自愈如果绕过它，就会把护栏刚判为可疑的那份产出
原样推上线 —— 2026-11-03 实测：自愈把 160 → 26 的产出直接落盘，池子从 94 掉到
26，而同一时刻定时刷新正被护栏拦着。

**重建的成败按「效果」判，不按「命令返回 0」**：产出带 WARP 但 sing-box 起不来
（端口被占、二进制坏了）时，下一轮 watchdog 照样看到 selector 缺失。按返回码
判成功会让 `_WARP_REBUILD_FAILS` 每轮清零、退避恒为 60s —— 每轮「成功」、
每轮修不好。所以重建后必须复查 `_warp_selector_missing()`，仍缺失就记失败。

同理 `_LAST_WARP_REBUILD_TS` 只在 `_submit_once` **真的提交了**才推进：
同名任务在跑时它返回 False，先记时间戳等于把这次尝试白记掉。

所以重建走 `refresh_subscription(reason=...)`，与定时刷新共用同一套护栏。唯一
让路条件是「线上配置**完全没有 WARP 出口**而新产出有」—— 护栏防的是把好池子
换成坏池子，这里是从「opencode 静默落机场池」换成「有小池子的可用配置」，
严格更好。其余情况（线上有 WARP、新产出反而更少）照旧拦。

**不要动**：不要因为「探活全绿」就下结论说出口正常。要看 `opencode-out` 在不在、
成员数是多少。

### 29. `proxy` 池的成员数是**动态**的，两台机器同刻可以差近 7 倍

**看起来像**：同一份代码、同一批订阅，云端 `proxy` 有 165 条、本地只有 25 条 ——
一定是本地哪里配坏了。

**实际是**：池成员 = **当前订阅节点** + **okz 沉睡池** − **实测判死的**。

三个部分逐一说明：

| 组成 | 本地实测 | 来源 |
|---|---|---|
| 当前订阅节点 | 62 | `okz` + `dasho`（两个源的可及性每天都在变） |
| **okz 沉睡池** | **57** | `dormant-outbounds.json` 的 65 条里，按 tag 去重后剩 56~57 条进池 |
| 实测判死 | 97 | `.dormant_state.json` 里 `alive:false` 的条目 |

**沉睡池具体是 `okz` 这个订阅**，不是某个单独的源。判据（2026-11-04 实测）：

- 65 条 = 55 条 `bilibili-image-cdn.juhazf.cn:50001–60194`（SNI 为 `*.okzdns.com`）
  + 10 条 `*-aws-N.acczzz.com:443`（SNI 为 `*.hi2026.net`），两个都是 okz 的域名
- tag 一律是 `host:port-any` / `-tr`，**没有 `~N` 后缀** —— 那是 `dasho` 那种
  「同一 host:port 挂多个节点」的源才需要的消歧后缀
- **它就是同一批节点的旧入口**，不是额外节点：okz 现在仍供这 63 个后端，只是
  入口域名从 `bilibili-image-cdn.juhazf.cn:<5xxxx>` 换成了 `cn.bing.com:443` /
  `us.bing.com:443`。按 (SNI, 协议) 对齐后 **63/63 的密码完全相同**；真正从
  订阅里消失的只有 2 条（`hk-aws-111` / `sg-aws-113`）。
- 所以沉睡池的价值是**备用入口**：bing 前置被墙时，旧的高位端口或许还能连。
  它不是「等节点复活」的墓地 —— 注释里那句「订阅源暂时不可用，等它复活」
  只是当初的设计意图，与实际用途不符。

**65 条里有 8~9 条与当前订阅同 tag**（都落在 `acczzz.com:443`），`make_config`
按 tag 去重后实际进池 **56~57** 条。具体几条取决于当天 okz 给哪些入口 ——
它每天在换，所以别把这个数当常量。

**沉睡池不是自动生成的**：`dormant-outbounds.json` 2026-10-28 15:52 手工固化后
再没变过（`git log` 里只有 `2e1b596` 一次提交）。okz 再换入口也不会自动补进来。

判死表则由 `dormant-probe.timer` 各自独立写，两台机器的探测结果和运行时刻都不同：

| | 订阅节点 | okz 沉睡池 | 判死摘出 | 在池 |
|---|---|---|---|---|
| 本地 | 62 | 57 | **97** | **25** |
| 远端 | 109 | 56 | **0** | **165** |

（数字取自各自的 `singbox-config.json.stats.json`，2026-11-03 实测。）

**这只是一张切片，不是规格**：同一台本地机器 11-04 再取就是
`138 / 56 / 71 / 123` —— 订阅源当天多活了 76 条，判死数也跟着变。
`stats.json` 里四个数每天都在动，唯一稳定的是它们**互不相等**这个事实。

本地那份 `.dormant_state.json` 里 97 条 `alive:false`；远端**根本没有这个文件**
（该 timer 装了但没产出），于是全量留在池里 —— 这是 25 vs 165 的全部原因。
远端订阅节点还多出 47 条（109 vs 62），那是 `dasho` 源在两台机器上的可及性不同，
与沉睡池无关。

**别把 `dormant_state.json` 的条目数当池子大小**：11-04 实测它有 **194** 条记录，
而当时池子只有 123 条。状态表比订阅活得久 —— 节点下架后 `alive:false` 记录仍在，
只是摘它不再改变任何东西（见 [reference/state-files.md](reference/state-files.md) §六）。

**为什么这不算故障**：`dormant-probe.service` 最近一轮实测「通 3 / 101」——
机场池当时确实大面积不通。判死把它们摘出池子是**正确**行为，否则 daemon 每轮
都在「撞死节点 → 标死 30 秒 → 再撞」之间空转（`parse_subscription.py:824` 的注释）。

**推论**：

- 不要把某个时刻的池子成员数写进文档/报警阈值 —— 它随订阅、时段、探测结果变。
  需要看就现查：`python3 -c "import json;..."` 或 Clash API `/proxies/proxy`。
- 两台机器池子大小不同**不是**部署问题，与第 24 条（429 率不同先怀疑池子）同源。
- 想让本地池子变大，先确认节点真的活着再把 `.dormant_state.json` 里对应条目
  改回 `alive:true`；直接删文件等于「把判死的节点又放回来」，静默做就是骗人。

## 八、渠道报表（tools/channel_report.py）的口径

**看起来像**：H2 线全是「成功率 —、样本 0、重启 0」，是不是报表坏了？

**实际是**：报表只统计 **daemon 的模型层实测样本**（`.warp_line_state.json`
的 `ban_probes`）。H2 线要走到模型层探测，先得 `warp_egress_ip()` 拿到出口
地址；H2 隧道拿不到地址时不产生样本，于是成功率留空、只有 `ban_noaddr_since`
在涨。这时看 **colo ban 列** —— 它是 `.warp_ip_history.jsonl` 里该机房全部
出口的封禁率，与渠道是否存在样本无关。两者不可互换：
- 渠道成功率 = 该条线自己探过几次、成了几次（有样本才有值）
- colo ban = 整个机房这段时间换出去多少个地址、多少被烧（一直有值）

**「重启」列显示 0 不代表没重启过**：它只数**窗口内**的 `restart_hist`。
H2 线的 `restart_count` 终身累计是 531~2411（2026-11-04 实测），但它们的
`restart_hist` 在 daemon 启动时被整表清空（`_load_line_state` 的注释：
重启是人工动作，不该继承重启前的小时预算），此后探测器没重启过它们
（拿不到地址 → 不产生样本 → 不进重启判定）。要读终身次数看
`restart_count`，要读「最近这段时间折腾了多少」看这一列。

**看起来像**：「出口段」列里 WG-16 是 `2/25/175/909`、WG-21 是 `2/51/191/1697 +3v` —— 同一个机房的线，/48 差一倍？

**实际是**：四个数分别是 **/32 批次 / /48 池子 / /64 抽签次数 / /128 地址数**。没有一个
是「机房池子有多大」—— 池子是共享的，同一时刻所有线在同一个池里抽签。
WG-21 的 /48 是 WG-16 的两倍，是**长期覆盖**的差别（这两条线的终身
`restart_count` 已接近 3800/3800，窗口内重启 59/62 次），不是「最近谁更勤」。
它回答的是「这条线跑过多少地方」，不是「还剩多少干净段」—— 后者看 colo ban 列。

**/64 和 /128 必须并肩看，缺一个都会读错**：`/64` 是抽签结果（每次会话
拿到一个 /64），`/128` 是真正被计费的单个地址（opencode 免费配额按地址扣，
不按段）。两者接近（`2/12/60/1035` → 平均每 /64 17 个地址）说明地址是摊开的；
`2/12/12/178`（NRT 线）说明 178 个地址挤在 12 个 /64 里 —— 前者撞的是池子，
后者撞的是「同一个 /64 里刚被烧过的邻居地址」。NRT 的 /128 级 5 分钟重复率
36.1%，SIN 只有 0.7%（2026-11-04 18:40 实测），差别全在这一列。

**看 /32，不看 /64**：一条线能有 191 个 /64、1697 个 /128，读不出规模；
`/48` 也有 51 个。只有 `/32`（Cloudflare 的地址批次，实测全场只有
`bac1` / `bac5` 两批）是一眼能读的规模。所以表格列写
`/32个数//48个数//64个数//128个数`（`2/12/60/1035`）。

**明细表按声明 colo 分组合并，不按渠道逐条印**：同一 colo 的各条线共用
同一个池子，段重叠度极高。逐条印出来是 50 多行几乎一样的文本，真正不同的
信息只有「哪条线在哪个 colo」—— 那已经写在主表的 colo 列了。实测合并后
SIN 的 /48 从 325 降到 92（省 72%）、/64 从 1721 降到 333（省 81%）；
NRT 的 /48 从 297 降到 44（省 85%）。所以明细表每个 colo 一行：
`出口段 32/48/64/128` + `池 48/64/128` + `指纹落点` + /32 细分 + 成员渠道 tag。
要看**单条线自己**的覆盖面，看主表那四个数。

**出口段、池、指纹同表，因为它们同维度**：三者都是按 colo 归的 ——
出口段是这组线落过哪些段，指纹是这些段反推的落地机房分布，池是指纹
归到该机房的三级去重个数。拆成两张表会让人以为它们是两件事。

**别把 /64 个数读成覆盖面**：`2/51/191/1697` 说的是「跨 2 个批次、51 个池子、
抽了 191 个 /64、见过 1697 个地址」，不是「覆盖了 1697 个地方」（同一 /64
里的地址邻居是同一个池子里的）。四级混成一个数一定会读错。

**这一列不按时间窗口截断**：段列表是「这条线去过哪些地方」，不是随时间衰减
的健康指标。按 6h 窗看时 H2 线全是 0 段 —— 它们的出口日志停在 11-03
（之后一直 `无地址`），会看起来像「从没出去过」。**显示的段因此可能比窗口
更旧**：这是设计，不是缓存没刷新。

**看起来像**：明细里 NRT 的池是 `12/12/1184`，SIN 是 `12/132/9731` —— /48 一样多，池子一样大？

**实际是**：`池` 列是 `/48 / /64 / /128` 三级**去重后**的个数（全日志合并，
含已下线的 tag —— 池子是机房属性，不随成员表缩水）。NRT 的 12 个 /48
底下只有 **12 个 /64**（每个 /48 恰好 1 个），SIN 的 12 个 /48 底下有 132 个。
而 NRT 上挂着 10 条渠道、SIN 上挂着 12 条 —— 只看 /48 会得出「两个机房一样
宽」，实际 NRT 的 /128 级 5 分钟重复率 **36.1%**（427/1184）、SIN 只有
**0.7%**（66/9732，2026-11-04 18:40 实测）。这个差异只在 /64 那一级显形；
`/128` 是被 opencode 计费的单位，所以第三个池数才是「真正可抽多少地址」的近似。

**`池` 的 /48 由它下面的 /64 决定，不是 `colo_of(/48)`**：`bac1:7680/76a0/
76c0/76e0` 是 PHX 与 SJC **共用**的段，`colo_of(/48)` 恒判 PHX。按 /48 归会
把 `:28` 那批 SJC 的 /64 记到 PHX 名下、同时让 SJC 的 /48 少算 4 个
（旧口径 SJC `8/52/…`，实际 `12/52/…`）。三级必须嵌套（/48 ⊇ /64 ⊇ /128）。

**段重叠是设计使然，不是故障**：51 条渠道共用 117 个 /48，只有 5 个 /48
只被一条渠道走过（4 个还是 `colo_of()` 没规则的 SLC/ICN 段，1 个是 ICN 的
`bac5:4752`），46 个 /48 被 ≥10 条渠道共用。同一 colo 内重叠到什么程度：
SIN 的 12 条线合并后 /48 从 325 降到 92（省 72%）、/64 从 1721 降到 333
（省 81%）；NRT 的 9 条有段线 /48 从 297 降到 44（省 85%）。真正有代价的
重叠只在 /128 层 —— 就是上一段的重复率。各 colo 的池子明细见
[architecture/ip-pools.md](architecture/ip-pools.md) 第三节。

`ICN` / `SLC` 的池是 `—` 不是 0：`ipv6_segments.colo_of()` 里没有
`bac1:3f40`（ICN）、`bac5:a538/a53b/a53c`（SLC）的规则，落进 `UNKNOWN`。
这是指纹规则表的缺口，不是这几条线没出过口 —— 它们的指纹分布行照样有数
（`≠UNKNOWN 100%`）。补规则要动 `ipv6_segments.py`，报表侧不做猜测。

数据来源只能是日志：`.warp_ip_history.jsonl` 的字段是 `ip/t/b/k`，**没有渠道
归属**（唯一写入点 `_mark_warp_ip_used()` 拿到的就只有地址）。带归属的是 daemon
的那两类出口行（`出口 <ip> 模型层` / `重启后出口=<ip>`），所以这一列靠
`channel_segments()` 现算。**日志被轮转清掉的部分就统计不到** —— 显示 `—`
（不是 `0`）表示日志里没见过它的出口，不是「它只有一段」。

**看起来像**：订阅源那列有时是 `okz（旧入口快照）`。

**实际是**：这个 tag 不在当前订阅里，只存在于 `dormant-outbounds.json`。
**沉睡池全部来自 `okz` 一个订阅**：65 条 = 55 条 `bilibili-image-cdn.juhazf.cn`
高位端口（SNI `*.okzdns.com`）+ 10 条 `*-aws-N.acczzz.com:443`（SNI
`*.hi2026.net`），2026-10-28 15:52 手工固化的快照。

它不是「已经下架的节点」：按 (SNI, 协议) 对齐后 **63/63 与当前 okz 订阅的密码
完全相同** —— okz 只是把入口域名从 `bilibili-image-cdn.juhazf.cn:5xxxx` 换成了
`cn.bing.com:443` / `us.bing.com:443`，后端没变。所以沉睡池等于**同一批节点的
旧入口**，新入口被墙时可以拿它当备胎。真正消失的只有 2 条。

**来源列写 `okz` 而不是 `沉睡池`**：报表是给人看的，「沉睡池」是代码里的叫法，
读到的人还是会问「那是哪家机场」。所以直接写源名，标签注明 `旧入口快照`
（`channel_report.py` 的 `dormant_tags()` 一带）。若哪天把别的源也塞进这份
文件，这里要跟着改 —— 它现在等于**硬编码了 okz**。

**看起来像**：`asip blk --delay` 里 H2 节点一半显示「不通」。

**实际是**：`--delay` 走的是 Clash API 的 `/proxies/<tag>/delay`，即
**sing-box 的节点出站直连 gstatic**。H2 线的真实数据路径是
`usque → sing-box direct 入站 → override 到 MASQUE 端点 → 节点出站`，
节点本身只被当作 TCP 中继，从没被直接 HTTP 打过 —— 机场节点直接打
gstatic 不通是常态（实测 SIN 块 22 个里 11 个不通，其中 4 个正在正常承载
WARP-H2 线）。判 H2 节点能不能用，看 `握手` 列（block-map 的实测结论）和
`绑定` 列（它现在是不是正在服务），不看这一列延迟。

**看起来像**：`asip blk` 里同一个节点后面挂了好几条线（如
`bilibili-50001` 同时被 WG-10/11/14 和 H2-SIN-3 用着）。

**实际是**：WG 线与 H2 线是**两条独立的承载路径，共用同一台落地节点**。
CF 侧只认设备身份（usque 进程），一条节点上可以挂多条不同设备的线；
真正不能共用的是**同一台 CF 设备**（会互踢）。所以「节点被多条线用」
不是重复绑定，是这台机器当了两条隧道的中继。

**看起来像**：报表里的订阅地址带 `***`。

**实际是**：token 不能进任何可分享的产物。`source_label()` 只留主机+末段+
`flag`，完整地址再过一遍 `redact_secrets()`。要核对某条线属于哪个源，看主机名
就够了，不需要 token。

### 13i. 测试台账必须隔离，否则「补位线有几条」决定用例结论

**看起来像**：`test_warp_wg.py` 的三个 `WARP_WG_COUNT/FAMILIES` 用例稳定通过，
与 daemon 改了什么无关。

**实际是**，它们读的是**线上** `.warp/backfill.json` 与 `.warp/h2/channels.json`：
`config.py` 在 import 时把这两份台账并进 `members`（`_append_backfill_members`
/ `_append_h2_members`）。补位线从 7 条涨到 10 条那天（2026-11-04），三条断言
「members 里只能有配置声明的那几条 wg 线」的用例一起转红，代码一行没改。

处置：`conftest.py` **在 `import daemon` 之前**就把两份台账指到空文件
（`ASIP_BACKFILL_FILE_PATH` / `ASIP_H2_CHANNELS_PATH`）。必须在 import 之前：
`config.py` 是在 import 时把台账并进 `members` 的，之后设环境变量已经晚了 ——
唯一的补救是 reload config，而 `reload` 会**原地换掉** `config.CFG` 这个对象，
与 `parse_subscription` 等 `from config import CFG` 的模块手里那个分家。
`test_warp_wg.py` 本来就用 reload 测环境变量，所以还要一个
