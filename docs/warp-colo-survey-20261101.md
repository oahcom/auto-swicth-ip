# WARP 落地实测：代理节点 → colo / 地址段（2026-11-01）

## 结论

**95 个代理出口 IP 中，48 个能承载 WARP 隧道（51%）；其中 38 个 v4/v6 双通。**

| 结果 | 数量 |
|---|---|
| v4 + v6 双通 | 38 |
| 只通 v4 | 8 |
| 只通 v6 | 2 |
| 两族全不通 | 47 |

## colo 分布（8 个）

NRT 22 · SIN 19 · PHX 13 · HKG 10 · TPE 8 · SJC 8 · LAX 4 · ORD 2

## 地址段

| 族 | 不同地址 | 不同段 |
|---|---|---|
| v4 | 15 | **13 个 /24**（集中在 104.28.x.x） |
| v6 | 32 | **27 个 /64**（2a09:bac1 / 2a09:bac5 两大前缀） |

同 colo 确实有多个段：8 个 colo 分出 27 个 /64，平均 3.4 个 colo。
v4 段则高度收敛，同 colo 通常只有 1–2 个地址。

## 为什么 47 个不通

**不是节点故障**：47 个里 46 个节点自身延迟正常（Clash API 实测能连 opencode.ai）。

是**节点转发 UDP 的能力**不同：

| 协议 | 全不通 / 该协议总数 |
|---|---|
| anytls | 40 / 59 |
| vless | 6 / 35 |
| trojan | 1 / 1 |

anytls 是 TCP 上的流复用（UoT），承载持续 UDP 流不稳定；vless+REALITY 原生支持 UDP 转发。
**生产要开 WARP 线，落地节点必须选 vless。** 池里 111 个 anytls 只有 6 个能承载 WARP。

## 建隧道成功率有随机性

首轮 190 次测试成功 58，对失败项补测一次后升到 86。
同一节点时通时不通 → 判定不能承载 WARP 需多测几次，单次失败不足以定论。

## 测量坑（排查耗了大半天，记下来免得重踩）

| 现象 | 真因 |
|---|---|
| v6 永远 0，v4 正常 | `peers[0].address` 用了 `peer_v6`（2606:4700:103::2）。它是「往 WARP 打的 UDP 目的地」，本身要求本机有 v6 出网 → 鸡生蛋。**一律用 `peer_v4`**，与出口地址族无关（生产 `build_line_config` 就是这么做的） |
| 部分实例启动即 FATAL | 节点入口是域名时缺 `domain_resolver` |
| 配置正确但连不上 | `tempfile.TemporaryDirectory()` 包配置，进程还活着目录已被清理 |
| 同上 | DNS server 的 tag 叫 `local`（与 type 同名）会让 v6 静默失效 |
| 并发互相踢 | 多个实例共用同一个 WARP profile（同一设备）；按槽位轮转 profile |

## 节点延迟（Clash API，测 opencode.ai）

## 复现方法

脚本在 `/tmp/opencode/warp_probe.py`（临时，未入库）。
对每个出口 IP 各建一条 WARP 隧道（v4/v6 各一次），UDP 经该代理节点转发，
读 `https://www.cloudflare.com/cdn-cgi/trace` 取 `colo` / `ip`。
