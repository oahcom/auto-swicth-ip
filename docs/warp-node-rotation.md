# 同块轮回守护（2026-11-02）

> 本文只讲**逻辑**，不讲代码。名词解释在前，判定流程在后。
> 相关既定事实见 [established-facts.md](established-facts.md) 第 8、10、11、18、19、20 条。

## 一、它解决什么问题

每条 WARP 线路绑定一个**机场节点**（借道出去的那台服务器）。机场节点随时可能
不可用，而且有两种"不可用"：

| 类型 | 表现 | 谁能发现 |
|---|---|---|
| 节点真的死了 | TCP 连不上 | 敲门就知道 |
| **节点活着但跑不了 WARP** | TCP 通，UDP:2408 不转发，隧道起不来 | **只有看"这条线有没有拿到出口地址"** |

第二类是最阴的：敲门有反应，所有"节点健康检查"都判它正常，但线就是不出流量。
本守护存在的意义就是抓这一类，并把线换到能用的节点上。

## 二、名词

| 名词 | 含义 |
|---|---|
| **节点** | 机场的一台服务器，WARP 流量从这里借道 |
| **线路 / 隧道** | 一条 WARP 连接，有独立设备身份，因此有独立出口 IP |
| **出口地址** | WARP 分配给你的那个 IP。拿到了 = 隧道真建起来了 |
| **colo / 块** | Cloudflare 落地机房。同一节点的流量通常固定从某个机房出去 |
| **当前出口（active）** | 22 条线里此刻正在为 opencode 服务的那一条，同一时刻只有一条 |
| **后备顺序（rotation）** | 布线时预先排好的候选节点名单 |

## 三、职责边界（必须守住）

**只管**：这条线绑的节点还能不能真的跑起 WARP。

**不管**：
- 哪条线该当当前出口 → 换线逻辑
- 出口 IP 有没有被限流 → 探测器
- IP 好不好、要不要重启换地址 → 补刷 / 预热

> 混进来的代价：曾把"出口 IP 被限流"当成节点问题，结果 22 条健康线全被判死。

## 四、一轮流程（每 60 秒，每条线依次过五道关）

### 第 0 关：轮得到吗
- 是当前出口 → 跳过（换节点要重启，会掐断在途流量）
- 未到检查时间 → 跳过

### 第 1 关：刚动过就先别碰
2 分钟内换过节点、或刚被重启过 → 跳过。

> 隧道握手 + 拿出口地址要几十秒，这期间看起来就是"没出口"，但那是还没起来。
> 不加这道闸门，每次批量重启都会让守护把所有线判成死的（实测：重启后 22 条
> 全被标记，40 秒后 19 条自己好了）。

### 第 2 关：敲门
经临时 sing-box 通过该节点连 `1.1.1.1:443`。三档结果：

| 结果 | 含义 | 下一步 |
|---|---|---|
| 通 | 节点收 TCP | 进第 3 关 |
| 不通 | 节点真死了 | 进第 4 关 |
| 测不了 | 观测者自己的问题 | **不动**（测不出来就不猜） |

### 第 3 关：TCP 通，但 WARP 真能跑吗
两条判据，任一成立就准备换：

**① 这条线从来没拿到过出口地址** —— 连续观察 3 轮（约 3 分钟）确认。
**② 本小时重启已打满 20 次** —— 重启这条路走到头了，只有换节点能换地址池。

都不成立 → 这条线是好的，不动。

> 判据必须是 `ip`（有没有拿到出口地址），不是 `last_ok_ts`（有没有成功服务过）。
> 后者在 `verdict=blocked/quota` 时会被主动清零，而 blocked 说的是"出口 IP 被
> opencode 限流"，不是"隧道不通"。

### 第 4 关：两轮确认
判死前先记一笔、等下一轮再判。连续两轮都不行才算真死。

> 机场线路抖得厉害。立刻换的话整个池子每两轮就翻一次面。

### 第 5 关：换到哪
从后备顺序里从头往下找：
1. **v6 线优先同机房** —— 同块换，落地机房不变，重连即换新 v6 段
2. **v4 线优先跨机房** —— v4 地址由机房决定，同机房换节点等于没换
3. **跳过已被其他线占用的节点** —— 两条线挤一台是把分散风险变成集中风险
4. 逐个敲门，第一个敲得开的就是它

## 五、换完必须重启（并绕过四道锁）

换节点只是改了配置文件，正在跑的进程还在用旧节点 —— 不重启等于什么都没做。

正常重启路径上有四道锁，换节点时必须全部让路：

| 锁 | 本意 | 为什么让路 |
|---|---|---|
| 夜间锁 | 夜里别为被封的机房反复烧重启 | 机房已经换了 |
| 渠道锁 | 这条线最近 100% 被封，重启没用 | 地址池已经换了 |
| 额度隔离 | 这个出口额度耗尽 | 新节点 = 新地址池 |
| 每小时 20 次上限 | 别无限重启同一条线 | 换节点重置了这个前提 |

共同点：它们防的都是"**在同一个烂地址池里反复抽签**"。换节点已经把池子换掉了。

> 实测踩过：WG-22 换到新节点后没重启（被渠道锁拦在重启入口里面），出口探测
> 一直拿不到结果 —— 配置改了、进程没动，守护却以为自己救过它了。

## 六、完整实跑（受控实验）

把 WG-22 硬绑到已知死节点 `cn.bing.com~13`：

```
22:31:10  第 1 轮观察 → 节点 TCP 通，但拿不到出口地址
22:32:32  第 2 轮观察
22:34:04  第 3 轮确认 → ⇄ 换到 ~33   ↻ 立即重启
          （~33 后来发现也是坏的）
22:37:46  第 1 轮观察
22:39:10  第 2 轮观察
22:40:42  第 3 轮确认 → ⇄ 换到 bilibili-50001   ↻ 重启
22:40:45  ✓ 拿到出口 2a09:bac1:6540:8::279:32
```

注意第二次换：换到的节点仍然是坏的，它**继续换**。只要线还没拿到出口，就接着
沿后备顺序往下走。

## 八、历史坑（别重犯）

| 坑 | 后果 |
|---|---|
| 守护挂在 `_dirty_line_janitor` 上，而生产 `prober_enabled=True` 走另一分支 | 守护是死代码，一次没跑过 |
| 只看"重启打满 20 次" | 节点收 TCP 不转 UDP 时，线要躺 20 轮才动 |
| 用 `last_ok_ts` 判"没出过口" | blocked/quota 也清零它 → 22 条全判死 |
| 加载状态表时只清 `last_ok_ts` 不清 `ip` | 陈旧 `ip` 让守护以为死线有出口，4 分钟不动 |
| 重启入口内部的夜间锁 / 渠道锁 / 额度隔离 / 小时配额 | 换完节点不重启，配置写了但进程没动 |
| 后备候选不排除已占用的节点 | WG-1/WG-2 同绑 `~13`、WG-8/WG-9 同绑 `pq.aws48` |
