# OpenCode Free Lane 503 根因报告 + 探测器失效分析

> 日期：2026-10-27
> 观测窗口：15:28:08（9router 进程启动）→ 18:40
> 分析方法：只读取证，未改动任何代码
> 涉及两个仓库：`~/.9router`（网关侧）、`~/dkk-projects/auto-switch-ip`（出口侧）

---

## 1. 结论

503 不是 9router 的传输层参数问题，而是**上游出口（WARP 隧道）不可用**。

上游不可用有两种形态，各自对应一族 503：

| 族 | 6h 计数 | 占比 | 表象 | 根因 |
|---|---|---|---|---|
| **A** | 3519 | 91.2% | `timeout:true`，19s 挂起后合成 503 | sing-box 进程活着，**内部 WARP 隧道静默死亡**（无 RST，数据永远不来） |
| **B** | 270 | 7.0% | `ECONNREFUSED`，< 100ms 即失败 | **sing-box 进程本身未监听 7890**（重启/崩溃窗口） |

两族合计占全部 503 的 98%，剩余 2% 为其它形态。

决定性证据：**17:48:23–17:48:53 sing-box 重启的 30 秒内，39 次 ECONNREFUSED 直接产生 20 次 503（耗时 46–92ms）；17:48:53 恢复后至 18:15，503 归零，111 次成功。**

### 1.1 路由确认

`singbox-config.json` 显式把 opencode 流量绑到 WARP 出口，不是走机场节点：

```json
{"domain_suffix": ["opencode.ai"], "outbound": "opencode-out"}
```

```json
"opencode-out": { "type": "Selector", "outbounds": ["WARP-CF", "WARP-CF-B", ... 共 21 条], "default": "WARP-CF" }
```

而 `route.final = "proxy"`（28 条机场 vless 节点）只承接其它域名。**opencode 的存活完全取决于这 21 条 WARP 线。**

## 2. 503 的产生链路

### 2.1 族 A：隧道静默死亡 → 19s 挂起 → 合成 503

```
9router chatCore
  → OpenCodeExecutor.execute → base.execute（fallbackCount=1，只有一条 baseUrl）
  → fetchUpstream → fetchViaTransport
      → Bun sidecar: sessionFor(proxy).fetch()
          WARP 隧道已死 → 连接建立但永无首字节
          → UPSTREAM_TIMEOUT_MS=19000 到点 abort
          → 返回 {"timeout":true}
      → lastResetAt 30s 全局冷却被占住
      → return null
  → fetchUpstream 拿到 null，拒绝 Node 降级，合成 503 UpstreamTransportError
  → base.js:161 tryRetry("503")：attempts=3 / delayMs=2000，同一条死路重试 3 次
  → 返回 503
```

证据链 1:1 对应（当前进程）：

```
upstream fetch failed (timeout:true)  1609
reset throttled, fail fast            1494
Bun transport unavailable             1494
ERROR 503                             1455
```

时长分布印证了重试叠加：`19–23s: 1131 / 23–40s: 252 / 40–65s: 72`。

### 2.2 族 B：sing-box 未监听 → ECONNREFUSED → 立即 503

`connectTimeout: 8000` 在此路径不起作用：端口无人监听时内核立刻回 RST，Bun 立即报 `ECONNREFUSED`，sidecar 返回 `timeout:false`，`fetchViaTransport` 走非超时分支再试一次，仍失败 → 合成 503。

**耗时 46–92ms** 是这一族的判别指纹（族 A 最短 19287ms）。两者相差两个数量级，不会混淆。

## 3. 真正的问题：探测器已经失效

### 3.1 现象

从 17:48:53 sing-box 恢复到 18:40：

```
↻ 换线触发         74
✓ 换线成功          0
⚠ 无新鲜备线不切    73
```

连续 **74 次换线全部失败**，日志恒为同一句：

```
· 暂无 120s 内 OK 的备线，等待探测器写入
⚠ 等待超时仍无新鲜备线，本次不切（不重启、不落池）
```

### 3.2 根因：`next_probe_ts` 被推到了次日 08:00

`.warp_line_state.json` 里 20 条线，**18 条的 `next_probe_ts` 是 2026-10-28 08:00**（距当时 13.3 小时），另 2 条是当日 23:29/23:31（4.7 小时）。**`last_ok_ts` 全部为 0.0** —— 没有任何一条线被认为"新鲜可用"。

而 `daemon.py:2677`：

```python
next_ts = float(st.get("next_probe_ts") or 0.0)
if now < next_ts:
    return False, next_ts        # ← 13.3 小时内根本不探
```

探测器因此对全部 20 条线**保持静默到次日早八点**。

### 3.3 08:00 这个时刻是怎么来的

不是任何显式的"每日重置"常量（全仓搜索 `08:00` / `28800` / `daily` 均无命中）。它是 **`ban_until` 这一绝对对齐时刻**，不是上游 Retry-After 被钳制后的落点。

证据：`.warp_ip_used.json['used']` 里 421 条记录带 `blocked=True`，其中 **417 条记录带 `ban_until`，全部 417 条落在次日 08:00**。这 417 条记录的 `ban_until` 跨度为 **86405.9 秒（恰好 24 小时）**，而标记时刻 `ts` 的跨度为 **104239.5 秒（28.96 小时）**。

```
ban_until 跨度: 86405.9s (24.0016h)  # 全部集中在今日 08:00 与明日 08:00
ts        跨度: 104239.5s (28.96h)   # 实际观测窗口
```

若是逐条相对时长（Retry-After 秒数），`ban_until - ts` 应随 `ts` 变化而变化，两者跨度应相近。**两者差距远大于 24h，说明 `ban_until` 是固定的对齐时刻（每日 08:00 配额重置），而非逐条计算的相对时长。**

推断上游在 429 响应的 `Retry-After` 头里给出了 HTTP date（指向次日 08:00），本地 `_mark_warp_ip_used`（`daemon.py:3948-3955`）将其解析为绝对时间戳写入 `ban_until`。

随后在探测回写路径：

```python
# daemon.py:2735-2742
elif verdict in ("quota", "flagged", "blocked"):
    wait = max(_line_persistent_retry(),                     # 21600s = 6h
               _line_block_remaining(st.get("ip"), ts))      # → ban_until - now
st["next_probe_ts"] = ts + wait
```

`_line_block_remaining` 返回 `ban_until - now`，于是 `next_probe_ts` 被直接推到 `ban_until` —— 即次日 08:00。

**关键更正**：我上一版把 08:00 归因到 `MAX_RETRY_SEC=86400` clamp —— **错**。实测 `rate429_guard_sec=60`（config.py:325 / 运行值）从未生效，`ban_until` 直接盖过它。真正的机制是 `ban_until`（绝对对齐时刻）→ `block_left` → `wait = max(6h, block_left)` → `next_probe_ts`。

### 3.4 链路后果

```
20 条线全被判脏（quota/blocked）
  → next_probe_ts 全部推到次日 08:00
  → _warp_line_needs_probe 全部返回 False
  → 探测器 13.3h 内一条都不探
  → last_ok_ts 恒为 0
  → _warp_line_fresh_candidates 返回空
  → 换线路径 _warp_line_wait_fresh 每次等满 switch_wait_sec=20s 后放弃
  → 74 次 × 20s = 24.7 分钟纯等待，落在 10s tick 的主循环上
```

这也解释了用户观察到的「探测没有生效，或者效率太低了」——**两者都成立**：探测停摆 13.3 小时（没生效），而每次换线还固定空等 20 秒（效率低）。

### 3.5 关键缺口：重启换 IP 的路径被自己堵死

`daemon.py:2956-2968` 的注释承认了矛盾：

```python
# 重启只换地址，不撤销该线已记录在案的惩罚：quota 的 16h /
# blocked 的 6h 是上游按 IP 给出的恢复时刻，重启把它改回 +5s
# 等于让惩罚失效（同址重启会立刻再烧一次配额）。
prev_next = float(st.get("next_probe_ts") or 0.0)
same_ip = bool(ip) and ip == prev_ip       # ← 关键
if block_left > 0:
    st["next_probe_ts"] = max(prev_next, now + block_left)
elif (same_ip and prev_next > now and ...):
    st["next_probe_ts"] = prev_next
else:
    st["last_verdict"] = "unknown"
    st["next_probe_ts"] = now + _line_unknown_retry()   # 5s，恢复探测
```

`same_ip` 的判定意味着：**只有重启后 IP 真的变了，才会把 `next_probe_ts` 拉回 5 秒重新探**。而重启（换会话）确实会拿到新 IP —— 这条逃生路径在代码里是通的。

但它走不到：`_warp_line_fresh_candidates` 先返回空 → 换线在"等备线"阶段就 `return False`，**根本没进入重启分支**。于是「没有新鲜线 → 不切 → 不重启 → 没有新 IP → 还是没有新鲜线」形成闭环。

`restart_count` 的分布侧面印证这些线历史上被大量重启过（`WARP-CF-E: 281`、`WARP-CF-16: 267`、`WARP-CF-15: 243`、`WARP-CF-12: 154`），说明重启这条路径本身是有效的，只是现在被 wait_fresh 挡在前面。

## 4. 9router 侧的次要缺陷（会放大故障，但不是起因）

### 4.1 429 重试会丢掉真实 429

`open-sse/executors/opencode.js:665-676`：

```js
const retryResult = await super.execute({ ... });   // ← 重新进入 fetchViaTransport
if (retryResult?.response?.status === 429) { ... }
return retryResult;                                  // ← 合成 503 就这样返回了
```

`super.execute` 不知道外层刚拿到 429，把重试当成全新请求。撞上冷却时它返回的是合成 503，**原始 429 被覆盖**。上层 combo 于是按"出口故障"处理，而不是按"配额限流"退避——两者该走完全不同的恢复策略。

### 4.2 备用出口恒为空

数据库现存 6 个池，只有 3 个 `isActive=1`，而它们**共用同一个 `proxyUrl = http://127.0.0.1:7890`**：

```
SELECT COUNT(DISTINCT json_extract(data,'$.proxyUrl')), COUNT(*)
FROM proxyPools WHERE isActive=1;   →  1 | 3
```

`identifyFixedEgress` 用 `hashEgress("proxy", proxyUrl)` 作身份，三条池算出同一个 egress id；`selectAlternateProxy` 用 `excludeIds.has(egress.id)` 排除当前出口，于是**三个全被排除，候选集为空**。

用户已删除的 `7000` 池曾是唯一 id 不同的候选——它没有监听、连接静默挂起，所以那时是"每次都选中死池"。删除后变成"永远没有候选"。**两种状态都不正确，同一处设计缺陷的两面。**

### 4.3 传输层冷却过粗

`opencodeTransport.js:236-243 / 261-267` 的 `lastResetAt` 是**进程级全局**变量：一条出口超时，冷却期内所有出口的请求都 `fail fast`。按出口分键可以把这个放大器去掉。

### 4.4 连接清理已关闭（正确的决定，但留下了另一面）

`cleanup_enabled = False`。代码注释记录了关闭的原因：

> DELETE 不区分「僵死的池化 socket」和「正在跑的在途请求」，实测会掐断正常流式响应（客户端报 upstream connection lost），而 sidecar 收到 socket hang up 又产生新 503，反过来再触发清理。

用户说的「好的请求被截断」正是这一条——**已经做了处理，方式是直接关掉**。代价是 `_verify_transport_failure` 里"出口正常但连接僵死"这条分支现在只记日志、不动作。

## 6. 修复方向（未执行，需授权）

按「改动小 → 收益大」排序。前三项在 `auto-switch-ip`，第四项在 `9router`。

| # | 位置 | 改动 | 解决什么 |
|---|---|---|---|
| **1** | `daemon.py:2956-2968` | `same_ip` 判定前置：在 `wait_fresh` 之前先对"全部线都不可探"的情形做一次重启换址 | 打破「无新鲜线 → 不切 → 不重启 → 无新 IP」闭环。这是唯一能让系统自愈的入口 |
| **2** | `daemon.py:4736` | `switch_wait_sec` 从 20s 降到 ≤3s；等不到就直接走重启分支 | 去掉每次 20s 纯空等，74 次省下 24 分钟 |
| **3** | `daemon.py:2735-2742` | 区分「该 IP 脏」与「该线停探」：`next_probe_ts` 不应超过 `_line_transient_retry` 的上限（600s），长期 ban 只影响选线权重，不影响探活 | 防止单条脏地址让整条线停探 13.3h |
| **4** | `9router/open-sse/executors/opencode.js:665-676` | 重试返回 503 且原始是 429 时，把 429 还给上层 | 让上层按限流退避而不是按出口故障重试 |
| **5** | `egress.js:64` + `auth.js:54` | 池身份纳入池 id（不只是 proxyUrl），或 `rotateStrategy=none` 时不构建 alternates | 消除「备用出口恒为空」，但用户已明确此项不改（「配多少个代理池是用户的态度」），故列而不推 |

### 6.1 新增修补点：探测逻辑不应被任何东西限制（用户指令 2026-10-27）

> **探测逻辑不应该被任何东西限制，即使没有任何东西可以探测，即使探测的结果全都是不好的。**

这对应设计文档 `docs/prober-gate-design-20261027.md` 的完整闸门分析。当前探测器要过 9 道闸：

| 闸 | 位置 | 类别 | 处理 |
|---|---|---|---|
| **闸 1 `next_probe_ts`** | `daemon.py:2672` / `:2742` / `:2763` / `:2962` / `:2965` | 结论驱动停探 | **P0 移除**：非 OK 结论统一固定节奏（cap 60s），不再读 `ban_until`；OK 分支直接赋值不再 `max`；**同时 `probe_persistent_retry_sec` 21600 → 60**（6h 地板是独立致停源） |
| **闸 2 `warming`** | `daemon.py:3011` | 资源/状态保护 | 保留（但需确保异常路径能清除） |
| **闸 3 `_warp_ip_is_blocked` 台账判脏** | `daemon.py:3028` / `:3991` | 结论驱动停探 | **P0 移除**：探测入口删掉判脏跳过，台账只用于选线排序 |
| **闸 4 整批失明** | `daemon.py:3035` | 资源/状态保护 | 保留（建议默认 30s 并配置化） |
| **闸 5 全局速率** | `daemon.py:2993` | 调度/资源限制 | **保留**（运行值 600/分钟） |
| **闸 6 结论缓存 TTL** | `daemon.py:657` / `_probe_ttl` | 结论驱动停探 | **P0 移除**：`quota`/`flagged` TTL 21600 → 600s |
| **闸 7 并发上限** | `daemon.py:3076` + `:3117` | 调度/资源限制 | **保留**（运行值 32） |
| **闸 8 模型层信号量** | `daemon.py:3041` | 调度/资源限制 | **保留**（运行值 32） |
| **闸 9 探测额度** | 物理约束 | — | 唯一硬约束，受闸 7/8/5 自然限制 |

**设计原则**：观测是观测，不是决策。观测结果（quota/blocked）只应影响「探完之后拿这个结论做什么（选线权重、重启冷却）」，不应影响「下次还要不要探」。

这不会造成配额灾难，因为：
1. 闸 5（600/分钟）与闸 7（32 并发）仍在，全局消耗有上限
2. 真正的配额保护应来自**统一的、与结论无关的固定节奏**（如每线每 60s 最多一次），而不是「上次结论是 quota 就停 6 小时」
3. 固定节奏是可预测的消耗；结论驱动停探是不可预测的停摆（本次 56.6 分钟零探测、74 次换线全废）

完整设计详见 `docs/prober-gate-design-20261027.md`。

## 7. 一句话

**503 = WARP 出口不可用；而出口不可用之所以持续，是因为探测器把 20 条线一起判了 13.3 小时停探，换线路径又只会空等 20 秒然后放弃——系统失去了自愈能力。探测逻辑不应被任何东西限制（用户指令），必须拆除所有结论驱动的停探闸门，只保留资源调度闸门。**
