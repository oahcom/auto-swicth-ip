# 第七闸口代理池轮换 — 根因与方案（v2）

> 本版推翻并替换 `plan-20261113-gate-rotation.md`。
> 替换原因：旧版把"候选集失真"归因为"按 IP 去重合并了共享额度池"，并据此认为额度只有 5 份。
> 新证据表明：**额度按出口独立计，轮换本身有效；真正的问题是系统不知道哪些出口已经用过。**

---

## 0. 一句话结论

第七闸口的选点逻辑按"入口名"管理 203 个节点，而**限额实际记在"出口地址"上**；同时唯一的归属字段是别的进程的出口快照，用量字段恒为空，最近使用窗口只有 5 格。

结果是：**名义 202 个成员、历史命中 174 个（当前在役 171）、去重后候选上限 61、地址桶上限 30**——三者之差源于一列错误的地址台账触发的去重连坐，不是观测缺失。该去重使同一时刻每个桶最多只出 1 个候选，并发出口上限 30，实际还随判死与冷却继续下降；桶内成员按可用性动态轮换。而 90% 的轮换动作是被 429 推着走的。

补充一个必须用数据说清的尺度：实测 76 个入口对应 63 个出口，冗余率 17%。也就是说 **203 个入口里约 175 个是独立出口**，个别同域名多端口的入口才共享。所以"合并同出口"这件事只在 17% 的范围内成立，而现有逻辑按一张不可信的地址表删掉了 82% 的候选。

## 1. 名词

| 名词 | 含义 |
|---|---|
| **入口（inbound entry / 节点名）** | 订阅里的一个条目，如 `cn.bing.com:443~7-any`。它是"门"，不是"房子"。 |
| **出口（egress）** | 真正承载请求的落地地址，如 `154.83.84.34`。额度记在这里。 |
| **`~N` 后缀** | 同一前置域名下的第 N 个 SNI 变体。前置域名是 CDN 入口，SNI 决定 CDN 把连接交给哪台落地。 |
| **前置域名（fronting）** | 如 `cn.bing.com`、`us.bing.com`，被借用作不被阻断的连接入口，本身不是落地。 |
| **额度（quota）** | 上游按出口地址计的可用请求数，约 200~300 次；耗尽后返回 HTTP 429。 |
| **Retry-After** | 429 响应头里的恢复时间。实测出现过 46799 秒（约 13 小时），说明这是日级额度而非秒级限速。 |
| **第七闸口 / slot-7** | 兜底出口，独立 sing-box 进程，监听 7897，Clash API 9097，选择器名 `proxy`。 |
| **P2C** | Power of Two Choices，随机抽两个候选取分数高者。当前选点算法。 |
| **在役窗 / proactive** | 定时主动换节点的节奏，当前 60 秒。 |

## 2. 资源模型：机场节点与 WARP 不是一类东西

这是全部结论的地基，也是此前所有误判的来源。

| 维度 | WARP | 机场代理池 |
|---|---|---|
| 额度记在谁身上 | **出口 IP**，共享，别人也在打 | **出口 IP**，独占，基本只有本机在用 |
| 可用性先验 | 不确定，必须探测 | 基本恒真，探测是白付成本 |
| 稀缺资源 | 干净、未被烧过的出口 | 每个出口 200~300 次预算 |
| 冲突来源 | 别人把同一 IP 打爆 | 自己把同一出口打过热 |
| 该回答的问题 | 哪个 IP 还活着 | **哪些出口还没用过、每个用了多少** |
| 换节点是否有效 | 有效（换 IP 就换额度） | **有效**（实测同刻 4 个出口 OK、2 个出口 429） |

关键：两者"稀缺资源"同为出口 IP，所以"按出口记账"的直觉是对的；但 WARP 的出口是**共享**的，机场的出口是**独占**的——共享资源需要"避让与探测"，独占资源只需要"遍历与记账"。

把 WARP 的探测、判死、避让机制整套搬到机场节点上，等价于把"防别人抢"的手段用在"防自己重复"的场景里，方向错位。

三条必须记住的实测事实：

1. **同一时刻，不同出口可以一个 429 一个 200。** 所以额度是**出口级**的，不是全局账号级。
2. **同一 server 的不同端口，出口完全不同。** 所以 203 个入口里绝大多数是独立出口，不能按 server 合并。
3. **确有入口共享出口。** 但不是普遍现象，是局部（同域名多端口的少数组）。
4. **`node_info` 的地址列不能用来数额度池。** 见下。

### 3.1 实测裁决：67 条"同址"记录里抽 10 个，8 个出口全不同

用独立测量实例（另起 sing-box，端口 7002 / 9099，不触碰生产 7897）对表里被标记为同一地址 `51.241.140.86` 的节点抽样 10 个，逐个切换并实测其真实出口：

| 节点 | 表里记录 | 实测出口 |
|---|---|---|
| `203.10.96.138:443-vl` | 51.241.140.86 | **203.10.96.139** |
| `cn.bing.com:443~21-any` | 同上 | **64.120.94.204** |
| `cn.bing.com:443~24-any` | 同上 | **64.120.94.210** |
| `cn.bing.com:443~6-any` | 同上 | **45.207.156.48** |
| `cn.bing.com:443~7-any` | 同上 | **154.83.84.34** |
| `cn.bing.com:443~8-any` | 同上 | **154.83.87.187** |
| `cn.bing.com:443~9-any` | 同上 | **156.224.78.207** |
| `ddixx-1dd1.dankenet.help:16895-vl` | 同上 | **152.175.146.70** |
| `cn.bing.com:443~23-any` | 同上 | 连接失败 |
| `ddixx-1dd1.dankenet.help:10309-any` | 同上 | 连接失败 |

**8 个可用节点，8 个不同出口，没有一个是 51.241.140.86。**

所以这个字段记录的不是节点归属，而是"回填那一刻主进程的出口"。67 条同址是污染累积，不是共享事实。

**这条实测同时裁决了一个方案级分歧**：有调查结论认为"203 个节点实际只有 30 个额度池，所以去重到 61 个是合理的"。该结论建立在同一张污染表上，且已被本表直接否定——如果 67 个节点共享一个出口，抽样 10 个应该测出同一个地址，实际测出 8 个互不相同的地址。

**去重后的 61 个候选是事实，但它不是"合理的收敛"，而是"把 66 份独立额度丢进了同一个桶"。**

### 3.3 限额有两层，轮换只能解决其中一层

这是最容易被忽略、也最影响预期的一点。

**第一层：出口级。** 机场对每个落地单独限速/限额。实测证据：同一时刻 6 个同域名不同端口的入口，4 个返回 200、2 个返回 429。这一层换出口有效。

**第二层：账号级。** 上游按账号（或设备指纹）计的额度。实测证据：Retry-After 稳定指向次日 08:0x，且换遍池子后仍有 98% 撞 429；03:00 那 5 分钟里，同一账号下 38 个不同入口同时 429。这一层换出口无效。

**判别方法**（可直接用于运行期判断）：连续试 20 个不同出口，如果全部 429，是账号级，此时继续切换只是空转；如果中途出现 200，是出口级，换出口仍然有效。

**对方案的含义**：
- 出口级问题，本方案能解决——恢复候选、按出口记账、主动遍历，都是为这一层设计的。
- 账号级问题，本方案解决不了，也不该假装能解决。它需要的是多账号分流或降低消耗，属于另一个议题。
- 因此方案里必须包含"识别当前处于哪一层"的能力，并在账号级耗尽时**明确报告、停止空转**，而不是继续制造 2000 次无效切换。

这也解释了为什么单纯"提高覆盖率"在风暴期看不到效果：那段时间撞的是第二层墙，换多少门都一样。

### 3.2 续航：给区间，不给单值

按实测请求速率 1128 次/小时、按每出口 200~300 次估算，三个口径分别是：

| 口径 | 可用次数 | 续航 |
|---|---|---|
| 瞬时只有约 61 个入口可用（去重永久剔除 141 个） | 约 1.5 万 | 约 13.5 小时 |
| 全池 203 入口（假设去重分组会漂移、跨时段能触达全部） | 约 5 万 | 约 45 小时 |
| 实测观测 | — | 每天下午出现 429 密集段 |

观测落在下限一侧：额度在日内就被打穿，不是跨日才耗尽。

但**如果瓶颈其实是账号级限流（见 3.3），续航这个指标本身就不成立**——那不是"钱花完了"，是"这个时段不让你花"。下午的 429 形态（密集、次日能恢复、换遍池子仍 98% 撞墙）更像后者。

所以对外只保留一句话：**当前配置下，池子的日内供给明显低于日内需求；恢复候选能补上出口级缺口，补不上账号级那一层。** 具体是 13 小时还是 45 小时，要等请求级埋点落地后才能定，现在给任何单值都是猜。

## 4. 问题链（按根本性排序）

### R1 身份不稳定，且记账单位与限额单位错位（最根本）

**现象**：系统以入口名（203 个字符串）为唯一键管理一切——延迟表、调用计数、最近使用、判死、去重分组。但这个键本身不稳定，有两处根子：

- 名字里的 `~N` 不是线路编号，而是"同一 host:port 下第几个撞名条目"的递增序号，从 2 起补空位，完全由订阅到达顺序决定。订阅刷新重新排序后，同一个 `~N` 就指向另一台机器。
- 用于判重的身份指纹是 `server|port|type|transport|sni`，**不含凭据**。同一入口下靠不同凭据区分的两个后端会被判成同一个身份，直接丢弃其中一个。

**为何影响**：账本挂在会漂移的名字上，等于把账记在别人的户头上；同时限额记在出口地址上，而一个出口可能对应多个入口。两个错位叠加——跨刷新无法对账，跨入口无法合并。

**如何影响**：既算不出"这个入口累计用了多少"，更算不出"这个出口还剩多少"。系统唯一的判定依据退化为"刚才那个名字有没有 429"。

**凭据**：名字生成与 `~N` 递增逻辑在订阅解析的 `_tag_for` 与撞名分支；指纹定义在 `_node_fp`。机场原始名保存在 `sources.json`：`cn.bing.com:443~6` = 「香港-01」、`~8` = 「香港-03」、`pq.aws63..67` = 「新加坡 AWS 01–05」——可见 `~N` 在机场侧确实是不同后端，只是共用同一个入口地址。

### R2 去重的意图正确，但喂给它的数据是坏的

**现象**：去重函数按 `node_info.ip` 分组，每组只保留 `call_count` 最低的一个，其余永久跳过。`call_count` 全为 0，排序退化为稳定排序，于是**固定留第一个、其余全弃**。171 条有记录节点被压到 30 组；加上无记录节点，实际候选约 61 个。

**为何影响**：这里必须区分两件事。"按出口去重"本身是对的——实测确认确实存在跨机场共用出口的情况（13 个实测节点里有 3 组两两共用一个地址）。错的是喂给它的数据：地址列是别的进程的异步快照。于是失效是双向的——**该合的没合上（分组整体错位），不该合的连坐（错删）**。

**如何影响**：实测样本里真实复用率约 1.3 个节点/出口（样本仅 13 个节点、集中在三个同源域名，偏置明显，只作存在性证据），而台账声称 5.7 个。多出来的那 4 倍就是被误伤的独立出口：全池 202 个成员，判死先削 62、冷却与最近窗口再削 11，去重从剩下的 130 个里再削 69——去重是单项最大的一刀。全量重放（15.3 小时、2644 次）：落点覆盖 171/202 = 84.7%，但任意 203 次窗口里平均只出现 74.4 个不同节点（36.8%），均匀抽样应当是 127 个。**所以候选上限是 61，按地址桶算更是只有 30。**

**关于桶内顺序**：不能断言"同一个桶永远由选择器里第一个节点霸占、死了才轮到下一个"。实测 14:43 之后，67 节点那个大桶里下标最小的 `cn.bing.com:443~6-any` 只被选了 3 次，桶内最多的是另一个节点 9 次。机制上是：去重的排序键（调用计数）全为 0，于是保留候选列表里最靠前的**可用**者；而候选列表每一跳都重算，可用性又受判死、冷却、最近窗口影响——所以桶内成员是**按可用性动态轮换**的，不是固定接力。

**台账行与"被选中"的关系**：171 行对应 172 个现役落点中的 171 个，差的那 1 个（`hk-aws-53`）被选中过 2 次但两次测量都失败；另 3 个落点是已下线旧名，行被清理任务删掉。所以不是等价关系，而是"被选中 **且** 测量成功 **且** 仍在池里"三者的交集——比"用过"窄得多，还带"只记好节点"的偏差。

代码佐证：`_dedup_by_ip`（`daemon.py` 10333）；`_load_candidate_stats`（10314）读 `node_info.ip`。

### R3 用量账本恒为空

**现象**：`call_count` 在 171 条记录里全为 0。原因有三层：
- 真正消耗额度的两条路径（429 触发轮换、第七闸口轮换）显式传入"不计数"；
- 计数的两条路径（60 秒主动轮换、外部命令轮换）恰好是不产生业务流量的；
- 每 20 分钟把内存计数与数据库字段一起清零。

**为何影响**：选择器里"调用次数少者优先"这一维永远拿不到数据，P2C 退化为"只看延迟的一次随机二选一"。

**如何影响**：无法识别"这个出口已经用了 200 次"，也就无法在耗尽前主动避开。

**附加偏差（三重过滤，不是抽样）**：一行数据要存在，必须同时满足"被选中 **∧** 测量成功 **∧** 该节点仍在当前选择器内"。反过来，没有行可能是三种原因之一：从未被选中、在位但测量失败、已退场被清理删行。所以 171 行不能当"池子健康样本"——它被三个条件同时筛过，越差的节点越会被三层一起滤掉。实例：`hk-aws-53` 在当前选择器内、两次作为轮换起点（13:35:06 / 16:09:47）、从未成为目标、测量失败——四条里三条满足，唯独测量没过，于是一行都没有。

**这层误解被写进了代码注释**：回填函数里写着"这是该出口真在被服务的准确时刻，不是切换捏造的预估"，而请求实际走的是主进程端口。错误前提以"已经实测过"的语气固化下来，后面所有基于这张表的判断都继承了它——这比单纯写错一行数据更难被发现。

代码佐证：`pick_next_node` 的 `count_call` 参数（10408），四处调用点分别传 False/True（9887、11947、14418、16052）；`_reset_node_call_counts`（11995）由主循环 20 分钟触发（15997）。

### R4 429 语义错位

**现象**：429 被定义为"IP 级限流"，进 60 秒冷却，冷却后重新入候选。

**为何影响**：实测 Retry-After 为 46799 秒。60 秒后回去，额度并未恢复。

**如何影响**：形成"429 → 冷却 60 秒 → 回来 → 再 429"的稳定空转；同时因为冷却只是暂时移出，节点总数不变，下一轮仍会撞上。

代码佐证：`429_cooldown_sec=60`（`config.py` 213）；`_cool_down_node`（10272 附近）；生产路径拿不到 Retry-After 而只有探测路径能拿到（6946–6976 的注释）。

### R5 覆盖窗口与池规模不匹配

**现象**：`_recent_nodes` 是长度 5 的双端队列，只排除最近 5 个。

**为何影响**：203 个入口，第 6 次轮换就可能回到第 1 个。

**如何影响**：即使候选完整，也无法做到"每个出口都用一遍"，覆盖率上不去。

代码佐证：`_recent_nodes = deque(maxlen=5)`（10221）。

### R6 切换由 429 驱动，而非主动遍历

**现象**：2027 次轮换里 1807 次由 429 触发（89.1%），主动轮换仅 42 次。

**为何影响**：系统不主动走遍池子，只在被打时换门。

**如何影响**：池子的利用完全由"哪几个出口先被打穿"决定，而不是由策略决定；越打不穿的越不被用，越被用的越快打穿，形成集中化。

代码佐证：`gate.log` 的 reason 分布；`_rotate_proxy_gate_once`（14472）的触发源。

### R7 判死把"额度耗尽"读成"链路坏了"

**现象**：常驻判死中位 62 个、峰值 143 个，占池子 31%–70%。202 个池成员（另 1 个是内置直连）里有 **31 个从未被成功切到过一次**——其中 10 个属于 bilibili 这个 29 入口的大族、9 个 cn.bing、5 个 us.bing、7 个 acczzz。它们 100% 在判死名单上，每个都有 12–29 次判死记录、0 次切换。

更关键的是判死门槛：判死事件里 **79% 是"单次探测失败即判死"**，TTL 只有 30 秒；这 79% 里有 **61.9% 事后复测是通的**。也就是说，绝大多数"死节点"只是那一次探测没在 5 秒内回来。

**为何影响**：判死依据是连通性探测。额度耗尽的节点 TCP/TLS 是通的，探测反而会成功；真正连不上的极少。反过来，5 秒超时对跨洋线路偏紧，慢节点会被读成死节点。

**如何影响**：候选池永久少掉三分之一，而摘掉的恰好是"额度可能还在、只是上次撞了 429"的那批。它与 R2 的去重叠加，共同把 203 压到 61。

**凭据**：`_apply_test_results` 的判死链路；判死名单 150 条记录。

### R8 池成员漂移无人修复，容量会静默缩水

**现象**：两处自愈都显式跳过池闸；更隐蔽的是，漂移判据本身只统计 WARP 成员，池成员被直接过滤掉。订阅刷新的热载路径只替换配置对象、不重建 outbound。结果是：**订阅新增的节点永远进不了运行时选择器，订阅删掉的节点继续留在可选集里**，而且没有任何告警。

**为何影响**：池子的实际容量由运行时决定，而运行时的成员集合与磁盘配置可能长期不一致。

**如何影响**：即使把去重和判死都修好，可用容量仍可能低于磁盘上的 203；反过来，已下线的节点会被反复尝试并持续失败，进一步污染判死名单。16 小时内没有任何一次槽位级重启记录，说明这条路径从未被触发过。

**凭据**：热载校验与漂移自愈两处的跳过分支；漂移判据的成员过滤；一致性自检只比对选择器，不比对池选择器。

### R9 两个写者同时改同一个选择器

**现象**：keeper 路径在锁外发起轮换，/rotate 路径在锁内。两者可在同一秒对同一选择器各发一次 PUT。合并窗只对 /rotate 生效，对 keeper 无效。

**为何影响**：PUT 之后的回读校验看到的是"另一个写者刚写进去的值"，于是判定本次失败。

**如何影响**：实测 4 次"回读不符"，4 次都能在同一秒找到 keeper 的轮换日志，且其目标恰好等于回读到的值——4 次全部因此触发重启。这不是偶发竞争，是结构性冲突。

**凭据**：keeper 调用点未持锁；4 组同秒日志配对；池闸回执里的切换时刻恒为 0（池闸不走槽位写入路径）。

## 5. 方案：把记账单位从"入口"换成"出口"

不改变"轮换"这件事本身，只改变"记什么、按什么分组、什么时候标记耗尽"。

### 5.1 建立入口→出口映射（唯一需要新增的观测）

**做法**：每次切换成功后，经**该闸口自己的入口**（7897）查询一次出口地址，写入映射表。不使用 7890，不使用任何共享快照。

**为何必要**：这是唯一可信的归属来源。现有回填走 7890，实测偏差 100%（记 `185.14.47.180`，实际 `141.148.214.234`）。

**代价**：每次切换多一次到公共 IP 查询服务的请求，不消耗上游模型额度。按每天约 200 次切换计，一天即可覆盖全部入口；也可在维护窗口批量补齐。

**渐进性**：映射未知的入口按"独占出口"处理（悲观假设），一旦测到就归并。不阻塞上线。

### 5.2 账本记在出口上

**记什么**：出口地址、累计成功次数、首次/最近 429 时刻、Retry-After 给出的恢复时刻、被哪些入口共享。

**不做什么**：不做周期清零。额度是日级的（Retry-After 达 13 小时），清零只能让系统忘记已经花掉的钱。

**前提：必须先有请求级归因。** 现有日志只能回答"谁被换下了"，回答不了"谁服务了这次请求、结果如何"。没有这一层，账本只能记"被选中次数"，而额度是按请求消耗的——两者不是一回事。14 小时里单节点最多被选中 47 次，如果它真能扛 250 次请求，说明每个节点在岗期间平均要服务 5 次以上，而这个数字现在无人知道、也无从计算。所以账本的第一块砖是归因埋点，不是计数表。

**为何能解决 R1/R3**：账本键与限额单位一致，"用了多少"才有意义。

### 5.3 选择器改成"出口级遍历 + 组内轮转"

**两层结构**：
- **外层按出口**：优先选未耗尽的出口，同层内按"最久未用"排序。这是覆盖，不是负载均衡。
- **内层按入口**：同一出口的多个入口轮流使用。理由是抗封锁——多个入口是不同的 TLS 特征，轮换它们比固定用一个更难被识别。

**为何能解决 R2/R5**：候选不再被永久删除，而是"延迟使用"；覆盖记忆按出口数（约 200）建立，不是 5 格。

**为何这不是"限频"**：它不降低切换频率，也不限制并发，只改变"下一个选谁"。

### 5.4 429 变成出口级的"耗尽标记"

**做三件事**：
1. 收到 429 时，把**该出口**标记为耗尽，而不是把该入口冷却 60 秒；
2. 尽可能读取 Retry-After 作为恢复时刻；生产路径拿不到时，由探测路径补齐；
3. 全部出口都耗尽时，不再做无效切换，直接报告"本日额度已尽"，不再空转。

**为何能解决 R4/R6**：把"换门"从默认反应改成"确认门后没房子才换"。

### 5.5 保留探测，但降级

探测只回答"这条链路连不连得上"，不再有判死权。原因是独占出口几乎恒可用，探测失败绝大多数时候是额度耗尽而非链路故障，用它判死会误杀。

## 6. 方案为何能解决问题（逐条对应）

| 根因 | 对应动作 | 因果解释 |
|---|---|---|
| R1 单位错位 | 5.2 出口级账本 | 记账单位与限额单位对齐后，"还剩多少"才可计算 |
| R2 候选被压 | 5.3 组内轮转 | 不删入口，只推迟；140 个闲置出口重新进入候选 |
| R3 账本为空 | 5.2 不清零 + 5.3 记账路径 | 所有切换路径统一记账，且不周期清零 |
| R4 429 语义 | 5.4 耗尽标记 | 用真实恢复时刻替代 60 秒猜测，避免回去撞墙 |
| R5 窗口不足 | 5.3 出口级记忆 | 记忆容量从 5 扩到出口数，覆盖率可达 |
| R6 被动切换 | 5.3 主动遍历 | 主动按"最久未用"走，而不是等 429 推着走 |

预期可观测变化（验收时用）：
- 连续 200 次轮换涉及的不同出口数，从当前约 30~60 提升到 150 以上；
- 429 占轮换原因的比例，从 90% 降到 30% 以下；
- 主动轮换占比从 2% 提升到 50% 以上。

## 7. 明确不做

1. 不限制轮换频率，不引入任何退避阶梯。
2. 不改渠道层（WARP 换线、重连、秒切槽）。
3. 不改 WARP 相关判据与出口池逻辑。
4. 不删除去重能力，只把它从"永久丢弃"改成"组内轮转"。
5. 不在第一批改动里调整选择算法之外的任何策略参数。

## 8. 验收判据

| 判据 | 阈值 | 取证方式 |
|---|---|---|
| 出口覆盖率 | 连续 200 次轮换覆盖 ≥150 个不同出口 | 轮换日志 |
| 账本对账 | 账本累计次数 = 实际切换次数，零误差 | 账本 vs 日志 |
| 429 依赖度 | 429 驱动的轮换占比 <30% | reason 分布 |
| 映射可信度 | 抽样 10 个入口，映射与实际出口一致率 100% | 经该闸口入口实测 |
| 恢复时刻准确性 | 每次 429 记录的恢复时刻与 Retry-After 一致 | 429 响应头 |
| 行为等价 | 第一批搬移后，相同输入下选点结果与搬移前一致 | 回归对比 |

## 9. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 出口查询走错入口，重现污染 | 强制经该闸口自身端口，禁止使用 7890；抽样校验 |
| 映射缺失导致误判为独占 | 缺失按"独占"处理，只影响分组精度，不影响可用性 |
| 出口级记忆误伤多入口组 | 组内轮转保证每个入口都会轮到，只是频率降低 |
| 切回 blind 模式（9router 不可用时自动回退） | 6 小时避让窗口会用污染地址判断"哪个出口刚被烧过"，把同一地址桶里的几十个节点当脏出口集体回避。当前观测模式下该路径惰性，一旦回退立刻生效。 |
| 第一批重构引入行为差异 | 只允许纯搬移，用回归对比证明等价 |

回滚：所有改动集中在 `asip/gate/` 包内，门面之外只留一行接线；回滚即断开门面调用，恢复原路径。

## 10. 结构前提

`asip/gate/` 作为独立包，与主模块隔离：

- `ledger`：出口级账本（映射、用量、耗尽时刻、恢复时刻）
- `allocator`：出口级遍历 + 组内轮转
- `policy`：耗尽/恢复的状态机
- `health`：只回答连通性，无判死权
- `config`：闸口自身参数
- `facade`：对外唯一入口，暴露 current / rotate / snapshot

共用部分下沉到 `asip/common/`（时间、锁、原子写、日志），不复制。

第一批只做搬移：把现有选择逻辑原样迁入，证明行为等价后再改语义。这样即使新语义出问题，也能确定问题不在结构上。
