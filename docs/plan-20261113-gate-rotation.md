# 第七闸口（代理池轮换）问题审查与修改计划书

- 日期：2026-11-13
- 对象：第七闸口 = 代理池轮换（slot-7，port 7897，Clash API 9097）对机场订阅池节点的轮换
- 不在对象内：渠道轮换（WARP 换线/重连/秒切槽）、渠道块内部的 IP 延迟择优打分器、常规槽 1-6 的修整链路
- 证据来源：daemon.py / config.py 实码、journalctl（gate.log / daemon.log）、sqlite 只读、Clash 9097 只读 GET、UDS /slots 与 /debug/state 只读 GET
- 数据窗口：2026-11-13 12:28–18:28（6h）；闸口真实活跃段 13:11:12–16:50:49（3.66h）；长基线用 gate.log 全文件（14.12h）

## 0. 一句话结论

闸口不是「轮换太频繁」，而是**成功判据、记忆维度、候选集、状态一致性四层全部错位**：它把「写进配置」当成「换成功了」，把「能连 gstatic」当成「能扛 opencode 配额」，把「节点名」当成「出口」，再用一份被污染的 IP 台账把 203 个池成员压到约 62 个可选项。结果是：93.6% 的轮换在 60 秒内被下一次报错否决（中位 3 秒），而这条证据不进入任何状态，系统因此永远学不到东西。

## 1. 名词表（先定义，后使用）

- **selector（选择器）**：sing-box 里「当前指向哪个出口」的容器。闸口换节点 = 改这个容器的指向，不是改节点本身。
- **P2C（Power of Two Choices）**：随机抽两个候选、按分数选更好的那个。分数由「延迟」与「调用次数」两维组成。
- **判死（_DEAD_NODES）**：把节点标记为不可用一段时间，期间不参与选择，有到期重测的复活机制。
- **冷却（_COOLDOWN_NODES）**：节点被换下后短期不再选它，当前固定 60 秒，按**节点名**记。
- **合并窗（coalesce）**：同一槽位在 800ms 内的多次报障只执行一次轮换，防并发风暴重复烧节点。
- **恢复即回**：报障时若存在「表上健康」的常规 WARP 槽，直接把重试目标指回它，不换池节点。
- **秒切兜底**：常规槽都修不了时，把流量指到闸口（7897）。
- **在役窗（serving window）**：闸口认为「流量正在我身上」的时间窗，默认 300 秒；窗内才做主动轮换。
- **预检（preflight）**：切换前对该节点做一次 gstatic 连通性探测，失败则重选，最多 3 次，不判死。
- **漂移自愈（drift heal）**：检测「磁盘配置成员」与「运行时成员」不一致并修复的机制，目前只覆盖 WARP 槽。
- **命中率**：一次轮换后，在观察窗内没有收到同签名报错的比例。它是「轮换有没有用」的唯一可测定义。
- **出口 / 协议族**：出口是真正出网的地址；协议族指 IPv4 / IPv6，两者额度独立计。
- **配置态 / 业务态**：「选择器指向了目标」是配置态；「经由它能成功完成一次业务请求」是业务态。

## 3. 根因链（从最根本到派生）

### R1（最根本）判据错位：把「配置态」当成「成功」，把「连通性」当成「业务可用性」

**现象**：闸口在 PUT 成功后立即把槽位标为 ok，没有任何数据面验证；健康三态由 3 个随机节点的 gstatic 探测决定。

**机制**：`_proxy_gate_rotate_node` 的验证只有「回读 selector 的 now 是否等于目标」。这证明的是「写进去了」，不是「能用」。而 ok 有三个来源：探针通过、**PUT 成功**（无探测）、缓存未过期的旧结论。三者混在同一个状态值里，下游无法区分。与此同时，池健康由 3 个节点的 gstatic 204 决定，而真实失败是 opencode 侧的账号配额 429——两者正交：节点连 gstatic 必然通，连 opencode 必然 429。

**数据**：轮换后 3 秒内又收到同一节点报错是常态（中位 3s）；13:13:31 换到 `cn.bing.com:443~3-any`，13:13:33 该节点即以 rate429 被换下。当前 slot-7 为 `ok` 但 `serving=false`、`egress=None`——ok 与可用完全脱钩。

**为何是根因而非症状**：下游全部决策都以这个 ok 为准——是否把 7897 递给 9router、是否回指常规槽、是否停止兜底。判据一旦失去业务语义，后面所有策略优化都没有意义。

### R2 无反馈闭环：轮换结果不落账

**现象**：系统没有任何地方记录「这次轮换之后有没有用」。

**机制**：失败证据客观存在且完整——下一次同签名报错就是上一次轮换的判决书；但代码只把它当作一次新的触发，不回头关联。选择侧的输入只有延迟表、60s 冷却、判死集合、以及每 20 分钟清零的调用计数。仓库里唯一实现过这条闭环的是 `GateRotateBackoff`，它也只做「跳过本次轮换」，不记录、不回馈选择，且被配置开关整体旁路（6h 内 0 条日志）。

**数据**：93.6% 的轮换在 60s 内被否决，同一节点仍被反复选中（最高 24 次）——每次只冷却 60 秒，到期重新参与抽签，没有任何累计惩罚。

**为何是根因**：没有它，任何改动都不可证伪。这也是上一轮「退避」方案能成立的土壤：没有指标，就只能靠推测宣布成功。

### R3 记忆维度错配：记忆的键是节点名，而失败发生在出口/协议族维度

**现象**：冷却、判死、近用、延迟样本全部以节点名为键；`call_count` 是死字段（恒 0）；协议族在选择层没有任何承载维度。

**机制**：`~N` 后缀只是同一 host:port 下的不同 SNI，不是不同出口，也不是协议族标记；池配置里没有任何 v4/v6 字段。因此「额度按协议族独立计」这件事在选择层不可表达。更严重的是 `call_count` 恒 0 且每 20 分钟清零，使 P2C 的「调用次数」维度失效：压力模式排序 `(-calls, ds)` 在 calls 全 0 时与正常模式 `(ds, -calls)` **完全等价**，「均匀分散」在闸口上是恒等式。闸口选点还显式 `count_call=False`，从不自增。

**数据**：171 行 call_count 全 0；去重组内按 call_count 取代表全部并列 → 代表被钉死在配置顺序最前 → 14h 内 48 个节点零命中，其中 16 个正处在被压掉的组里。

### R4 候选集失真：用污染 IP 去重，把 203 压到约 62

**现象**：`_dedup_by_ip` 名义上「同一出口只留一个」，实际按一份与节点无关的记录值分桶。

**机制**：`node_info.ip` 的写入函数 `fetch_node_ip_region` 完全不使用传入的节点名，它经**主进程 7890** 查 ipify，记录的是写入那一刻**主进程落池节点**的出口。于是每个被轮换的池节点都被写上「别人的地址」。

**数据**：171 行只有 30 个不同值，最大一组 67 个节点共享 `51.241.140.86`；实测对照——闸口当前节点 `upoz...:28065-any` 真实出口 141.148.214.234，库里记的是 185.14.47.180（主进程另一节点的出口）。去重把 203 压成约 62：**真不同出口被误杀，真重复出口反而保护不了**。

### R5 判死噪声：单次失败即判死，重启后成批假死

**现象**：一次探测失败即进死表 30 秒，没有「连续 N 次」门槛。

**数据**：6h 内判死日志 2119 条，91.8% 是「连续失败 1 次」；死表峰值 143/203（70%），当前 90/203；16 次「成批失败」事件中 12 次落在 daemon 重启后 60 秒内，同批节点 15 秒后复测只剩 1 个失败。

**机制**：判死表是共享资产，闸口、主路径落池、补闸都读它。把「基础设施瞬时抖动」与「节点真的坏了」混成同一状态，等于随机削掉可用面，还把闸口推向「无候选」。

### R6 状态一致性缺陷：并发写、时间证据恒 0、合并窗丢证据

**现象一（并发写）**：`/rotate` 的换节点在全局锁内，keeper 的主动换节点**不持锁**。两条路径可同秒对同一 selector 各写一次，最后写入者胜。6h 内 4 次「PUT 成功但回读不符」全部与同秒 proactive 重合；验证失败被当成「换不出来」，进而回 `no_healthy_slot` 并触发整机重启信号。

**现象二（时间证据恒 0）**：回执里 `switched_at` 取自槽位状态，而该字段的唯一写入口只服务 WARP 槽，池闸从不经过它 → slot-7 的 `switched_at` 永远是 0。后果：合并窗吞掉的请求回执里既无 `switch_to_url`、又无 `switch_to_node`、`switched_at=0`，9router 一条重放条件都不满足 → **423 条请求白报一次障**。

**现象三（合并窗语义不一致）**：主路径与常规槽是「合并不换线、证据照收」，池闸是「合并即全丢」——被合并的报障既不冷却节点、也不刷新状态。

### R7 边界治理缺口：漂移自愈与可观测都对池闸例外

**机制**：配置热载后的成员校验与 keeper 兜底都对 `slot-7` 直接 `continue`；漂移检测用的是 WARP 的 selector 与 WARP 成员过滤，池节点会被过滤掉。所以订阅新增节点**永远进不了闸口的轮换集**，容量静默缩水，无告警、无自愈。

**可观测**：`_api_stats["switched"]` 从不统计池闸（实测 0 而实际 1103 次）；`/slots` 对 slot-7 恒 `serving=false`；日志无出口协议族、无上一节点在役时长、无「轮换后首个结果」。

## 4. 修改方案的逻辑（每条对应一个根因）

**M1 对应 R1：把「成功」重新定义为业务态。**
- 改什么：闸口不再以「PUT 成功」作为成功；改为「轮换后观察窗内未收到同签名报错」才算成功，「收到」即判失败。健康拆成两维：连通态（既有探针）与业务态（来自报错反馈），不再混为一个 ok。
- 为何能解决：失败证据只有 9router 有，接进来之后 ok 才有业务含义；不新增业务探测，因此不烧配额。
- 影响面：只改判定来源，不改触发与执行，9router 契约不变。
- 验证：「ok 但下一次请求即失败」的比例应从高位显著下降。

**M2 对应 R2：建轮换结果台账。**
- 改什么：每次轮换记录（旧节点、新节点、原因、时刻、出口族若可知）；下一次同签名报错到达时回填「上次轮换存活秒数」；提供只读导出。
- 为何能解决：把已经在日志里的证据变成可计算的状态，命中率第一次成为可测指标，后续每条改动都可被证伪。
- 影响面：纯记录，不改行为；需决定持久化（重启不丢证据）。
- 验证：命中率可计算，并与日志抽样对齐。

**M3 对应 R3：记忆加「累计惩罚」，并停止制造错误身份。**
- 改什么：同一节点被换下的次数累计，冷却时长随次数递增（60s→2m→5m→…），而不是永远 60s；闸口维护自己的惩罚视图，不污染主路径共享冷却表。
- 为何能解决：93.6% 的新节点 60s 内再失败，说明故障时间尺度是小时级而记忆只有 60 秒。让被反复证明烧过的节点退到队尾，是提高单次有效性，不是减少轮换。
- 影响面：必须与共享冷却表分层，否则会同时改变主路径行为。
- 验证：同节点重复被选次数分布、命中率同步观察。

**M4 对应 R4：停止在污染字段上做去重。**
- 改什么：`_dedup_by_ip` 不再使用该字段；立刻停止向池节点写主进程出口；已有脏值标记为不可信，不参与任何判断。
- 为何能解决：203→62 的压缩没有任何有效依据，且误杀真不同出口。解除压缩后候选面回到接近全量（扣除真实死节点）。
- 影响面：去重是共享函数，主路径也调用——需先量化主路径依赖，再决定「全局停用」还是「按数据来源分层」。
- 验证：有效候选数、被选中节点分布、零命中节点数。

**M5 对应 R5：判死门槛改为「跨样本连续失败」，并给重启加宽限。**
- 改什么：单次失败不进死表；要求连续 N 次、且失败来自不同探测轮；进程重启后的首轮探测不判死；死表跨重启保留或在宽限期内不写入。
- 为何能解决：91.8% 的判死与 12/16 的成批假死都指向「把抖动当坏了」。改门槛直接回收被误杀的可用面。
- 影响面：判死表是共享资产（闸口、主路径、补闸都读），必须按证据质量分账，不能只给闸口打补丁。
- 验证：单次失败判死占比、死表规模波动、重启后成批判死次数。

**M6 对应 R6：让「对外说法」与「内部事实」一致。**
- 改什么：① keeper 换节点与 /rotate 共用同一串行入口；② 池闸拥有自己的 `switched_at` 写入口，任何真实换节点都写入；③ 合并窗内被吞掉的请求，回执必须带「刚刚换过」的时间证据与目标节点，不能回「无可用闸口」。
- 为何能解决：4/4 验证失败与 423 条不可重放回执都源于这三个缺口；补齐后假故障与白报障同时消失。
- 影响面：锁范围扩大可能拉长 /rotate 延迟（当前锁内已含多达 3×10s 预检），需与「预检移出锁」一并设计。
- 验证：PUT 后验证失败次数（目标 0）、coalesced 回执可重放率（目标 ≥95%）。

**M7 对应 R7：把池闸纳入同一套治理。**
- 改什么：漂移检测改用池 selector、去掉 WARP 成员过滤；统计口径纳入池闸；`/slots` 如实反映闸口在役与出口；日志补出口协议族、上一节点在役时长、轮换后首个结果。
- 为何能解决：容量变化从此可见可修，改动效果可被观测。
- 验证：debug/state 的 drift checked 对 slot-7 大于 0；stats.switched 与实际轮换数一致。

## 5. 明确不做（并列明理由）

1. **不限制轮换频率、不加退避、不加节流。** 理由：轮换是唯一的搜索手段；上一轮方案的收益是噪声级（日志少 1%、预检少几个请求），代价是把搜索速率降到 1/17。6h 内闸口轮换只占系统动作的 4%（1103 vs 渠道层 WARP 重连 26229）。
2. **不改渠道层。** WARP 换线、重连、秒切槽、槽位修整都不在对象内。
3. **不改「恢复即回」的优先级。** 它 91% 的复发率是事实，但属于渠道轮换域的判据；本计划只把它作为 R1 的旁证记录，不在本次修改。
4. **不改选点打分器的最优性设计。** 只修它的输入（身份、计数、判死），不动 P2C 本身。
5. **不在没有测量前改任何行为参数**（阈值、窗口、间隔）。

## 7. 风险与回滚

- **共享资产风险**：冷却、判死、去重三处都是主路径与闸口共用。任何一处改动必须先量化主路径依赖；方案优先「分层视图」而非「全局改语义」。
- **锁与延迟**：串行化范围扩大可能拉长 /rotate；因此 M6 必须与「预检移出锁」同批设计，避免用正确性换延迟。
- **身份数据**：停止写污染 IP 会让 dedup 立刻失去输入——这是期望效果，但要确保代码对空 IP 有明确分支（不得回退成「全部同组」）。
- **回滚**：每条改动独立开关，默认关闭新行为；指标达标后再逐条启用。任何一条无法给出量化改善即回滚，不做「审美性重构」。

## 8. 结构性前提（不是问题，是使能条件）

当前 7 条根因里有 4 条（R3 记忆、R4 候选集、R5 判死、R6 一致性）落在「主路径与闸口共用」的资产上。没有模块边界，就无法安全地「只改闸口这一侧」。

目标形态：`asip/gate/` 包，含 policy（纯决策）、state（池状态所有权）、actions（PUT/验证/预检，依赖注入）、health（连通态与业务态）、config（本模块参数）、tests（模块内测试与假件）。对外只暴露一个 Facade；`daemon.py` 只保留构造、注入、两条调用（UDS /rotate 与 keeper）。判据：模块不 import daemon、不 import config；可整体搬到另一进程仍可运行；测试不依赖 daemon 全局状态。

配套目录治理（独立工作流）：根目录现有 295 项（140 个 .py，其中 65 个 test_*；93 个 .json 多为 `cap_*` 实验残留；10 个 log）。归档必须 `git mv` 保历史、分批验证 pytest 收集与 systemd ExecStart 路径，不与逻辑改动混在同一批。

## 9. 顺序（按根本性，不按好修）

R1 → R2 是「先让系统能看见」，R3 → R5 是「再让系统选得准」，R6 是「同时保证说法与事实一致」，R7 是「让上面这些长期可见」。

M6 中「并发写」与「switched_at」可以先于 M1 落地，因为它们是不依赖新指标的正确性缺陷；但必须与「预检移出锁」同批，否则会以延迟换正确性。
