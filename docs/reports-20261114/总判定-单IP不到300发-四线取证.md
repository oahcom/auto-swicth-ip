# 总判定：生产单 IP 为什么达不到 300 发（四线交叉取证）

> 窗口 2026-11-13 02:00–19:35（有效负载约 8.6h，04:00–12:59 服务停）
> 取证：4 条并行调查线（上游规则 ×2、asip 法医、代码审查）+ 主控交叉对码 + 互相纠错
> 行号基线：daemon.py **20:16:37 版（16,414 行）**；审查期间该文件被另一路改动（+508/−86，台账 expires_at/影子采样，未触碰换线逻辑）
> 报告索引：trackA-会话复活取证.md / trackB-7897与时段性.md / trackC-误切与记账法医.md / trackD-换线代码审查.md（含各自脚本与数据）
> **口径裁决（终）**：主口径 = 8,684 WARP attempt / 7,468 WARP 绑定 / **1.16 发每绑定**；闸口 4,572 次借道 attempt 单列不下沉到 IP；13,256 仅作全流量脚注（比例结论三口径一致）

---

## 0. 一句话结论

**"300 发/IP"测的是 IP 额度的独占容量（L2 实测 0–358），但生产里 429 以请求/会话身份为主要维度、出口 IP 为次要维度——换 IP 的边际救活率只有 0.87%（分段 0–4.2%），96.1% 的 429 发生在换过出口/会话之后，却把每 IP 承载摊到 1.16 发/绑定。单 IP 达不到 300 是两层叠加：①结构上我们从不让 IP 攒量（429 即换线、换线必挑处女 IP、端口 15s 预冷却白跳、借道弹跳）；②即使攒量，当前 429 里只有少数是 IP 额度型，300 这个口径本身需要修。**

## 1. 达标判定：不达标，差两个数量级

| 指标 | 数值 | 对照 |
|---|---|---|
| 每 IP attempt：中位 / p90 / p99 / max | 5 / 27 / 131 / 205 | 预期 300 |
| **≥300 发的 IP** | **0 / 695** | — |
| 每次(WARP端口,IP)绑定承接 | **1.16 发**（8,684 attempt / 7,468 绑定） | 到 300 需绑定降到 ~1/30，消除 99.6% 换线 |
| 真实换线 | 5,304 次（拆分：**同端口换节点 2,391**（闸口池内换 node）+ **跨端口换槽 2,913**） | 真正 IP 消耗 = 跨端口 2,913 + 白跳 357 + 借道 1,440 = 4,710 |
| 429 结局请求 | 65% | — |

误切全消（transport 992 条可证无辜全救）→ 1.16→1.33 发/绑定、单 IP 12.5→13.9 发——**只闭合 300 差距的 13.3%**。
（全流量口径 13,256 attempt / 1.33 发每绑定；若把闸口借道算入分子 1.78——比例结论与口径无关。）
**per-IP 分布不受闸口污染**：8,684 本就是纯 WARP 口径，闸口 attempt 从未进入 IP 归属（反证：混入闸口后 max 会虚高到 733）。

## 2. 为什么：三层归因（按对 300 差距的贡献排序）

### 2.1 结构层（主因）：「429 即换线 → 换线即新 IP」的机器

- 每次 429 都换出口，每次换线落到**处女 IP**（`_warp_ip_rank` 四档：0 从未见 > 1 探针刚 OK > 2 撑过流量 > 3 无成功；daemon.py:7550）——结构上不允许单 IP 攒量。"中位 5 发"的直接成因（D2，✅ 对码）。
- 换线重试**每次都 sessionRotate**：trace 实测某 IP 9 秒内 4 次重试把 15 格会话池烧掉 4 格——不做功也在消耗 L1 的 40 个 session 名额（trackA）。
- **端口 15s 预冷却（D16，新）**：`asipRotate.js:300-302` 在请求 asip 前就按客户端分类打 15s 端口冷却，唯一清除通道要 daemon 回 `line_ok`（asipRotate.js:173）而 **daemon 从不返回 line_ok**——already_retired/coalesced/too_frequent 这些"本意保留端口"的结论照样被冷却，请求被挤到别的槽白烧新 IP，且两套冷却表不互通。
- 探针全天 33,052 次是**发包活动量**（= 生产 attempt 的 2.4 倍、按请求 5.1 倍），**不等于额度消耗**——机制上：429 节点探测烧 0 格（响应即 429，无量可扣），OK 节点有 30 分钟结论缓存（TTL 1800 命中即复用不实测），每线每 30 分钟最多烧 1 格。探针真正的额度代价 ≈「OK 判定的去重 IP 数」，不是 33,052。（但探针 OK ≠ 生产可用仍成立：探针一句话 body vs 生产 144–300 MSG，探针 OK 484/h 时生产首死 94.8%。）
- **换线几乎不救请求**：闸口边际救活 19/2,186=0.87%（**分段：02–04h 0.21%、13h 4.2%、14:00–16:45 0%**——13 点池里有干净节点时换出口并非完全无效，14 点后 807 次换 198 个出口全灭）；96.1% 的 429 记账发生在非首发端口，首发 attempt 的 429 只占 3.9%（185/4,790）；51.4% 的请求在 429 过程中跨过 ≥2 个出口 IP。

### 2.2 上游层（方向 1：opencode 未探明规则）—— 429 以身份/会话为主，出口 IP 次要

- 【推断·已收窄】**该 429 以请求/会话身份为主、出口 IP 有次要作用，两者比例未知**。证据：换 IP+强切会话后仍 429 占 46.5%+（按换过节点算 96.1%）；换机场出口救活率 0.87%（分段 0–4.2%）；13 点 4.2% 说明出口并非完全无关。**不能再说"换 IP 完全无效"**。
- **16:45 悬崖（强，但是我们自己踩的）**：新 IP 首死率 94.8%→6.2% 压缩在 16:45→16:46 一分钟，与 9router 16:45:45 重启同秒（主控复核：16:44–16:47 共 50 条 ERROR 429，16:46 后归零）；排除自身负载与上游波次。推断重启清了进程内 auth/会话复用状态（关联 15:37 P0-3 resession），但 15:54 同类重启无效、确切变更【未知】→ **当前 17–20 点的健康不是稳态**。
- **/64 段级热度（中）**：自身 429 的 83.5% 落在 300s 内刚烧过的 /64（基线 41.4%，2 倍富集）；净段首发 429 率 15.5% vs 热段 ~27–30%。段级影响"429 是否发生"（产生端），不解释复活。
- **IP 级额度（L2）真实存在但非生产 429 主体**：单 session 连打实测 215–358 发/IP；真自身-429 的 98 个 IP 里 87.8% 窗口内不复活（探针 quota→OK 间隔 1,532s–64,245s，一簇 ≈16h 对齐 Retry-After）。
- **session 侧上限真实存在**：固定 session ID 跨 IP 复用被全局拉黑；L1=40 session/IP。
- 未钉死：L2 是 per-IP 还是 per-IP×session（生产日志不可分）；新连接短窗门控（推断）；段级共享额度 vs 热段选择效应。
